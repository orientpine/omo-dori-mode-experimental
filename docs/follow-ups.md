## Heavy tools: two installs of a tool are named only when the job runs here (#397)

With two installs of rv under `~/.local/share` and none on PATH, `dori heavy --tools rv` sends `tools=rv` without a version, and `HEAVY_TOOLS_UNCLEAR` (which names both installs) is printed only when the job then runs here; a helper that takes the unversioned job runs its current bundle and nothing says the caller's rv was unclear (review of #397, LOW). The egress gate (#370) takes the owner's card answer as proof only from its own receipt of his tap (`card-receipts.jsonl`); the node (cytoplasm `owner_origin`, #232/#233) cannot read that file and still trusts the card's text, so its only guard is that the gate refuses every hand-made answered card at the Discord port and rebuilds every Discord write it forwards. A card forged before #370 was installed stops counting on the node 24 hours after it was posted. What would close it: the node reads the gate's receipt for the card (a read-only gate endpoint or a shared receipt file) instead of the card's text.

## Lane handover: one record per lane, with a generation number (#320)

A lane's waiting handover is spread over several per-lane files: the lock, the pending journal, the ready mark, the ready-resume claim, the safe-point file and the facts snapshots, plus the waiting request read from the last rollover row. Review rounds 7-12 of #320 found 2-5 new races per round, nearly all between two of those files. #320 therefore keeps crash repair as main had it: a dead journal is repaired by the next handover run of the lane, under the lane's lock, and `freshness` repairs nothing itself.

What would close it: a single per-lane record, written under the lock with a generation number that each writer checks and bumps (compare-and-set), holding the request, its phase (asked, waiting, moving, repointed, committed) and the run that owns it. Recovery then reads one phase instead of inferring one from several files, and `freshness` can finish a committed move or undo an uncommitted one by itself. Write the crash points x actors as one table test before the code.

Until then a run that dies after repointing the lane, before it finishes, leaves the move to the next `dori handover --lane <key>` run, whether the lead starts it or an automatic rollover does.

Design chosen after review round 17 of #320 (not started; the lead set it aside on 2026-11-04), plan `/tmp/tmp.6Nnl3yJr6R/plan-320-r17.md`:
- One record per lane, `<stateDir>/handover/lanes/<key>.handover.json`, changed only by a transition under the lane lock; it folds in the lock owner, the waiting request, the ready-resume claim, the takeover files and the journal, and the rollover log stays history only.
- Three numbers: `rev` (every write, compare-and-write), request id (`at` + `by`), and `epoch` (the fencing token, bumped only when ownership of the move changes), checked under the lock at the repoint and the commit row.
- One executor: commands (lead run, ready mark, `--force`, a due auto) only write intent, and one `reconcile()` does every move, so the owner's four flows (one waiting request, start again on ready or idle, the first `--force` moves, never two moves) are checked in one place. Cutover is quiesced (one PR switches every writer and imports a waiting row once); liveness holds given that the lane eventually goes idle or ready and freshness keeps sweeping.
- About 3 PRs: record + `reconcile()` + an exhaustive interleaving harness (safety checked before review); cutover of the writers; docs + herdr QA.

## Lane handover: an exception after the commit with --keep-old rolls the move back (#320)

With `--keep-old`, the new session is told `HANDOVER_COMMITTED` before the post-commit steps (the note append, the owner report). If one of them throws, the run's exception repair uses `recover()`, which closes the new session while the old one is alive, as on main. A process that dies there is handled the same way by the next run. The lead accepted this as main's behaviour on 2026-11-04. The record above closes it: the committed phase makes recovery finish the move.

## Lane handover: a crash between the idle-moment freeze and the journal leaves the old agent stopped (#320)

An automatic start (`--wait-idle`, or a waiting request `freshness` starts again) freezes the lane's agent at its idle moment, before the new session opens and before the pending journal is written. A run that dies in that window leaves the agent stopped (state T) with no journal, so no later run knows to thaw it. The code is the same as on main (plan challenge of review 320 round 13). What would close it: write the journal, or the per-lane record above, with the frozen agent's pid and start time before the `SIGSTOP`, so the repair under the lock thaws exactly that process; until then the lead resumes a stopped lane by hand (#332, open, has `dori watch` report it as `LANE_SUSPENDED`).
- A lane handover that meets a stopped or backgrounded agent reads its stale screen as main does (busy), and its rows go into the waiting-request ledger the same way. #332 gives it one design of its own: a stop state that keeps the lead's request waiting (`blocked` stopped, never terminal), keeps an ask the lane has not taken on the request, and delivers any typed text only while the agent is its tty's foreground group (`tpgid == agent pgrp` from `/proc/<pid>/stat`, not the pane's command name). Its acceptance tests are the three review rounds that tried it in #333 (a request kept waiting through a stop; an undelivered ask carried through it; a first request made during the stop getting its ask), in the branch history at 9f8fe43 and e160aa9. Main already types an untold safe-point ask from `freshness` readyResume without checking who holds the tty; the same gate closes that.

## dori send: the last post of a place counts only dori send's own posts (#338)

#338 refuses a new message equal to the last post `dori send` or `dori thread reply|wait|done` made to that place, at any age (`SEND_DUPLICATE`, exit 3, `--again` posts). Nine review rounds of #338 recorded every post and edit at the messenger layer instead, and each round found a new interleaving between the writers of that one record (out-of-order completion, an edit while the posting command waits, a close summary posted past `dori send`, a Slack share with no ts, clock skew, two edits at once, a live edit lock taken over by age or by the day-old cleanup, a topic edit without its topic, a double record write, link naming done twice, an unmatched thread edit, the creation record racing an edit). The lead split it on 2026-11-04: #338 keeps only `dori send`'s own posts; the ledger goes to its own PR.

Left out, so today: an edit does not move the record (send A, edit it to B: A is refused once more, B can be sent again once); a post another command makes (a close summary, a lane post, a card) and a Slack file share are not the place's last post (the text before them is refused once more, `--again` posts it); two inputs that differ only in a thread link written bare or masked key apart (a `--ping` already in the text keys as the one message).

What would close it: one writer of the record per message, every post and edit through it under one per-message kernel lock (takeLock, never by age, kept out of the day-old cleanup), the comparison and the record keyed on the exact prepared payload that is posted (prepared once), unresolved edits kept apart by platform, chat and message id instead of promoted to a place, and a Slack share recorded only under its real ts. The work so far, with a regression test for each finding of reviews 1-9, is on the branch `fix/send-ledger` (4aa2d75); review 9's three findings (prepare twice, unmatched thread edit, creation record vs edit) are its acceptance tests.

## Session readers: one argv source that keeps word boundaries (#342)

`resolveSession` (session-id.ts) splits an agent's command line on whitespace outside Windows, and every session-log reader except herdr's lead record looks only in `sessionsDir`'s folder for the cwd (background.ts, handover.ts, launch.ts, explore.ts, auto-signals.ts; launch.ts gives up on a `--session-dir` session). So an agent started with a spaced `--session <file>` and no `--session-id` is not identified, and a spaced `--session-dir` is cut at its first space. #342 reads the herdr lead's session log only where the agent's arguments keep their word boundaries: the exact log path omo hands its bash and eval children (`PI_SESSION_FILE`, Linux) comes first, then the log the arguments name (Linux `/proc/<pid>/cmdline`, Windows `winArgv`; a `--session` to another copy of the session goes over the one recorded), then the log recorded before for the same session; a log that cannot be read keeps the session's recorded model instead of the launch `--model`, and arguments whose boundaries cannot be read name no log (never a whitespace split). On macOS no log is looked for from the arguments until this follow-up gives it boundary-keeping ones: only `PI_SESSION_FILE` and the log recorded before are read (and the recorded log at revive time), else the launch `--model` stays, as on main. A lead whose session cannot be identified keeps its record as it was, as on main.

What would close it: one argv source in session-id.ts, used by `resolveSession` and every log reader. On Linux it is `/proc/<pid>/cmdline` (NUL-separated). On macOS it is `sysctl KERN_PROCARGS2` (argc, then the executable path and its padding, then NUL-terminated arguments; https://chromium.googlesource.com/crashpad/crashpad/+/360e441c53ab4191a6fd2472cc57c3343a2f6944/util/posix/process_util_mac.cc), opened through `bun:ffi` on first use the way checkpoints.ts opens libc. On Windows it stays `winArgv`. `ps` text cannot give the boundaries back. Test each platform on its own OS (a Mac and Windows), not only here on Linux.

## Heavy: a helper run whose command never started goes back here (#372)

#372 checks the programs a job starts before a helper admits it: `need=` paths and `which=` names are looked for in a box made like the job's (same mounts, PATH, the job's folder for relative PATH entries), and a helper without one refuses, so the job runs here (HEAVY_LOCAL). A check before the run can still differ from the run itself (the helper's system changing in between, a lookup rule exec has that the check lacks), and then the run on the helper ends 127 or 126 as a local run would, with the shell's line on stderr: a failure, never an empty success.

What would close it: tell "never started" from the job's own exit on the helper and rerun only the first here, as distcc reruns its accidental failures locally. bwrap's `--json-status-fd` writes `exit-code` when the command ran and none when its exec failed, but none either when the scope kills a started job (RuntimeMaxSec, MemoryMax), so it needs three outcomes: completed (exit-code), proven not started (no exit-code, bwrap exited 1, not by a signal, before any output), interrupted (anything else: keep the failure, never rerun). Write the test first: `sh -c 'echo STARTED; sleep 30'` with the bwrap monitor killed after STARTED must not rerun here. Sources: the dori challenge of 2026-11-07 on plan-r5 and tree F188-F214.
