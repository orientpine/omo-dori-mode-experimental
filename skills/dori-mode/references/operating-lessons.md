# Operating lessons

Things that went wrong, or nearly did, while running a Dori every day, and what to do instead. Each one names the behavior of the scripts that causes it, so you can check it still holds.

## 1. A done claim closes the lane: do not give it more work afterwards

When a lane runs `dori claim-done`, `dori watch` waits out the close window (`closeAfterMin`, 5 minutes by default), reads every `Done =` signal back, and when they all hold it closes the lane: the thread is marked done, the aoe session or herdr tab is closed, and the lane's worktrees are removed. An instruction you send the lane after its claim is lost with the session, and the follow-up has to start as a new lane.

If you want the lane to do one more thing after it claimed:

- run `dori object-done <key> --reason "<the extra item>"` first, inside the window. The lane goes back to not-done and gets `[LEAD] not done: ...` in its pane; send the extra instruction after that, and it claims again when finished;
- or, when you launch it, give the lane a `Done =` signal that already checks the extra item, so a claim made before it is ready is turned into not-done instead of closing.

## 2. Pausing a lane that waits on the owner

`dori freshness` nudges every lane whose status is `working` and has been silent too long, and posts a short status line to the thread. For a lane that is deliberately waiting on an owner decision, that repeats a ping nobody can act on.

Pause it instead: `dori pause <key> "waiting on the owner's decision about X"`. The lane's status becomes `paused` and the reason goes into its history. From then on freshness neither nudges nor posts for it, `dori watch` reports no `LANE_BLOCKED` for it, `dori dead-panes` skips its pane, and a done claim it makes is announced (`LANE_DONE_CLAIMED_PAUSED`) but does not close it on a timer. When the owner answers, `dori resume <key>` puts back the status it had (working or not-done) and restarts its silence clock. Don't edit the registry file by hand for this any more.

## 3. A new lane thread starts with what it is for

A thread that only shows the lane's title and nothing else looks abandoned to the owner, especially when the lane reports only to the Dori's own pane. When you open a lane's thread, make its first post say in a line or two what the lane is doing and why. Post the lane's important reports (milestones, blockers, the done result) in that thread too, not only in your pane.

## 4. Replacing a question card that was never answered

If a card becomes moot before the owner taps it (you asked a better question, or the lane decided itself), run `dori resolve <qid>`. Besides forgetting the question, it returns the card's thread from waiting (⏸️) to working (🔄) when no other card in that thread is still open. Without it the thread keeps showing that it waits on the owner.

## 5. Two Dori bots in one channel: no eyes on the other bot

The eyes reaction promises "I read this and will answer". When two Doris share a pair channel (`DORI_DISCORD_PAIR_CHANNEL`, `DORI_DISCORD_PAIR_BOT`), the other Dori's posts arrive as `pair-bot` rows: information, not requests. The listener puts no eyes on them, because an eyes reaction that is never followed by an answer only confuses the people reading the channel. The owner's own messages in the pair channel still get eyes.

## 6. Applying an update to the scripts

`dori` runs the code of its clone (`~/.dori/src`) directly. After a change is merged upstream:

```sh
git -C ~/.dori/src pull --ff-only
```

One-shot commands (`dori ask`, `dori launch`, `dori send`, ...) use the new code at once. Long-running processes keep the code they started with until restarted. Configure `update.services` with their source prefixes, logs and ready patterns, then baseline `dori update` before the next pull. After a pull:

```sh
dori update
```

`dori update` replaces the manual restarts and ready-line checks, logs new unset config keys, and tells the lead what changed. The `dori-update.path` user unit runs it automatically when the clone's checked-out branch ref changes; see the setup's "Auto-apply updates" step. `dori update --pull` combines the pull and apply; the path unit's run it sets off waits for it and logs one `UPDATE_SKIP` line, so services restart and the lead is told once per commit. A rejected pull logs and alerts `UPDATE_FAIL` rather than silently leaving stale code running.

## 7. Replacing a listener: shadow first

To swap one inbound listener for another, run the new one as a shadow that writes only to its own inbox file and never to the messenger, compare the two inboxes id by id in a written table, then switch in one command that stops the old one before starting the new one, so the two never receive live at the same time, and keep the one-line rollback ready. The full procedure with the checks is in [`../setups/discord-aoe/README.md`](../setups/discord-aoe/README.md#switching-an-existing-listener-over).

## 8. What goes to the owner is in plain words

A lane's `[REPORT]` is a note for the lead: abbreviations, numbered items, an English head, written for someone who knows the plan. Posted as it is in the owner's thread it reads like an office memo, and the owner asked why it was written like that. Anything a script posts to the owner on its own must be in plain words, in the owner's language, and short.

- `dori freshness` posts `discord.quietText` (`{min}` = minutes since the last report) after `postAfterMin`, not the report. The report goes to the lead pane as `[DORI] <key>: ... Last report: ...`; when you see it, tell the owner where the lane stands in your own words.
- The automatic close in `dori watch` posts `discord.doneText` through `hooks.threadDone`, not `Done: <evidence>`. The evidence stays in the lane's record; sum up the result for the owner yourself.
- Set both in the owner's language, for example Korean in casual speech: `"quietText": "진행 중이야 — 마지막 보고는 {min}분 전. 정리해서 곧 알려 줄게."`.
- `discord.postRawReports: true` brings back posting the raw report and evidence. Leave it off unless the owner reads those notes directly.

## 9. Stuck on one metric: branch the explanations, do not repeat the patch

An RL lane (E7) training an excavator to dump soil into a bank kept failing on one metric: the policy picked up a load and stood still instead of dumping. The lead re-instructed it with reward patches, one after another: a dump credit, then a small reward for dumping waste in the spoil band. Each patch had a plausible story and none moved the metric. What found the cause was a forced four-way diagnosis: four competing explanations (the reward is too weak; exploration has collapsed; the critic undervalues the states after a dump; the geometry of the target makes dumping unreachable), each with one cheap test that only that explanation predicts. The exploration test answered first: the swing action's sigma had collapsed to 0.0068, so the policy could no longer try the swing that leads to a dump. Reward patches could never have fixed that.

What the scripts now do so this happens on the second failed patch instead of after many:

- `dori fix-attempt` refuses a second attempt on one metric with no improvement unless it comes with at least three competing hypotheses and one discriminating test each (`HYPOTHESES_REQUIRED`, exit 5). With them it logs `STUCK_BRANCH` and puts them into the area's hypothesis tree. `--improved` resets the count after a fix that did move the metric.
- `dori fork-explore` runs the tests side by side (GPU ones queue on the heavy slot) and prints one table; for E7 that is reward x2, a swing-sigma log, a value probe before and after a dump, and a reachability check of the dump point, all reporting the dump count.
- At the third attempt the lane is told to search outside first (`dori research-hint`: here, "policy gradient action std collapse" is a known failure mode with known remedies such as an entropy bonus or a std floor).
- The search goes through omo's ulw research, and that only starts from what is typed. omo attaches its ulw-research skill pointer only to typed input that names `ulw research`. A text that starts with a `[TAG]` such as `[LEAD]` is masked whole, and a brief that mentions the skill is not typed input. So the old `[LEAD] ... search outside` text never started it: no lane session on the host ever showed the pointer. The text now starts with `ulw research ` and the question built from the lane's records, and `dori research-check` reads the session log for the pointer (`omo-ulw-research:skill-pointer`) and a read of `ulw-research/SKILL.md` instead of trusting that the lane started.
- A read means a call that reads the file, not any call that names it. The first check counted any tool call whose arguments held `ulw-research/SKILL.md`. On a re-send in the same session the lane did not read the skill again, but it recorded a `dori tree add` finding whose text said "the session log shows ulw-research/SKILL.md was read", and the check reported `RESEARCH_STARTED`. It now counts only the `read` tool on that path, or an `eval`/`bash` call that opens the file (`Bun.file`, `readFile`, `cat`, `sed`, `head`, ...); quoting the path in a finding, an `echo` or a note does not count. The read must also come after the re-sent text reached the session: live, a lane still busy with the first send read the skill a few seconds after the re-send was typed but before it got the new text, then only quoted the path in a finding; that read is the first send's.
- The tree goes into every new brief for that repo, so the next lane sees "reward too small: falsified" and does not start from it again.
- Before the next expensive step (a nine-seed run), `dori challenge` gets a model of another family to argue against the plan, and `dori intent-check` compares the lane's new direction with the owner's goal in their own words, which catches a lane that has started optimizing a proxy.

## 10. The lead routes; it does not make the change itself

One day a Dori worked through a run of small requests by doing them itself: it renamed folders and the services that pointed at them, swapped a bot token in an env file, edited its agent config, and handed a few pieces to in-process child tasks. Each step was quick and each one worked. The owner still told it to stop and open a session for every job, however simple: none of those changes had a thread, a brief or a Done check, so the owner could not see what had changed or whether anyone had checked it, and while the Dori was busy editing, new messages waited.

Open a lane with `dori launch` for every change, even a one-line one, with a `Done =` signal that reads the result back. Keep for yourself only what changes nothing: reading to answer, launching, pausing and closing lanes, checking a done claim live, and messaging. A child task or subagent inside your own session is not a lane. The rule is in `SKILL.md`, "Every change goes to a lane".

## 11. The tool owns a thread's status mark

The owner asked why a thread was called "🔄 🔄 Dori ...". The lead had opened it with a title that already began with "🔄 ", and the code that opens a thread adds its own "🔄 ". On close only the first mark was swapped, which gave "✅ 🔄 ...".

- Pass a plain title. Never start it with 🔄, ⏸️, ✅, ⏳ or a `[working]`-style word.
- Every status change (reply, wait, done, a card asked or answered, a reopen, `dori close`, the automatic close) now strips all leading marks and writes exactly one, so a name that already stacked marks heals at its next status change.
- A local thread opener of your own (a `kit.ts` `openThread`) must do the same: strip every leading mark from the title before it adds one.

## 12. Tangled card answers and the rename limit

Three question cards went up in one thread in quick succession. The owner answered two by button and the third by voice in the thread, and the lead resolved that one by hand. Every ask, answer and resolve renamed the thread (⏸️ and 🔄). Discord allows about two renames per ten minutes per thread, so one rename came back 429 with `retry_after` 340 s. It was logged and dropped, and the title stayed wrong.

- Thread status renames now go through one queue per thread, persisted in `thread-status.json` next to `questions.json`. A burst becomes one rename. A 429 keeps the rename with the time Discord gave (`THREAD_STATUS_PENDING`), and `dori inbound discord` applies it then (`THREAD_STATUS_APPLIED`), also after a restart. Only a refusal that waiting cannot fix is dropped (`THREAD_STATUS_DROPPED`). A one-shot command never waits out the limit itself: it leaves the rename for the listener.
- The mark comes from the truth, not the last event: a closed lane is ✅, any open card in the thread is ⏸️, otherwise 🔄. A reply or an answer while another card is still open leaves ⏸️.
- When the owner answers in text in a thread where a card is still open, the inbox row carries `open_cards` and a `note` (`card Qn still open, owner replied in text`), and the listener prints `CARD_STILL_OPEN`. It never resolves the card on a guess. Read the reply, then `dori resolve <Qn> --answer "<the answer, short>"`: the card folds into its record the way a tap folds it (2026-10-13: a card answered in text and resolved kept its buttons until it was folded by hand). Resolving the last open card turns the thread 🔄.
- A local script that renames threads directly (a `kit.ts` `setThread`) must not retry inside the 429 window either. Write the rename to the same `thread-status.json` and let the listener apply it.

## 13. A reviewer that never writes the review

The E7 lane ran `dori challenge` on its next-run design three times and got no review each time (exit 1). The grok reviewers answered with one line, roughly "I will check the files first, then write the three sections", and stopped: the reviewer runs with no tools and one reply, the plan cited other files, and the model spent its only reply announcing that it would read them. The lane tried another model, a "this file is self-contained, write the three sections now" note inside the plan, and another working directory; none helped. The gpt and gemini reviewers failed for a different reason: their provider ids (`github-copilot/...`, `google/...`) were not logged in on that machine, and omo exits 1 with a pointer to its docs.

- The first fix (fork PR #31) told the reviewer it had no tools and retried a reply without the headings. It helped, but it treated the symptom, and a reviewer without tools thought for 3.5-7 minutes, past the old 5-minute limit.
- The root cause, found by reproducing the failure from the exact plan and tree: `omo -p` runs the reviewer as an agent, and an agent run ends at the first reply without a tool call. Given a plan that cites files and results, an agent model's habit is "announce, then read"; with `--no-tools` the announcement was the whole output (5 of 5 runs; the json event stream held nothing more, stop reason `stop`, no tool call, a few hundred tokens). Changing only `--no-tools` to read-only tools (`read,grep,find,ls`) in the plan's repository turned the same inputs into complete reviews (4 of 4, 7-8 reads each, about 3 minutes) that cite the real numbers. That is now the default; the stricter retry stays as a safety net.
- Reviewer ids are checked against `omo --list-models` and the logged-in providers before any call. A model on a provider that is not logged in is called on one that is; one no logged-in provider offers is skipped with the reason. `omo auth check` alone is not enough: it reports a subscription provider served by an extension as `not_ready` (`provider_not_found`) while its accounts are logged in, so an account that is not blocked also counts.
- The default order is the best GPT, Claude and Grok model a subscription login offers, then a second model of each. The first that writes a review wins; `--all` asks one of each family when one review is not enough.
- Check which reviewers your machine can call before you depend on one: `dori challenge --check`.

## 14. Switching the lead to a new session

A long conversation gets slow and expensive, so the lead moves to a fresh session from time to time. The work itself does not stop: lanes are their own sessions, and the registry, inbox and logs are files. What breaks is everything that names the old session:

- **Monitors.** omo restores persistent monitors only when the same session restarts (`self-restart.sh` restarts the same aoe session). A new session starts with none and hears nothing from the inbox, the lanes log or session events until it arms them again.
- **Reports.** Every running lane has the lead's tmux name written into its brief footer at launch, and `dori watch`, `freshness` and `dead-panes` read `leadPane` once when they start. Changing `config.json` alone leaves both pointing at the old session. `DORI_LEAD_PANE` set by a wrapper script wins over the file.
- **Cards and boot.** Open question cards keep the asking session's tmux name, and `dori-lead.service` and `self-restart.sh` start the pane in `DORI_LEAD_AOE_ID`/`DORI_LEAD_TMUX`.

`dori handover` does the switch in that order: a note, the new session, every pointer moved, then checks in the new session (its monitors run, a `[REPORT]` probe and an inbox probe are acked from it) before the old session is closed. If a check fails, everything moves back and the old session stays the lead. Before you run it, put what lives only in your head into a file and pass it with `--note`: promises to the owner, things you wait for, one-off reminders. Started from inside the lead, it detaches itself, because closing the old session ends the processes in it. The new session does not continue your conversation; the note is all it knows. A watch that is not an omo monitor of your session (a host guard, a listener started elsewhere) is invisible to it: list it in `handover.watchers` with a check command, or the new lead runs without it. A lead started from a symlinked folder gets its new session in the real folder; set `handover.cwd` if you want another.

## 15. Moving a lane to a new session

A lane that has run for days can be moved to a fresh session the same way the lead is, with `dori handover --lane <key>`. Three rules came out of building and trying it:

- **Only with a decision on record.** A crossing threshold only proposes (`dori rollover-propose` prints the proposal for the lead); the handover of a real lane runs with `--approved-by`, else it is refused. Since 2026-10-12 the lead decides (`lead:<reason and signal>`) and the owner is told afterwards, with that message's id in the log; an owner's card or link still counts. The only signal on is rung 4 of the stuck ladder (#19); context, compaction and age thresholds and the automatic mode are off (the evidence is in `references/rollover.md`) until the owner decides from `dori rollover-stats`, so a move never surprises the work the lane is doing.
- **At a safe point.** A running turn, an open question or a local child process (a training chain, a watcher loop started in the lane's shell) dies with the old session. The handover refuses then, unless the lane ran `dori handover ready` at a point where nothing is lost, or you pass `--force`. Detached jobs (systemd-run, nohup into their own session) survive; they are listed and never touched. Pausing a lane (`dori pause`) stops the nudges and rollover proposals, but it does not make the lane safe to move: the busy and chain checks still apply.
- **One copy of every job.** In the first live try, the new session read "a local chain was running" and started it again while the old copy still ran: the same work twice. The note now says "do not start these again now"; after the old session is closed the handover checks the chains and tells the new session `HANDOVER_CHAINS_ENDED` (start from the checkpoint or progress file, skip finished steps) or `HANDOVER_CHAIN_SURVIVED` (leave it alone). The new session can also come up on another account from the pool; the handover prints `HANDOVER_ACCOUNT` and the rollover log keeps both.
- **Nothing the conversation knows is dropped silently.** Before a move, the lane writes its conversation summary (the owner's words and constraints quoted exactly, decisions and why, what is ruled out, what is half done, the next step) and runs `dori handover ready <key> --note FILE`; the note also lists its fix attempts and the path of its full log. The new session restates what it understood before it is committed; what it left out (tried fixes, the owner's goal and quoted words, decisions) is filled in from the note and the old log, with the log lines quoted, and it restates again, up to `handover.supplementRounds` (2) rounds; only a gap that outlasts them rolls the move back, and its questions come to you as `HANDOVER_QUESTIONS`: answer them in the new pane. Until `HANDOVER_COMMITTED` it does no work, and the old agent is frozen, so two sessions never act at once.
- **The lead's own move is checked the same way.** Before `dori handover` for yourself, write your summary (`dori handover --template`: the owner's words quoted, decisions, what you promised him, what is half done, the next step) and pass it with `--note`. The new lead restates what it understood; every open lane, every card waiting for the owner, every timer and the owner's messages of the last 24 hours must be in it, and what it leaves out comes back with the old log lines, up to `handover.supplementRounds` rounds, before the move rolls back and you stay the lead.
- **Compaction is the normal mode.** The research (references/rollover.md, "Rollover or compaction only") found long runs on compaction alone working, no rise in errors or corrections after compactions in our logs, and a real cost to every move. Propose a rollover when a lane reaches rung 4 of the stuck ladder, or when the owner asks; not because a session is long.

## 16. Repeats and broken instructions without tags

The rollover and `SAME_FIX_3` signals counted fix attempts only when a lane tagged its report `(fix: <metric> / <hypothesis>)` or the lead ran `dori fix-attempt`. In the whole watch log `SAME_FIX_3` fired once, in a test. hr35-e7 changed prescriptions many times overnight with no tags, and only the lead reading its reports noticed. Intent-check's word overlap gave `INTENT_DRIFT` (overlap 0.00) whenever a Korean goal met an English report of the very step that served it.

- **Infer the loop from what the lane leaves.** `REPEAT_SUSPECT` reads the reports, branch commits and tree, and counts "a gate line failed, then a later prescription names it" per metric. On three days of real logs (2026-10-08 22:30 to 10-11 22:30 UTC, 355 hr35-e7 reports and 269 commits, 198 hr35-eth-beat reports and 62 commits) the first version looked good until the challenge (grok-4.7) printed its attempt times: its one "true" alert counted an eval report as both the failure and the attempt. Counted strictly (a failure is not consumed by the report that states it; only prescription words, not “시작”/“반영”, make an attempt), the defaults catch neither hr35-e7 loop. With two area aliases (교착 = deadlock(s), 정지 = 무작업/멈춤/hold/idle) and reports only, both loops come up with no false alert: the deadlock loop at 10-10 12:44, two hours before the lead stopped it by hand ("보상 조정 중단", 14:47), and the loam-1.0 hold loop at 10-11 15:44, before the overnight prescriptions; adding commit subjects adds two false alerts. hr35-eth-beat, which had no such loop, raised nothing in any setting. The aliases were picked after reading this window, so give an area its aliases when you launch it, and read each alert's evidence file before acting.
- **A discrimination is exempt only when it changed the next action.** The 2026-10-12 check of the installed version found the owner-confirmed 정지 loop on hr35-e7 (10-11) no longer caught: any report with `판별` in it cleared the failed lines, and hr35-e7 writes "판별 결과: ... 둘 다 기각" in the same report as the next prescription ("처방안 한 장 확정"). Dropping the bare `판별` was not enough: it then flagged the design report that came out of the registered probes X1'-X5 (10-12). The rule now looks at what the report does: one that tells hypotheses apart and makes no new attempt (it rules a prescription out, "처방 없음", or reports a probe) still exempts the next attempt; one that also prescribes counts as an attempt. Replay of 10-08 22:30 to 10-12 13:06 UTC: 교착 at 10-10 12:44 and 13:39, 정지 at 10-11 20:53, nothing on the probe day. The same replay found `안 ` in "처방안" read as "not", which hid a prescription; negation now needs the word.
- **Alerts, not brakes.** Neither signal stops or moves a lane. (Since #19 the inferred count is one input of the stuck ladder: with the owner's approval it can start rung 3's research in the lane, and it never starts an automatic rollover.)
- **Let a model read Korean, and check its quotes.** `OWNER_CHECK` gives a reviewer of another family the brief, the owner's words (in the brief and in `[LEAD]` relays with the Discord link or 원문) and the newest reports. Three things came out of live runs on hr35-e7: (1) the cheap `gpt-6-luna` flagged a relayed order's scope wrongly twice ("학습은 멈추지 말고 … 기존 기록만으로" read as "no new training"), `gpt-6.1-sol` read the same input as OK twice, so sol goes first; (2) the lead's own working orders are not the owner's words, and a constraint given for one experiment ("원인 확정 전 수정 금지") must not be applied to another, so only linked or 원문 relays are passed; (3) a planted report that started T-reward training before the registered verdict came back `VIOLATION` with both quotes verified. A quote the inputs do not contain is marked unverified.
- **A quote counts only where the owner said it, and only once.** On 2026-10-12 the check raised `VIOLATION` on hr35-e7 twice (09:46Z, 11:18Z), with the owner supposedly saying "학습은 멈추지 말고". The owner never said it. A 10-11 relay quoted his question ("정지한 상태에서 … 알려줘") and then went on in the lead's words: "학습은 멈추지 말고, 이미 있는 기록·문서만으로 …". The quote was grounded against the whole relay, so the lead's text passed as the owner's. Meanwhile the owner had chosen to hold training until he decided (card Q96, "학습 전 형 확인"). The second alarm also read a report that training's restart (Q99) had already superseded, and one more such finding would have been rung 4, a rollover proposal. Now only quoted text (in a relay or the brief) and the owner's own messages and card choices are his words; a relay's link is looked up in the inbox, and relays from other lanes in the same cwd are not read. The owner's card answers and messages in the lane's thread go to the reviewer dated, and the newest decision wins. A finding is dropped (`OWNER_CHECK_UNGROUNDED`, `OWNER_CHECK_STALE`) when its owner quote is not in the owner's words or its report was already read by an earlier check, and one report moves the context rung once.
- **Relay the owner with the link, and put his words in quotes.** The check can only hold a lane to words it can see, and only the quoted part of a relay is taken as his.

## 17. One piece of work, one thread: reuse the existing thread, merge the rest

One morning a single piece of work had spread over several threads: lanes that only continued earlier work were launched into new threads, and follow-ups got threads of their own instead of going back to the first. The lead folded them into one, and the owner asked for exactly that from then on: when work is the same as, or continues, earlier work, keep it in the existing thread; when a thread's work is done, close it and carry what remains in the thread that goes on. Several threads for one job split the history the owner has to read across places, show more open work than there is, and leave status marks on threads nobody updates any more.

- **Look before you open.** Before you open a thread for a request, check the registry (`dori sync`) and the open threads for one on the same repo, topic or goal. If one carries the same work or the work this continues, use it.
- **Reusing is passing the ref.** `dori launch` never opens a thread: `--thread <adapter>:<id>` puts the lane on the thread you name. A thread that already has messages keeps them (`THREAD_START_SKIP`); only an empty one gets the lane's first message. `dori set-thread <key> <ref>` moves a lane that is already running onto another thread. Several open lanes may share one thread.
- **Merge when a thread's work is done.** Close the finished thread, move what remains to the thread that carries on (repoint its open lanes with `dori set-thread`; `dori resolve` an open question card there and ask it again in the other thread), and post a one-line "(merged)" note in both threads with a link to the other, so the owner can follow the work from either side.
- **A shared thread is done only when its last user is.** Two lanes (dori-dedup-fork and zzangdori-dedup-local) shared one thread; when the first closed, the automatic close ran `hooks.threadDone`, which renamed the thread to done and archived it while the second was still working there, and the lead had to set it back by hand. Closing a lane now looks at what else maps to its thread first. While another open lane (paused counts) or an open question card is on it, `dori close`, the automatic close in `dori watch` and the claim settle post the closing lane's result (`<title>: <text>`; straight to Discord with a token, so even a waiting mark stays, else through `hooks.threadReply`) and leave the thread's status as it is: no `hooks.threadDone`, no rename, no archive (`thread left open: open lane <key> uses it too` or `open card <Qn>` in the receipt). The last lane to close marks the thread done. Never mark a shared thread done by hand early either (`dori thread done` and `dori thread set ... done` do not check for other lanes). When the last lane closed while a card was still open, the thread stays open; once the card is answered and nothing else is on it, close it with `dori thread done`.
- **By hand too, and working beats a card.** The same check later showed two gaps. `dori thread done` typed by the lead archived a thread that still had an open lane and an open card; it and `dori thread set ... done` now make the closing check themselves (`THREAD_LEFT_OPEN`; `--force` to override, with a `THREAD_DONE_FORCED` warning), and a lane's own close tells it which lane is closing (`DORI_CLOSING_LANE`). And an open card turned a lane's working report into ⏸️, so the owner saw "waiting on you" while the lane kept working. ⏸️ means nothing is left on our side: while a lane in the thread is working (or not-done), it shows 🔄 whatever card or wait is open; ⏸️ comes only when no lane there works.
- **Closing the last working lane hands the thread to the owner.** A re-verify closed the only working lane of a thread with an open card: the result was posted and the thread stayed 🔄, although nothing was left on our side. The post leaves the mark alone, and the closing lane still counted as working while it ran. Now a close that leaves the thread open asks for ⏸️ once the lane is recorded closed, when only an open card or a paused lane is left (a paused lane waits on a human, so it does not keep 🔄; `dori resume` turns the thread 🔄 again). Another lane there that is working, not-done or done-claimed (the lead still decides) leaves the mark as it is; ✅ and archive come only when no open lane or card is left. Cards are read again after the cleanup, so one answered meanwhile does not bring ⏸️ back. The `hooks.threadReply` fallback gets `DORI_CLOSING_LANE` too, so `dori thread reply` does not count the closing lane.

## 18. Change the feature that exists; do not add a parallel one

The owner's rule: when something already does a job, change it instead of adding a new feature beside it. A parallel feature doubles what has to be documented, tested and kept in step; the old one keeps its flaw; and the next lead or lane cannot tell which of the two to use. The cheap moment to catch this is the brief, before a lane has built anything.

- Before you write a brief that adds a command, flag, hook, service or rule, look for what already does that job: `SKILL.md`'s command table, `references/scripts.md`, the config keys and the code.
- A brief that adds a feature says which existing feature does the same job and why it cannot be fixed or extended instead. If nothing does that job, the brief says that in one line.
- When the existing feature is wrong or too narrow, the lane changes it in place, with its docs and tests. Keep an old flag or name working only when something still depends on it, and say so in the PR.

## 19. Five stuck signals folded into one ladder (a consolidation, not a new feature)

By 2026-10-12 one lane failing the same metric a third time could raise four lines at once, `SAME_FIX_3`, `RESEARCH_DUE`, `REPEAT_SUSPECT` and `ROLLOVER_DUE`, from four counters (`fixCount`, `metricAttempts`, `repeatsOf`, `inferRepeats`) and three settings that each said "3" in different units. Two of them gave opposite orders at the same moment: research in this session, and move to a new one (a researching lane cannot be moved). The lead's monitors grepped none of the newer names, so most never woke anyone. `intent-check` counted shared words with a Korean goal and scored 0.00 on the very step that served it (22 false `INTENT_DRIFT` lines), while `OWNER_CHECK` already read the words with a model. Each had been added beside an older feature instead of fixing it (#18); the owner asked for the duplicates to be found and fixed in one go (audit 2026-10-12, card Q84).

What changed, all in existing code (`recordFix`/`afterFix`, `repeatTick`, `rolloverDue`, `intent-check`), no new module:

- **One count, one rung, one line.** Per metric, the larger of the tagged and the inferred failed attempts since the last PASS or `--improved`. Rung 2 hypotheses, rung 3 ulw research plus a challenge of the next plan in the same session (no rollover there), rung 4 the lead may roll over (a failure after rung 3, one hypothesis tried 3 times after branching, an owner-check finding still there after a re-read the lead confirmed). One `STUCK` line per rung change; the replaced names stay at its end for one release, so old greps and `rollover-stats` still match.
- **A rung counts what the lane already did.** On 2026-10-12 14:33Z the ladder typed ulw research and a challenge into hr35-e7 for "정지" although the lane had done exactly that the same day (ulw research read 10-11 21:57Z and 10-12 05:56Z, `dori challenge` x2 from 07:56Z, an owner card that followed). The count had jumped from 1 to 3 when a fix to the repeat detection re-read old cycles, and rung 3 looked only at the count. Rung 3 now checks the lane's session log, research folders and challenge records after the repeat that made it due, on that symptom; when both are there it waits for the next attempt, and a failure after them is rung 4. Nothing is typed into a paused lane.
- **The owner check is the intent check.** `dori intent-check` records the direction and runs the owner check on it; a finding is the ladder's context rung, and the re-read goes to the lane only after the lead confirms it (`dori owner-check <key> --reread`).
- **The lead decides rollovers.** `--approved-by lead:<reason and signal>`; the handover tells the owner afterwards and logs the message id.
- **Old keys keep working.** `sameFix.after`, `explore.researchAt`, `explore.hypothesesFrom`, `handover.laneRepeats`, `autoSignals.repeatAfter`, the two `attemptPattern`s and the two reviewer lists move to `stuck.*`, `reviewers.models` and the renamed patterns with one `CONFIG_OLD_KEY` line each.
- **Monitors follow the names.** After a change like this, the lead's watch filters grep `STUCK|OWNER_CHECK` (and keep `SAME_FIX` until the old names go); a new alert name that no monitor greps is an alert nobody reads.

## 20. Owner instructions: common rules go into the fork, local ones stay local

Rules the owner gave piled up in one Dori's local handoff notes, where every other Dori running this skill never saw them, and some host-specific notes leaked into the shared skill. The owner's rule since: each instruction is filed when it arrives, as common (it holds for every Dori) or local (it holds for this Dori or this host only), and the owner is asked when that is unclear.

- **Common** goes into the fork's `SKILL.md` (or the `references/` file it belongs in), generalized: no names, ids, hosts or paths of one setup. It reaches every Dori with the next update, and the local copy is deleted once it is merged.
- **Local** goes into the local agent instructions or handoff file next to that Dori's config: a host's paths, an account, a person's preferences that are not a rule about how a Dori works.
- **Unclear** (a rule that might be a preference of this owner, or a fix for one host's quirk): ask the owner which it is before filing it, with your pick.
- The fork is the original and the local layer keeps configuration only, so a common rule left in local notes is a rule the other Dori break.

## 21. Two Dori on one host: each runs on its own dori.env, whatever the parent environment

After a power outage on 2026-10-13 the second Dori posted in its own channel as the first Dori's bot. At boot the first Dori's `dori-lead.service` (`EnvironmentFile=dori.env`) ran `self-restart.sh`, which exported the file again; its `aoe session start` was the first tmux command after the boot, so it started the tmux server with that environment. tmux keeps the server's start environment as its global environment and hands it to every pane it opens: all sessions, the second Dori's included, had the first Dori's token, inbox, card store and lead. The second Dori's wrapper named its own `dori.env`, but a variable already set won over the file, so the inherited token won.

What holds now:

- **Nothing hands a Dori's variables to aoe or tmux.** `dori-lead.service` has no `EnvironmentFile`; `self-restart.sh` reads its env file without exporting it, runs `aoe` without any `DORI_*`, and drops `DORI_*` from the tmux server's global environment before it starts or restarts a session; every `aoe` and `tmux` the CLI runs gets no `DORI_*` either. A unit that loads `dori.env` for its own process is fine; one that can start the tmux server must not.
- **A Dori's own file beats another Dori's environment.** When the env file names a different bot token than the inherited one, the inherited instance variables are dropped first (`DORI_ENV_FOREIGN` on stderr). A variable set for the same Dori still wins over its file.
- **The directory says which Dori.** List the other Dori under `instances` in `~/.dori/config.json`; a plain `dori` run in its `defaultCwd` uses its config and `dori.env`.
- **A post as the wrong bot fails instead of going out.** Set `discord.botId` in each Dori's config; every Discord write checks the token's bot and refuses with `DISCORD_BOT_MISMATCH`.
- **Starting the other Dori.** The lead starts it through `self-restart.sh` with that Dori's `DORI_CONFIG`, `DORI_ENV_FILE` and `DORI_STATE_DIR` set, not with a bare `aoe session start`, so the tmux global environment is cleaned first and the failure notice goes to that Dori's channel.
- **Check after a reboot:** `tr '\0' '\n' < /proc/<pane pid>/environ | grep ^DORI_` in each Dori's pane shows no other Dori's token or paths, and `tmux show-environment -g | grep ^DORI_` is empty.

## 22. A read mark that returned success can still leave the badge

On 2026-10-14 the owner found two unread messages in one of a Dori's KakaoTalk group rooms. Its watcher had taken both in (13:16 and 13:17 UTC) and marked the room read each time; it marked a room read only when its read cursor moved and printed a line only on failure, and that Dori's session had never received one `KAKAO_MARKREAD_FAIL`. So retrying failures alone would not have cleared the badge. The watcher also lived only in that Dori's local `bin`, where no other Dori could use or fix it.

- **Keep what was marked read apart from what was read.** `kakao-markread.json` sits beside `kakao-cursors.json`; a room whose cursor is ahead is marked again with backoff, and a restart retries what is still pending.
- **Do not trust a success code for something the owner sees.** Every sweep marks again the rooms with recent messages and the rooms `chat list` shows unread.
- **`chat list` is a delta.** agent-messenger's `kakaotalk chat list` returns only chats changed since the account's last sync (it can return `[]`), so "no unread rooms" from it proves nothing; use its counts as a hint only.
- **A helper one Dori needs today goes into the fork anyway** (#20): off by default, with that Dori's ids, names and paths in its `dori.env`. The local copy is deleted once the fork's version runs.

## 23. The owner can call a Dori from any channel

On 2026-10-14 the owner mentioned a Dori's role in a thread under another agent's channel with a request. The listener took only the Dori's own channel, its threads, DMs and the pair channel, and dropped everything else without a line in its log, so the request never reached the inbox and the owner had to ask whether the Dori had seen it. The message carried the Dori's managed role in `mention_roles` (its `mentions` list was empty): typing `@<Dori>` often picks the bot's role, not the bot user.

- **Being called counts wherever it happens.** An owner message anywhere in the guild that mentions the Dori's bot user or one of its roles is a `scope:"mention"` row with a `link`. The roles are read from the bot member at start (`DISCORD_MENTION_IDS`); `discord.mentionRoleIds` adds others. Each Dori has its own bot and role, so a mention of the other Dori stays the other Dori's.
- **Called is not owned.** Answer a mention in the Dori's own channel or work thread with its link (the link takes the eyes off). A channel another agent owns is read, not written; the eyes on the owner's own message are the only mark the Dori leaves there, and only when it was called. The owner's other messages there stay ignored.

## 24. Confirm a read mark on the server, not by its reply

On 2026-10-14 the owner still saw "1" on messages a Dori had read in KakaoTalk, a day after the retry and sweep fix (#55). Its own record said every room was marked. On the server, its read mark in the busiest room had stopped at 04:21 UTC with four messages unread after it: from then on every `mark-read` was acked with status 0 and dropped. Sent alone in a fresh session, NOTIREAD did nothing (five tries). After SYNCMSG of the room from the account's read mark in the same session, it moved the mark (unread 6 to 2, then 4 to 0). Retries and sweeps had repeated the dropped call.

- **Read the result back from the place the other person sees.** A mark counts only when the account's own read mark (CHATONROOM watermarks) has reached the message, read in a separate session; anything short of that is a loud `KAKAO_MARKREAD_FAIL` with the server's mark.
- **A changed protocol call is tried live before it ships.** The packet shape that moved the mark is the one the watcher sends; an untried variant (a one-message sync window) was caught by `dori challenge` before the PR.

## 25. A room the server keeps no read mark in is not marked, and no mark is retried forever

On 2026-10-16 a Dori's account was signed in again and a new room appeared: "카카오계정", where KakaoTalk sends account notices. Every mark there ended in `KAKAO_MARKREAD_FAIL`: the account's read mark stayed at the same id while the newest message moved past it, and the watcher retried with a growing backoff without end, so the monitor kept raising an alarm about a room nobody reads. Its CHATONROOM says why: room type `PlusChat` (a KakaoTalk channel, `writable: false`), and the account's own read mark in it unchanged after the watcher's synced marks. That the server ignores NOTIREAD in every channel room is inferred from this one room.

- **Decide by the room's type, not its id.** Types the server keeps no read mark in (`PlusChat`) are skipped, with one `KAKAO_MARKREAD_SKIP` line; the type comes from `chat list` or the mark's own CHATONROOM. Every other room still counts a mark only when the server's read mark reaches the message (#24).
- **A retry has an end.** Five failed tries at one message give one `KAKAO_MARKREAD_GIVEUP` and stop until a newer message arrives; that point survives a restart. An alarm that repeats with nothing new to say hides the next one that matters.

## 26. A lane that waits all night runs out of turns of its own

omo stops a session that keeps running without anyone typing: after 150 turns it started by itself since the last typed message (`engineTurns.maxPerUserInput` in omo's settings; 12 tool-free ones in a minute is the other limit) it starts none until a message arrives, and shows "Paused: the agent started 150 turns on its own since your last message. Send any message to continue." Goal continuations, monitor notifications and task or eval completions all count. On 10-16 a lane that waited overnight for an 08:06 KST check paused at 03:29 KST (184 of its 193 turns were goal continuations) and its 08:06 monitor wake was refused; the watch said nothing because the screen still showed `◉ watching`. Since then `dori watch` reads the pause from the transcript, prints `LANE_AUTOTURN_PAUSED` and types one message that lifts it, at most `autoturnResumeMax` (3) times a day per session, so omo's guard against an endless self-driven run stays. Raising `engineTurns.maxPerUserInput` would only move the stop; to not need the resume, a lane that waits for a set time arms one monitor gate for that time and ends its turn, instead of re-checking on every goal continuation or wake. To turn the stop off, set `"engineTurns": {"maxPerUserInput": 0}` in `~/.omo/agent/settings.json` (new sessions at once, running ones after `/reload` while idle, which keeps context, background jobs and monitors). The owner chose that on 2026-10-17 (Q197: "한도 없애기(0) — 안 멈춤, 폭주 막는 장치는 우리 감시만 남음"). Then the watch is the runaway guard: `LANE_AUTOTURN_LONG <key> <turns> <last user message time>` every `autoturnLongTurns` (300) turns a session started on its own since its last user message.
