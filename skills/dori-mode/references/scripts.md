# Scripts

`scripts/` is a bun + TypeScript package with one CLI, `dori`. Every external command runs as an argv array; nothing builds a shell string.

## Install and test

```sh
cd skills/dori-mode/scripts
bun install          # dev dependencies only (types, tsc)
bun link             # puts `dori` on your PATH
bun test             # behavior tests with fake herdr/git/gh; nothing real is touched
bunx tsc --noEmit    # typecheck
```

Needs: bun 1.3+, herdr, git, and the GitHub CLI (`gh`) for `merged`/`closed` signals (npm for `published`). The `command`, `file` and `url` signals need nothing extra. The full list of signal kinds is in `sessions.md`. A `command` signal runs with git's `core.quotepath` off (set through `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>`, after any entries the environment already has), so `git status`, `git log --name-only` and `git diff --name-only` print a Korean or other non-ASCII path as it is (`보고서.md`, not `"\353\263\264..."`) and a `stdout~` regex or a `grep` on it can match. The host guard reads `sysctl`, `memory_pressure` and `df` on macOS; on Linux it reads `/proc/loadavg` and `df`, and memory and swap read as unknown.

Tokens and ids come from the environment. Every command first reads `~/.dori/dori.env` (or the file in `DORI_ENV_FILE`, or another Dori's file when the working directory is one of its `instances`), `KEY=VALUE` per line; a variable already set wins, except when the file's token (`DORI_DISCORD_TOKEN`, `DORI_SLACK_TOKEN`, `DORI_TELEGRAM_TOKEN`) is another bot than the inherited one (a Discord token's bot id, a Telegram token's id before the colon, else the whole token; a rotated token of the same bot is the same bot). Then the environment is another Dori's (a tmux server or unit that loaded its `dori.env`), and every inherited `DORI_DISCORD_*`, `DORI_SLACK_*`, `DORI_TELEGRAM_*`, `DORI_LEAD_*` (not `DORI_LEAD_PANE`), `DORI_ASR_*`, `DORI_GOOGLE_*`, `DORI_KAKAO_*` and `DORI_USAGE_*` value is dropped before the file is read, with one `DORI_ENV_FOREIGN dropped <n> ...` line on stderr; `DORI_CONFIG`, `DORI_ENV_FILE`, `DORI_STATE_DIR`, `DORI_LEAD_PANE` and `DORI_DISCORD_SHADOW_INBOX` stay. To run with another bot's token (scratch QA), point `DORI_ENV_FILE` at a file holding that token, not at the real one. Every Discord write (`send discord`, thread starts, renames, posts, cards, the listener, presence) first checks the token's bot (the base64 user id before its first dot): not `discord.botId` when that is set, or the pair Dori's bot (`DORI_DISCORD_PAIR_BOT`), is `DISCORD_BOT_MISMATCH <why>` with exit 2 and nothing sent (`launch` prints it in its `THREAD_START_FAILED` line). `aoe` and `tmux` always run without any `DORI_*` variable, because the tmux server they may start hands its environment to every pane. The Discord commands need `DORI_DISCORD_TOKEN`, `DORI_DISCORD_GUILD`, `DORI_DISCORD_CHANNEL` (the one channel the Dori talks in) and `DORI_DISCORD_OWNER`. Every `dori.env` variable (needed or not, secret or not, what it turns on), which files stay local, and how to add another Dori on the same host: [Settings per Dori](../setups/discord-aoe/README.md#settings-per-dori).

### Nested configuration keys

The fields of `stuck` (defaults in parentheses): `stuck.hypothesesAt` (2: from this many failed attempts on one metric, rung 2: `fix-attempt` needs competing hypotheses), `stuck.researchAt` (3: rung 3, the lane gets ulw research and a challenge of its next plan, in the same session; a failure after it is rung 4), `stuck.fixatedAfter` (3: one hypothesis tried this many times after the lane branched, two or more hypotheses on the metric, is rung 4 at once, marked `fixated`; unbranched it stays rung 3 and only adds `SAME_FIX_3` to the line), `stuck.rereadText` (the text `dori owner-check <key> --reread` types into the lane after you confirmed a finding; `{key}`, `{brief}`, `{finding}` filled in). The fields of `reviewers` are `reviewers.models` (above). The fields of `signals` are `signals.launchLanes`, `signals.numberedAttemptPattern`, `signals.rootCausePattern`.

Old keys (before the stuck ladder, 2026-10-12) still load, each with one `CONFIG_OLD_KEY <old> -> <new>` line on stderr, and are moved to their new home unless the new key is set too: `sameFix.after` -> `stuck.fixatedAfter`, `explore.hypothesesFrom` -> `stuck.hypothesesAt`, `explore.researchAt` -> `stuck.researchAt` (it counted stuck signals, so 2 becomes 3), `signals.attemptPattern` -> `signals.numberedAttemptPattern`, `autoSignals.attemptPattern` -> `autoSignals.inferAttemptPattern`, `explore.challengeModels` -> `reviewers.models`, `autoSignals.ownerCheck.models` -> `reviewers.models` and `autoSignals.ownerCheck.first`. Ignored with a `CONFIG_OLD_KEY ... is no longer read` line: `sameFix.sendToLane`, `sameFix.laneText`, `explore.driftBelow`, `handover.laneRepeats`, `handover.proposalOptions`, `autoSignals.repeatAfter`.

The fields of `explore` (defaults in parentheses): `explore.minHypotheses` (3: competing hypotheses rung 2 asks for), `explore.sendResearchToLane` (true: at rung 3 type `explore.researchText` into the lane, `{question}`, `{n}` (failed attempts), `{metric}`, `{key}` filled in), `explore.researchText` (must start with `ulw research ` and contain `{question}`, else every dori command stops with `CONFIG_INVALID`; see `dori research-hint`), `explore.researchVerifyMin` (5: minutes the lane's session log may take to show that ulw research started before `RESEARCH_NOT_STARTED`), `explore.stagePattern` (regex; a milestone report matching it announces a new stage and `freshness` runs that lane's owner check first), `explore.treeLines` (6: entries per group in a brief's tree section), `explore.modelsCommand` (`omo --list-models`: the ids this host offers, per provider; `[]` turns the check off), `explore.authCommand` (`omo auth check --provider {provider} --json`: logged in when it says `ready` or lists an account that is not blocked), `explore.challengeCommand` (argv template with `{model}`, `{prompt}` and `{system}`, the reviewer instructions that replace the agent's system prompt; default `omo -p --no-session --tools read,grep,find,ls --no-extensions --no-skills --no-context-files --omo-senpi-disabled --system-prompt {system} --model {model} {prompt}`, run in the plan's repository), `explore.challengeMinutes` (10), `explore.branchCommand` (argv template for a `fork-explore` agent branch; default `omo -p --no-session --model {model} {prompt}`), `explore.branchMinutes` (15).

The fields of `autoSignals` (defaults in parentheses), for the inferred count (cycles of "a gate line failed, then a new attempt targets it" on one metric, the inferred half of the stuck count) and `OWNER_CHECK`: `autoSignals.repeatGapMin` (30: attempts on one metric closer than this are one attempt told twice, a commit and its report), `autoSignals.failPattern` (a gate line's failed verdict, matched as written: `FAIL`, `불합격`, `미달`, ✗; a test suite's "13 failed" is not one), `autoSignals.passPattern` (`PASS`, `합격`, ✓: a pass of the metric starts its count again), `autoSignals.verdictPattern` (a prescription's verdict, `REJECTED`, `NOT JUDGEABLE`, `UNCLEAR`, `기각`, `판정 불가`: it fails every known metric its sentence names), `autoSignals.inferAttemptPattern` (a new attempt: 처방, 조정, 수정, 패치, 벌점, retrain, adjust, penalty, a `fix(`/`feat(` commit; 시작 or 반영 alone are not, they also start evals and record decisions), `autoSignals.prescriptionPattern` (words that make a clause an attempt even when it also reads as a diagnosis), `autoSignals.diagnosticPattern` (탐침, 재생, 판독, probe, eval, a `qa(`/`docs(` commit: a clause that only diagnoses is no attempt), `autoSignals.aliases` (empty: names that mean one gate, `{ "교착": ["deadlock", "deadlocks"], "정지": ["무작업", "멈춤", "hold"] }`; the key is the name shown; add them per area, they let an English commit count for a Korean gate), `autoSignals.conditionWords` (soil types, seed, depth, cell in Korean and English: names a report breaks results down by, as in `교착 113(양토 1.0 61 ...)`, never read as a metric), `autoSignals.discriminationPattern` (`dori tree H..`, `가설 판별`, `판별`, discriminat, falsif, ablation: a report or tree entry that tells hypotheses apart; when it makes no new attempt itself, its result changed the next action, so the failed lines it investigated need a new failure before an attempt on them counts; a falsified or supported tree entry counts too. One that states its discrimination result and prescribes again in the same report ("판별 결과: ... 기각" next to "처방안 확정") did not change the action and counts as an attempt like any other. A clause with `안 ` (the word "not") says an attempt is not made; `처방안`/`방안` (a plan) does not), `autoSignals.targetScope` (`sentence`: an attempt targets a metric named in its sentence; `clause` only between commas, quieter and misses more). `autoSignals.ownerCheck` holds the owner check: `autoSignals.ownerCheck.enabled` (true: `freshness` runs it), `autoSignals.ownerCheck.first` (`chatgpt-subscription/gpt-6.1-sol`: tried before the rest of `reviewers.models`; on live Korean lane logs the cheaper `gpt-6-luna` misread a relayed order's scope; the lane's own family is skipped and each id is checked like a `challenge` reviewer), `autoSignals.ownerCheck.command` (`omo -p --no-session --no-tools --no-extensions --no-skills --no-context-files --omo-senpi-disabled --system-prompt {system} --model {model} {prompt}`), `autoSignals.ownerCheck.minutes` (4: time limit per call), `autoSignals.ownerCheck.minIntervalMin` (30: at most one check per lane in this time), `autoSignals.ownerCheck.maxPerDay` (48 per lane: one every 30 minutes all day), `autoSignals.ownerCheck.reports` (6: the newest reports it reads at least), `autoSignals.ownerCheck.maxReports` (20: it reads every report since the last check up to this many, so a violation followed by routine reports is still read; more unchecked than that is said in the line), `autoSignals.ownerCheck.relays` (8 newest owner relays read), `autoSignals.ownerCheck.perTick` (1 check per `freshness` sweep).

The fields of `handover` (defaults in parentheses): `handover.prompt` (`Dori mode`: the first words typed into the new lead session, followed by the note's path), `handover.title` (empty: the old session's title plus `-MMDDhhmm` in UTC), `handover.model` (empty: `defaultModel`), `handover.services` (empty: the `update.services` units; the user units restarted after `leadPane` moves so long-running sweeps read it again; add `dori-session-watch` if it runs), `handover.timers` (regex for the `systemctl --user list-timers` lines the note lists), `handover.verifyMin` (15: minutes for all checks together), `handover.inbox` (empty: `DORI_DISCORD_INBOX`, else `<stateDir>/discord/inbox.jsonl`; where the inbox probe goes), `handover.cwd` (empty: the old lead's aoe path with symlinks resolved; where the new session opens, `~/` allowed), `handover.watchers` (empty: none; watches that are not omo monitors of the lead, such as a host guard or a listener started outside omo: each entry has `handover.watchers.name`, `handover.watchers.check`, an argv run with `{pane}` and `{session}` filled in whose exit 0 means the watch runs, and optional `handover.watchers.arm`, the text that tells the new session how to start it). Example: `"watchers": [{"name": "host guard", "check": ["pgrep", "-f", "dori guard --loop"]}]`. Rollover fields (see `references/rollover.md`): `handover.readyMin` (30: minutes a lane's `dori handover ready` mark counts as a safe point), `handover.laneContextPct`, `handover.laneCompactions`, `handover.laneAgeH` (0, 0, 0: the context use in percent from the status line, the compactions in the session log, and the hours since the session began at which `freshness` says a lane's rollover is due, once per pane; The fields of `directives`: `directives.common` (the fork layer, default `skills/dori-mode/references/directives.json` of this checkout; empty turns it off) and `directives.local` (the host's own ledger file, with the directives only this host and its repos have and links to the owner's messages; a local entry with the id of a fork entry overrides its fields, e.g. its source link; empty: none). Both are JSON: `entries` (each `id`, `name`, `by` (`owner`: he stated the directive and `words` is that sentence, or it is a block of his words; `lead`: a rule the lead set, `words` empty and `trigger` = what he said that led to it), `basis` (one line: why it is his directive or the lead's rule, from the context of his message), `words`, `original` (his whole message as he sent it, on record; several joined with ` / `), `fixes` (`[as received, corrected]` pairs for a typo or speech-to-text error in `original`), `trigger`, `rule`, `date`, `source`, `scope` {`all`, `ui`, `kinds`, `repos`, `keywords`}, `mode` `inject` | `require` | `lead`, with `block` (`eight-steps`, `ui-steps`), `require` (regexes the brief must all match) or `check` (`thread`, `ledger`), and `retired`), `kinds` (kind name -> regex), `minHits` (hits a brief needs to count as that kind of work, 3), `labels` (words that name a scope, left out like directive names), `standing` (regex for an owner message that sets a standing directive), `reviewed` (owner message ids judged not a directive) and `fillers` (words and phrases with no directive in them, such as 알겠어 or 아 그리고; the host layer adds the owner's name for its Dori; both layers' lists count). `dori directives check` validates them; `words` with an ellipsis (`…`, `...`) is refused: his sentences go in whole, and only sentences unrelated to the directive may be left out, never a part of one. An entry with `original` must have `words` that is `original` (after its `fixes`) with words deleted and nothing else: every word kept as he wrote it and in his order, and each deleted run either fillers (and ellipses) only or whole sentences or clauses (from and to `.`, `!`, `?`, `,`, an ellipsis, a line break, a ` / ` between messages or an end of the message); a reworded, reordered, added or half-cut word fails the check (`words is not his original with words deleted`).

A new config key: run `dori update` on every Dori on the host (or read its CONFIG_NEW_KEY lines) and set the key in each config.json that needs it.

### Backend `aoe`

With `"backend": "aoe"` lanes run as [agent-of-empires](https://github.com/njbrake/agent-of-empires) sessions instead of herdr panes. Needs `aoe` and `tmux`. What differs:

- A pane id is the session's tmux name, `aoe_<title>_<first 8 of the aoe id>`; `leadPane` and `ignorePanes` take these names. Panes are the live sessions in `aoe list` that have a tmux session; `aoe_term_*` terminals and stopped sessions are not panes. `workspace_id` is the aoe profile, so leave `workspaces` empty or list profiles.
- `launch` runs `aoe add <cwd> -t <key> --tool <agentCommand[0]> -l --extra-args "--model <model>"`, waits up to 3 minutes for the agent's `❯` prompt, then types the lane prompt. `agentCommand`'s other arguments and `laneWorkspace` are not used. aoe refuses a title+path pair that already exists, even in its trash.
- Text goes in through `dori type` (it runs `tmux send-keys -t =<name>: -l -- <text>` and a separate `Enter`, each an argv array, then checks the input box); lanes report to the lead the same way, never with a raw `send-keys`. Only the agent's input box (the lines between the last two `─` borders, cut where the borders end, so senpi's FILES/TOOLS/MEMORY side panel on the same rows is not read) counts as unsent text, so the same text echoed in the transcript does not trigger extra Enters, while a paste folded into `[paste #1 +13 lines]` or a tall box whose `❯` line scrolled away does.
- `close` runs `aoe session stop <id>` and `aoe rm <id>`: the session goes to the aoe trash and can be restored. It is never purged.
- The session id comes from the agent's `--session-id` argument (aoe passes one to omo), found under the tmux pane's pid; the environment and session-file rules follow as with herdr.
- `claim-done` without a key finds the lane by the tmux session it runs in. `guard` and `can-launch` count aoe sessions as panes.
- `watch` also reads `aoe ps --json` and the lane screens and prints `LANE_BLOCKED <key> <state> <pane>` for a working lane whose agent waits for a human (see `dori watch` below).
- `launch` reports `STARTUP_ERROR` with the agent's own message as soon as a startup error or `Pane is dead` shows while it waits for the prompt.
- `launchEnv`: aoe does not hand its own environment to the session it opens; tmux copies only the variables its `update-environment` option names from the client (`aoe add`, `aoe session restart`) into a new session. So with a non-empty `launchEnv`, `launch` and lane `handover` first append each name to the global `update-environment` (once), then run `aoe add` with the values set, or, for a `--use-gpu` lane, with those names removed, and read the new session's environment back (`tmux show-environment`). A session that lacks a value gets no lane prompt (`STARTUP_ERROR ... launchEnv not in the session`), and a handover's new session is closed while the old one stays the lane (`HANDOVER_FAIL ... lacks launchEnv`). The running session of an adopted pane keeps the environment it started with. A restart makes a new tmux session from the restarting client's environment, which is why `self-restart.sh` asks `dori launch-env` first. `--use-gpu` drops every `launchEnv` variable, so keep `launchEnv` to what keeps lanes off the GPU. Limits: omo's task subagents run inside senpi's RPC host, whose environment senpi builds from a fixed allowlist (`PATH`, `HOME`, `LC_*`, `XDG_*`, `SENPI_*`/`OMO_*`/`PI_*`, proxies, API keys; senpi 2026.10.13 `host-daemon-env`), so they and the commands they run do not get `launchEnv` and still see the GPU (measured 2026-10-14: the lane's own bash `False`, its quick subagent's bash `True`); the lane's own tools and eval kernels do get it. aoe's own auto-resume after a reboot starts sessions from aoe's environment, not through dori (a lane gets `launchEnv` back at its next handover or `self-restart.sh`); emptying `launchEnv` later leaves its names in tmux `update-environment` until the tmux server restarts or `tmux set-option -gu update-environment` restores tmux's default list. Sessions start as before meanwhile, since dori and `self-restart.sh` then run aoe without those variables.

Hooks are argv templates for your messenger CLI. `{thread}`, `{text}` and `{key}` are filled into each argument separately, so the text stays one argument whatever it contains.

## Commands

### `dori update [--pull] [--dry-run]`

Applies the clone's current HEAD. `--pull` first runs `git -C <update.repo> pull --ff-only`. The first run saves HEAD and sorted known dotted config keys to `<stateDir>/update.json`, prints and logs `UPDATED first-run`, and restarts and announces nothing. If HEAD equals the saved `applied` SHA, it prints `UP_TO_DATE` without writing a watch-log line.

On a new HEAD it diffs the saved SHA against HEAD. Every service with a matching `update.services.paths` prefix is restarted once. It notes the service log's byte size before restarting and waits only for a new complete line matching `ready`, not an old ready line. With an empty `ready`, it checks user-unit activity instead. Each attempt prints and logs `RESTARTED <unit> <sha7>` or `RESTART_FAIL <unit> <reason>`; it attempts every affected service and then records the HEAD even when readiness failed. `UPDATED <old7>..<new7> changed=<n> restarted=<units>` lists successful restarts.

Keys this code knows but the saved code did not, and which are not set in the raw config file, print and log `CONFIG_NEW_KEY <key> unset in <config path> (default used)`. The known keys are saved for the next run. A restart failure sends `[ALERT] dori update: RESTART_FAIL ...` to `update.alertPane`, including new-key notices; without a restart failure the key notices do not trigger an alert. Git failures (including rejected pulls) print and log `UPDATE_FAIL` with stderr and alert the same pane, preserving the previously applied SHA.

After restarts, one `[UPDATE]` summary goes to `leadPane` (`DORI_LEAD_PANE` overrides it). It contains merged PR titles from old..new (or commit subjects if there are no merges), changed `references/`, `SKILL.md`, and `setups/**/README.md` paths under this skill, new config keys, restart results, and `update.announce`. Delivery prints and logs `ANNOUNCED <pane>` only after the pane-send helper saw the text submitted (see `dori type`), else `ANNOUNCE_FAIL <pane> <reason>` next to the helper's `NOT_SUBMITTED` line. A missing lead pane logs `ANNOUNCE_FAIL` without sending anything. Alerts and announcements use the same argv pane-send helper as lanes.

`--dry-run` prints planned local changes and restarts with a `DRY_RUN` prefix; it does not pull, restart, send, or write state/watch logs. A failed update/restart exits 1. The generic systemd path unit can run `dori update` after a pull; see the Discord + aoe setup.

### `dori notify-change --summary TEXT [--file PATH ...]`

Sends one `[UPDATE]` message containing the supplied summary and changed guidance paths, followed by `update.announce`, to `leadPane`. Use it when a Dori's own memory or AGENTS guidance changes outside the script clone. Prints and logs `ANNOUNCED <pane>` or `ANNOUNCE_FAIL <pane> <reason>`; failed delivery exits 1.

### `dori handover [--note FILE] [--title T] [--model M] [--keep-old] [--no-monitors] [--minutes N] [--dry-run]`

Moves the lead to a new agent session when its conversation got long (backend `aoe`). In order:

1. **Note.** Writes `<stateDir>/handover/<stamp>.md` (and `.json`): the open lanes with status, pane, thread and last report; every monitor the old session still runs, persistent or not, read from omo's manifest `<sessionsDir>/--<cwd>--/extensions/terminal/<session id>.json` (a monitor whose recorded process is gone is left out; the new session re-arms each one as persistent); the configured `handover.watchers`; open question cards; the old session's unfinished todos and goal; timers matching `handover.timers`; the owner's messages of the last 24 hours in the inbox (at most 8, rows whose author is `DORI_DISCORD_OWNER` or `DORI_KAKAO_OWNER_ID`); the path of the old session's log; and the file given with `--note`, the old lead's summary under the headings `dori handover --template` prints (Owner's words and constraints, quoted exactly; Decisions and why; Promised follow-ups; In progress; Next step; a `--note` without them is refused). It refuses (`HANDOVER_REFUSED`, exit 2, nothing changed) when `leadPane` has no live aoe session, when `DORI_LEAD_PANE` is set in the environment (it overrides the config file, so lanes would keep reporting to the old pane; drop it, also from a wrapper script that exports it), when another handover holds `<stateDir>/handover/lock` and its process is alive, when a `handover.watchers` check fails for the old lead (`configured watchers not running`; `--no-monitors` does not skip it), or when neither a running monitor nor a configured watcher was found (the line names the manifest it read, or says the omo session could not be told; `--no-monitors` hands over without them). The session id comes from omo's `--session-id <id>` or `--session <session file>` argument (the uuid at the end of the file name), else a child's `PI_SESSION_ID`, else the session file made at start. When the old lead's path is a symlink it prints `HANDOVER_CWD_SYMLINK <path>, a symlink to <real path>; the new session opens in <cwd>`.
2. **New session.** Opens `aoe add <cwd> -t <title>` (`handover.cwd`, else the old lead's path with symlinks resolved), waits for the prompt, tells the old lead to stay quiet, and types `handover.prompt` plus "read the handover note at <path>". The note tells the new session to re-arm every monitor, to start each watcher whose `arm` says how, to answer `HANDOVER_PROBE <id>` lines with `dori handover ack <id>`, and to answer `HANDOVER_UNDERSTAND` and `HANDOVER_SUPPLEMENT` lines (step 4).
3. **Repoint.** `leadPane` in the config file (and `update.alertPane` if it named the old lead), `DORI_LEAD_TMUX` and `DORI_LEAD_AOE_ID` in `dori.env`, added when the file lacks them (each file backed up as `.bak-handover-<stamp>`), every open lane's brief footer (the old pane name replaced) plus a `[LEAD]` message with the new report command, and open question cards whose `tmux` was the old lead. Then it restarts `handover.services`, because `dori watch`, `freshness` and `dead-panes` read `leadPane` once at start. Lines: `HANDOVER_CONFIG`, `HANDOVER_ENV`, `HANDOVER_LANE <key> brief=rewritten|unchanged|missing told=yes|no`, `HANDOVER_CARDS`, `HANDOVER_RESTARTED`.
4. **Checks**, within `--minutes` (default `handover.verifyMin`): every monitor of the old session runs in the new one (same command and filter, or same path; the description only for a monitor with neither; persistent, not suspended, its process alive; the new session's manifest is read under the new cwd), `HANDOVER_MONITORS_OK`; every `handover.watchers` check exits 0 with the new pane and session filled in, `HANDOVER_WATCHERS_OK`; a freshly loaded config routes reports to the new pane; then a `[REPORT] handover-probe ... HANDOVER_PROBE <id>` line typed into the pane the config names, and a `{"kind":"handover-probe"}` line appended to the inbox file, are both acked by `dori handover ack <id> --state <stateDir>` run from the new pane; then `[LEAD] HANDOVER_UNDERSTAND <id>` asks the new lead to write what it understood to `<stamp>.understood.md` under Goal, Owner's words, Open lanes, Open work, Open cards, Timers, Promised follow-ups, Decisions, Next step and Questions, and ack. It is checked against the handover's own records (every open lane key under Open lanes, every open card id under Open cards, every timer's unit under Timers, each todo under Open work, the old session's goal, each of the owner's recent messages quoted) and against the summary (its quoted owner's words, decisions and promised follow-ups). What it left out goes back to it in `<stamp>.supplement-<n>.md` with the old log lines behind each item (`HANDOVER_SUPPLEMENT lead round n/m`), up to `handover.supplementRounds` rounds; still missing after them, or no ack, fails the check like any other (`HANDOVER_SUPPLEMENT_OK`, `HANDOVER_UNDERSTOOD` when it passes; its questions print as `HANDOVER_QUESTIONS lead`). The rounds and items go to the rollover log (the probe line carries `--state`, so a Dori whose `dori` wrapper sets another state dir acks into the right one). An ack from any other pane (the old lead also sees the inbox) does not count.
5. **Freeze.** Only when every check passed: the old lead's agent and every process under it get SIGSTOP (`HANDOVER_OLD_FROZEN <pane> agent <pid>: N processes stopped (...)`), so it uses no tokens and does nothing; its pane and its conversation log (JSONL) stay, a record goes to `<stateDir>/handover/frozen/<pane>.json`, then `HANDOVER_DONE` and the new lead gets `[LEAD] HANDOVER_COMMITTED`. It is closed `handover.frozenCloseH` hours later (below); with `--keep-old` it stays frozen until closed by hand. Before the commit the old lead is only told to stay quiet (the quiet mark), and a rolled-back move stops nothing. When nothing can be stopped (no agent under the pane, the signal refused) it prints `HANDOVER_FREEZE_FAIL`, resumes what it stopped and closes the old session as before (`HANDOVER_CLOSED`; with `--keep-old` it stays open and is told it is no longer the lead). A failed check prints `HANDOVER_VERIFY_FAIL <reasons>`, runs step 3 the other way round (config, env, lanes, cards back to the old lead, services restarted), tells the old lead it stays the lead, leaves the new session open to look at (`HANDOVER_ROLLED_BACK`) and exits 3.

Every line also goes to `watchLog` with source `handover`, and the outcome to `<stateDir>/handover/<stamp>.result.json`. Run from inside the lead's own tmux session, it re-runs itself as a `systemd-run --user` unit (`HANDOVER_DETACHED unit=... log=<stateDir>/handover/run.log`), because freezing the old lead stops every process under its agent (and closing it ends every process in it); with `--keep-old` too. `--dry-run` writes the note and prints the plan (`HANDOVER_DRY_RUN`) without opening or moving anything.

`dori handover frozen` lists the frozen old leads (`FROZEN <pane> since ... (agent, processes, close time, the lead that replaced it, its log)`). `dori handover thaw <pane>` resumes one frozen by mistake, children first and the agent last, and forgets its record (`HANDOVER_OLD_THAWED <pane>: n/m processes resumed`); it is still not the lead (the lead's pane is `leadPane`), so tell it what to do. `dori handover close-frozen [<pane>]` closes that one, or without a pane every one whose close time passed: resumed first (a stopped process does not act on the hangup), then `aoe session stop` and `aoe rm` (`HANDOVER_OLD_CLOSED ...; its log stays at <path>`); its log is never deleted. `dori freshness` runs the same close every tick, so a frozen lead is closed `handover.frozenCloseH` hours after its handover. `dori sync` and `dori dead-panes` skip frozen panes.

`dori handover --template` prints the headings of the old lead's summary. `dori handover ack <id> [--state DIR]` records the pane it runs in for that probe, restatement or supplement id under `<DIR or stateDir>/handover/acks/` (`HANDOVER_ACK <id> pane=<pane>`).

### `dori launch <key> --title T --brief FILE --done "..." [--thread REF] [--model M] [--cwd DIR] [--tag T ...] [--done-weak-ok] [--goal G] [--challenge-before STEP ...] [--use-gpu] [--ui] [--dry-run]`
Opens a lane: appends the footer to the brief, opens a tab, starts the agent, and checks the pane for startup errors after 20 seconds. Exit 3 on `STARTUP_ERROR`. With backend `aoe` the session starts with `launchEnv`; `--use-gpu` (a lane that needs the GPU, e.g. a training run) starts it without, and the lane keeps `useGpu: true` in the registry so its handovers and restarts do the same.

With `--thread discord:<id>` and `DORI_DISCORD_TOKEN` set, it then writes the lane's first message in that thread, so a thread opened for the lane never sits empty: `discord.laneStartText` with the title, the `--goal`, the first lines of the brief, the Done line, the key and the pane. It prints `THREAD_START_POSTED <ref> message=<id>`; a thread that already has a message is left as it is (`THREAD_START_SKIP`); without a token it prints `THREAD_START_NO_TOKEN` and a Discord error `THREAD_START_FAILED`, and the lane runs either way. `launch` never opens a thread itself: for work that is the same as or continues an earlier lane, pass the ref of the thread that work already has, so it stays in one place; several open lanes may share a thread, and a close leaves a shared `discord:` thread open while another open lane uses it.

Before the footer it adds a `## Past signals (written by dori launch)` section when earlier lanes in the same area have a record: lanes with the same `--cwd` (unless it is `defaultCwd`) or a shared tag. The key's first word is always a tag (`rl-e8` shares `rl` with `rl-e7`); `--tag` adds more and is stored in the lane. Up to `signals.launchLanes` lanes, newest first, one line each (numbered attempts, root-cause switch, fixes, rejected claims, re-sends and nudges) plus their warnings, so the new lane does not repeat a fix that already failed.

After Past signals comes `## Hypothesis tree (written by dori launch)` when the area's tree (the lane's `--cwd` unless it is `defaultCwd`, else its first tag, plus its other tags) has open entries: a few lines each of open, supported and falsified hypotheses, untried directions, research due, findings and recent attempts (see `dori tree`).

The footer tells the lane to report with `["dori","type","<leadPane>","--text","<report line>"]` (an argv array; `NOT_SUBMITTED` means send it once more), for herdr and aoe alike. `--goal "<the owner's words>"` is stored in the lane as `goal` and written into the footer with the instruction to run `dori intent-check` at each stage change; without it `launch` prints `LAUNCH_NO_GOAL <key>: ...` and goes on. `--challenge-before "<step>"` (repeatable) is stored as `challengeBefore` and tells the lane to put that step's plan through `dori challenge` first; `claim-done` refuses (`CHALLENGE_MISSING`, exit 5) until a challenge is on record. Require it for steps that cost hours or a GPU queue, change the approach, or follow a falsified hypothesis. `--dry-run` prints the brief exactly as the lane would read it (your text, Past signals, Hypothesis tree, footer) followed by `DRY_RUN <key>: ...`; it writes nothing, registers nothing and opens nothing.

When every `Done =` signal only checks that files exist or contain text (a `file` signal, or a command that is only `grep`/`test`/`cat`/`ls`/`wc`/`jq`..., directly, via `sh -c` or in a readable shell script), it first prints `LAUNCH_DONE_WEAK <key>: ...` asking for a signal that measures behavior, then launches anyway. `--done-weak-ok` silences it. A script it cannot read is not called weak.

Every launch checks the brief for the eight step headings of the template in `references/sessions.md` (`1. 조사:` ... `8. 보고:`): with none it inserts the whole block from that file, byte for byte, after the paragraph of the four fields ([목표] ... [넘으면 안 되는 선]), or after the `ulw` line (else at the top) when there are no fields, and prints `LAUNCH_STEPS_ADDED <key>: ...` and a watch-log line; with all eight it changes nothing; with some of them it adds nothing and prints `LAUNCH_STEPS_PARTIAL <key>: ... (missing N, ...)` and a watch-log line. `--dry-run` prints the same line. With `--ui` the brief reads `ulw`, the UI steps, the four fields, the eight steps.

`--ui` is for UI work (a screen, a design, a dashboard, a page, an app's UI): it puts the owner's seven UI steps, the block between the markers in `references/ui-work.md`, at the top of the brief, right after its first line when that line starts with `ulw`, else above everything; a brief that already has them gets no second copy. Without `--ui`, a brief that reads like UI work (two UI words such as UI, UX, dashboard, frontend, 대시보드, 프론트엔드, 디자인, 웹페이지, 화면, at least one of them not 화면; a word inside a hyphenated name such as a lane key, a quoted word and a directive's name do not count) prints `LAUNCH_UI_HINT <key>: ...` and a watch-log line; with the directive ledger on (directive `ui-steps`) the steps go in anyway and the lane launches with them (`--waive ui-steps "<reason>"` keeps them out of a brief that is not UI work), without a ledger it launches as is.

`REF` is `<adapter>:<id>`, e.g. `discord:<thread id>` (digits only) or `telegram:<chat>/<topic>`. An empty id (`discord:`), a bare `--thread`, a ref without an adapter, or whitespace in the id is refused before anything opens: exit 1 with a one-line reason, and no lane is registered. Leaving `--thread` out is fine; the lane is registered with thread `none`. `adopt` checks `--thread` the same way.

**The directive ledger.** Every launch also reads the directive ledger (`directives.common` and `directives.local`). It decides what the brief is about from the lead's text with quoted words, directive names and scope labels left out (a brief that only names "UI 7단계" is not UI work): UI work (`--ui`, or two UI words), a kind of work (`minHits` hits of that kind's regex), the repo of `--cwd` (its `origin` remote's name, else the directory's name) and keywords. An `inject` directive in scope that the brief lacks goes in under one heading, `## 형 지침 (지침 장부에서 dori launch가 넣음)`, at the end of the lead's text: an owner directive with words as its `prompt` under the tag `[형 지침 <id>, <date>]` (the lead's rewrite of his words as the standing rule a lane follows from now on, like a general prompt: imperative or declarative, no question; a task he asked to be done once in that message, a description of that situation and asides are left out; every condition, target and strength word (반드시 꼭, 앞으로 항상, 절대로) kept, nothing added; his `words` and `original` stay in the ledger as the record; no summary, no rule, no context; an owner decision on record without his sentence is tagged `[형 결정 <id>, <date>, 원문 없음: 리드 기록]` with the rule), a lead rule as `[리드 규칙 <id>]` and its rule; the trigger and the basis stay in the ledger and `dori directives`, and launch prints `LAUNCH_DIRECTIVE_ADDED <key>: <id> (<why>), ...` and a watch-log line; the `eight-steps` and `ui-steps` blocks are placed as above (a brief that reads like UI work without `--ui` gets the UI steps too, with `LAUNCH_UI_HINT`). A `require` directive in scope the brief does not meet (the four fields) stops the launch before anything is written or opened: `LAUNCH_DIRECTIVE_MISSING <key> <id>: ...` and a watch-log line, exit 4 (`--dry-run` prints the brief and exits 4 too). `--waive <id> "<reason>"` (repeatable) leaves that directive out: `LAUNCH_DIRECTIVE_WAIVED <key> <id>: ...` in the watch log, the waiver in the lane's `directives.waived` in the registry, and `discord.waiveText` to the owner (`DIRECTIVE_WAIVE_SENT`, or `DIRECTIVE_WAIVE_NOT_SENT` and why). A waiver of an id not in the ledger is refused, and so is a ledger that does not validate. The lane records `directives.applied` (the ids in scope) and `ui`.

### `dori directives [table|prompts|check [--static]|apply <key> [--dry-run]]`
`table` (the default) prints the ledger as one markdown table for the owner: id, name, the owner's words, the prompt briefs get, date, source, scope, how it is enforced, layer, retired. `prompts` prints only his words next to the prompt (`| id | 형 원문 | 지침문 |`), for him to read. `check` validates both layers (ids, dates, modes, kinds, regexes; every owner entry with words has a `prompt`, and no prompt asks: a `?` or a question ending such as 않아, 할까, 하니 is `prompt is a question`), then has a reviewer of another family than `defaultModel` (`reviewers.models`, `autoSignals.ownerCheck.first` first, the `ownerCheck` command) compare each new or changed prompt with his words (leaving out a one-time task or the situation of that message is not a loss; a dropped or added condition, target or strength is): `DIRECTIVES_MEANING_OK <id>`, or `DIRECTIVES_BAD directive <id>: prompt does not mean what his words mean: MISSING|ADDED|STRENGTH|QUESTION: ...` for a dropped condition, an added requirement or a changed strength (반드시 to 가능하면), or `DIRECTIVES_MEANING_FAILED <id>` when no reviewer answered; any of those exits 1. A SAME verdict is kept in `<stateDir>/directives/meaning.json` per (id, original, words, prompt), so only a new or edited prompt is read again. `--static` skips the reviewer (launch runs the static part only). All good: `DIRECTIVES_OK <n> directives (<fork>, <local>) in <files>`.

`apply <key>` is for a lane launched before a directive was in the ledger (or before it was in scope). It judges the lane's scope again as owner-check does (its brief, the repo of its cwd, `ui`) and takes every directive in scope its brief lacks, in launch's format: `[형 지침 <id>, <date>]` and the prompt, `[리드 규칙 <id>]` and the rule, a built-in block (the eight steps, the UI steps) as its text. They go to the lane's pane as one `[LEAD] 지침 보충: ...` message (the lane keeps its work and follows them from now on); once it is SUBMITTED, the same texts go into the brief under `## 추가 지침(리드, launch 뒤)`, after the lead's text and before what launch appended (past signals, tree, footer; nothing above is changed), the ids into the lane's `directives.applied`, and `DIRECTIVES_APPLIED <key>: <ids> ...` into the watch log. Nothing missing: `DIRECTIVES_APPLY_NONE <key>` and no change, so a second run is a no-op. Not submitted: `DIRECTIVES_APPLY_NOT_SENT <key> <pane>`, exit 1, brief unchanged. A `require` directive (the four fields) is not a text to send: `DIRECTIVES_APPLY_REQUIRE <key> <id>` asks the lead to write it in. `--dry-run` prints what would be sent and changes nothing. The words in that section never change the lane's scope (launch's and owner-check's scope text leaves it out, like `## 형 지침`). Either section starts only at its heading on a line of its own: a brief that quotes the heading inside a field (a lane about this command) keeps the rest of its fields.

### `dori directive-audit [--since 24h|Nd|ISO] [--dry-run]`
The daily check that nothing slipped past the ledger (the `dori-scorecard` timer runs it after the scorecard, `--since 24h`). For each lane opened since then: every directive in scope that is not in its brief (`DIRECTIVE_GAP <key> <id>: ...`; waivers on record are left out) and a lead directive the lead did not follow (`DIRECTIVE_LEAD <key> lane-thread: ...` for a lane launched without `--thread`). Then the owner's messages since then (the inbox, author `DORI_DISCORD_OWNER`) that match the ledger's `standing` regex and that no entry cites by message id and `reviewed` does not list: `DIRECTIVE_UNLEDGERED <link> "<text>": ...`, a directive the lead did not put in the ledger the same day. Gaps go to the watch log, one line each, and one `[DIRECTIVE_AUDIT] <n> directive gaps ...` summary is typed to `leadPane` (`DIRECTIVE_AUDIT_SENT`, or `DIRECTIVE_AUDIT_NOT_SENT`). No gap: one `DIRECTIVE_AUDIT_OK ...` line on stdout and nothing else. `--dry-run` prints the lines and writes and sends nothing.

### `dori adopt <key> --pane ID --title T --brief FILE --done "..." [--thread REF] [--tag T ...] [--goal G] [--challenge-before STEP ...] [--use-gpu]`
Registers a lane that is already running; `--goal`, `--challenge-before` and `--use-gpu` are stored as for `launch`. The running session keeps its environment: with backend `aoe` and a `launchEnv` it prints `ADOPT_ENV <key>: ...` saying the lane's setting applies from its next handover or restart.

### `dori set-gpu <key> on|off`
`on`: the lane's next session (handover, `self-restart.sh`) starts without `launchEnv`; `off`: with it. The running session keeps its environment. Prints `GPU_SET <key> <old> -> <new>: ...`. Mark a lane that trains on the GPU `on` before its next handover or restart.

### `dori launch-env <tmux-session>`
Prints, one per line, the `env(1)` arguments a restart of that session needs to start the way dori opens it: `NAME=VALUE` for an open lane, `--unset=NAME` for a `--use-gpu` lane, a closed lane, the lead or any other session (unsets first, as `env` reads options only before the first assignment). It appends the names to tmux `update-environment` first. Nothing without `launchEnv`. `setups/discord-aoe/self-restart.sh` runs `aoe session start|restart` under these arguments.

### `dori set-thread <key> <adapter>:<id>`
Points an open lane at another work thread, for example one created after the lane was launched. The ref is checked as for `launch`; a bad one exits 1 and leaves the lane unchanged. Prints `THREAD_SET <key> <old> -> <new>`.

### `dori done-set <key> --done "<signals>" --reason "<why>"`
Changes an open lane's `Done =` line when its plan changed after launch and the old signals can no longer read back live, though the work is done (an owner's later instruction replaced a service with a dashboard tab and a timer, say). The new line is checked as for `launch` (an unreadable signal, no `--reason`, or the line the lane already has exits 1 and changes nothing), then every new signal is read once and printed as `SIGNAL OK|NOT <signal> -> <detail>`, ending in `DONE_SET <key> live <k>/<n>: ...`. The change is kept either way: the lane's `doneChanges` in the registry holds the earlier line, the new one, the reason, the time and whether it read back live; the watch log gets `done-set DONE_SET <key> live k/n; reason: ...; was: ...; now: ...`; the brief's `- Done =` footer line is replaced, with a `- Done changed ... Earlier: Done = <old>` line under it (`BRIEF_UPDATED`, or `DONE_SET_BRIEF_WARN` when the brief cannot be written); and the lane is told in its pane (`LANE_TOLD`, or `DONE_SET_NOT_SENT`). `dori signals` and later lanes' Past signals show the change. Nothing is skipped: `dori close` and the watcher read the new line, and every signal still has to read back live.

### `dori sync [--write]`
Prints `key | thread | pane | session | status` for every open lane and every unregistered agent pane, followed by a `SIGNALS <key> [<outcome>] ...` line for each open lane that has a record (see `dori signals`) and drift. Read-only unless `--write`, which stores session ids.

### `dori claim-done [<key>] --evidence TEXT` / `dori object-done <key> --reason TEXT ...`
The two halves of the done flow. Both message the lane's pane and check that Enter registered. A claim on a paused lane is recorded and printed as `LANE_DONE_CLAIMED_PAUSED <key> <pane> <evidence>` (and once by `dori watch`), but it never closes the lane on a timer; the lead closes it or objects. A lane launched with `--challenge-before` that has no `dori challenge` on record gets `CHALLENGE_MISSING <key>: ...` and exit 5 instead of a claim.

### `dori pause <key> <reason>` / `dori resume <key>`
Parks a working or not-done lane that waits on a human, for example on the owner's approval. The status becomes `paused`, the previous one is kept in `pausedFrom`, and `PAUSED: <reason>` goes into the lane's history. While paused, `dori freshness` neither nudges nor posts for it, `dori watch` reports no `LANE_BLOCKED` and does not auto-close it, and `dori dead-panes` skips its pane. `dori resume` restores the previous status with a `RESUMED` history entry and restarts the silence clock, so the first nudge comes a full `nudgeAfterMin` later; when a claim arrived during the pause it prints a `NOTE` saying so. Pausing a lane that is not working or not-done, or resuming one that is not paused, exits 1.

### `dori fix-attempt <key> --metric M --hypothesis H [--hypotheses H1 --test T1 ...] [--improved] [--no-hypotheses REASON]`
Records a fix you asked the lane for, in the lane's `fixes`, and takes one step of the stuck ladder. Prints `FIX_RECORDED <key> attempt=<n> on-metric=<m> stuck=<s> (tagged t, inferred i)` (n: this metric and hypothesis; m: this metric; s: the stuck count) and the `STUCK` line when the metric's rung went up. `dori freshness` records the lane's own reports tagged `(fix: <metric> / <hypothesis>)` the same way; a fix you recorded that the lane then reports counts once. Before it records, it prints what the area already tried on that metric: `PRIOR_FIX <lane> "<metric>": <hypothesis> xN, ...` per lane (this lane, its cwd, its tags), or `PRIOR_FIX none on "<metric>" in this area`, under the metric's name in `autoSignals.aliases` as the stuck count uses it (`--metric deadlocks` lists the fixes recorded as `교착`; `HYPOTHESES_REQUIRED`, `STUCK_BRANCH` and `HYPOTHESES_OVERRIDE` use that name too), and `PRIOR_ATTEMPTS <key> numbered attempts 1-N, root-cause switch: <time|none>` when the lane's reports number their attempts. See `sessions.md`, "Repeated fixes".


The stuck ladder: failed attempts on one metric are counted whatever the hypothesis (a fix you asked for that the lane then reports counts once), in the lane's current session, since the last one recorded with `--improved` (the previous fix moved the metric) and since the last PASS of the metric its reports showed; the inferred count (`dori repeat-check`, under the same `autoSignals.aliases` name) counts too, and the larger one is the stuck count. Each rung change prints and logs one line, `STUCK <key> "<metric>" rung N (tagged t, inferred i, hypotheses h[, fixated][, inferred only]) -> <what to do> [<old names>]` (source `stuck`), once per rung; a count that went down (PASS, `--improved`) lowers the mark silently, so the next stuck run alerts again. The old names at the end (`HYPOTHESES_REQUIRED`, `RESEARCH_DUE`, `ROLLOVER_DUE`, `SAME_FIX_3` when fixated, `REPEAT_SUSPECT` when the inferred count reached `stuck.researchAt`) stay for one release so monitors that grep them still match.

- Rung 2, from `stuck.hypothesesAt` (2): `fix-attempt` refuses unless you give at least `explore.minHypotheses` (3) distinct competing hypotheses with `--hypotheses`, each followed by one cheap discriminating experiment with `--test`, in the same order. A refusal prints `HYPOTHESES_REQUIRED <key> attempt N on "<metric>" ...` with the command to run instead, logs the same line, exits 5 and records nothing. An accepted branch prints and logs `STUCK_BRANCH <key> attempt N on "<metric>": H4 ... (test: ...) | ...` and puts every hypothesis with its test into the area's tree as open. `--no-hypotheses "<reason>"` goes on without them and logs `HYPOTHESES_OVERRIDE <key> ...: <reason>`. Every recorded attempt also goes into the tree as tried. A lane's own unbranched second report is rung 2 too: the `STUCK` line tells you to re-instruct it with hypotheses.
- Rung 3, from `stuck.researchAt` (3): a research entry goes into the tree (so the next brief in the area shows it), and with `explore.sendResearchToLane` the lane gets `explore.researchText`: ulw research on the exact symptom, then a `dori challenge` of its next plan, before the next patch, in the same session. No rollover at this rung: a lane that is researching cannot be moved, and a moved one would re-read the research. An inferred count starts it too. Rung 3 is already done, and nothing is typed, when the lane ran both on its own after the repeat that made rung 3 due: ulw research (a real read of the ulw-research `SKILL.md` in its session log, or a research folder `<cwd>/.omo/ulw-research/<YYYYMMDD-HHMMSS>` started after it) and a `dori challenge` on record after it, on that symptom (the metric or one of its `autoSignals.aliases` names in a plan one of those challenges reviewed, or in a research folder's `brief.md`). The line then says `already done after attempt 3: <research> and <challenge>; nothing sent, wait for the next attempt's result` and carries `RESEARCH_DONE` instead of `RESEARCH_DUE`; a failed attempt after that research and challenge is rung 4 (at the first scan too, when the count jumps past it). A paused lane gets nothing typed either: the line says so, and `dori research-hint <key> --send` sends it after `dori resume`.
- Rung 4: an attempt that failed after rung 3, one hypothesis tried `stuck.fixatedAfter` (3) times after the lane branched (`fixated`), or an owner-check finding still there after a re-read the lead confirmed (`"@context"`, see `dori owner-check`). A count that jumps (the first untagged scan of a long loop) prints one line with the skipped rungs' old names and `first count` or `from rung N`. `--improved` restarts both halves (the inferred cycles counted so far become a baseline), a PASS too, and the `fix-attempt` gate uses this same count. The line says to decide a rollover (`dori rollover-propose`, then `dori handover --lane <key> --approved-by "lead:<reason and signal>"`). Nothing switches by itself unless `handover.autoRolloverLanes` is on: then `freshness` starts the rollover at rung 4 like at a measured threshold (`ROLLOVER_AUTO`).
### `dori signals [--lane K | --cwd DIR | --tag T ...]`
What earlier lanes in one area tried and how it went, from records only (no model call). Read it before you re-instruct a lane. The options combine as "any of". The first line is the area: lanes, done claims rejected over claims, and rework (your messages to the lanes plus freshness nudges, per lane). Then per lane, newest first:

- its outcome (`open`, `paused`, `not-done`, `done-claimed`, `closed, verified`, `closed by the lead`), cwd, tags, re-sends (`scorecard.leadSendPattern` in `scorecard.leadSessions`) and nudges (`scorecard.lanesLog`);
- numbered fix attempts: a `[REPORT]` line or a message you typed into the lane matching `signals.numberedAttemptPattern` ("adjustment 2", "조정 2/2욌째"), with the words around the first mention and the latest mention before the root-cause switch;
- the root-cause switch: the first such message after an attempt that matches `signals.rootCausePattern` (a message about the root cause is never itself an attempt);
- tagged fixes by metric with each hypothesis and its count (the lane's `fixes`, or the `(fix: M / H)` tags in its reports when the sweep never recorded them);
- rejected done claims with the reasons;
- warnings: `SAME_FIX` (one metric and hypothesis `stuck.fixatedAfter` times), `REPEAT` (one metric over several hypotheses, or numbered attempts up to `stuck.fixatedAfter` with no root-cause switch), `REJECTED` (two or more rejected claims).

Without an option it prints one `SIGNALS <key> [<outcome>] fixes N, attempts 1-N, rejected R/C, re-sends S, nudges U` line per open lane with a record. Session files older than the oldest lane asked about are not read.

### Exploring when stuck

The point of these commands: when a fix does not move a metric, the next step is to find out which explanation is true, not to patch again. Each has its own section below; how the lead uses them is in `sessions.md`, "Stuck: branch, look outside, check intent", and the E7 example in `operating-lessons.md`.

### `dori tree [show|add|falsify|support|close|reopen] [ID] [--lane K | --cwd DIR | --tag T] [--kind K] [--text T] [--test X] [--metric M] [--result R]`
The hypothesis tree of one area: a JSON file per repo (`<stateDir>/trees/cwd-<path>.json`) or tag (`tag-<tag>.json`). A lane's area is its cwd unless that is `defaultCwd`, else its first tag. Without an area option it uses the lane of the pane it runs in, else the current directory. Entries have an id by kind: `H` hypothesis, `D` untried direction, `F` finding, `R` research due, `T` an attempt tried; and a status: `open`, `falsified`, `supported`, `closed`.

- `show` (default) prints `TREE <area>: N entries` and the entries by group: open hypotheses with their tests, supported, falsified (do not retry), untried directions, research due, findings, attempts tried, then closed ones.
- `add --kind hypothesis|direction|finding|research --text T [--test X] [--metric M] [--result R]` prints `TREE_ADDED <id>`, or `TREE_EXISTS <id>` when the same kind already says the same thing (a missing test is filled in).
- `falsify|support|close|reopen <ID> [--result R]` sets the status and prints `TREE_SET <id> <status> -> <result>`.

Fed automatically by `fix-attempt` (tried attempts, branched hypotheses, research due), `freshness` (the lanes' tagged fix reports), and `fork-explore` (results). `launch` attaches the compact form to new briefs.

### `dori challenge <key> --plan FILE [--model M] [--all]` and `dori challenge --check [<key>]`
Adversarial review before a big step. It sends the plan (up to 60,000 characters), the lane's title and goal, and the area's tree to a model of another family than the lane's own model, in a fresh context (no session, skills, context files or lane history): `explore.challengeCommand`, by default `omo -p --no-session --tools read,grep,find,ls --no-extensions --no-skills --no-context-files --omo-senpi-disabled --system-prompt <reviewer instructions> --model <reviewer> <prompt>`, run in the plan's repository (the git top level of the plan's directory, else that directory). The reviewer can read and search files there to check what the plan cites; it cannot change files or run anything. Its final reply is the review, under three headings: "Reasons this will fail", "Missing alternatives", "Cheapest falsifying test". Only a reply with all three is saved. Families come from the model id (`claude`/`opus`/`sonnet`/`fable` anthropic, `gpt`/`o3`/`codex` openai, `grok` xai, `gemini` google, `qwen`, `kimi`, `glm`, `deepseek` ...), whatever provider serves it.

Why read-only tools: `omo -p` runs the reviewer as an agent, and an agent run ends at the first reply without a tool call. With `--no-tools`, a reviewer given a plan that cites files and results answered "I'll read the cited evidence first, then write the review" and that sentence was its whole output (reproduced 5 of 5 on a real plan; with read-only tools the same prompt wrote the review 4 of 4, reading 7-8 times first).

Order: by default the best GPT, then the best Claude, then the best Grok model that omo offers with a subscription login (`chatgpt-subscription/gpt-6-astra`, `anthropic-subscription/claude-fable-5-1`, `xai/grok-4.7`), then a second model of each family (`gpt-6.1-sol`, `claude-opus-5-5`, `grok-4.6`). Why these: `gpt-6-astra` is OpenAI's top tier in omo's catalog (priced 5x `gpt-6.1-sol`, and omo's escalation model above it), `claude-fable-5-1` is Anthropic's (priced 2.5x `claude-opus-5-5`, newer than `claude-fable-5`), and `grok-4.7` is the newest xai model (4.3 to 4.7 cost the same). On another machine, run `dori challenge --check` and put its best callable model of each family first. The lane's own family is always skipped, so on a Claude lane the order is GPT, then Grok. Without `--all` the first reviewer that writes a review is the only one asked (fallback order). With `--all` one review is collected from each family in list order, the next model of a family standing in for one that fails; each review is saved and recorded, and a family with none is reported. `--model` asks that one model (refused when it is the lane's family).

Before any call, each id is checked on this host: `explore.modelsCommand` lists the models each provider offers and `explore.authCommand` says whether a provider is logged in. An id whose provider offers it and is logged in is called as listed; one whose provider is not logged in (or does not offer it) is called on a logged-in provider that offers the same model (`github-copilot/gpt-6-astra` -> `chatgpt-subscription/gpt-6-astra`); one no logged-in provider offers is skipped with the reason. Ids are compared exactly as `omo --list-models` prints them (a `:high`-style thinking suffix aside): omo itself runs an inexact id as whatever it matches (`xai/grok-4` ran as `grok-4.7`), so such an id is skipped rather than silently doubled. `dori challenge --check [<key>]` prints this per id, without a review: `REVIEWER_OK <id> [-> <id called>] (<family>): <why>` or `REVIEWER_SKIP <id> (<family>): <why>`; with a key, only the ids of another family than that lane's model. It exits 1 when none can be called.

- A final reply that lacks a heading gets one stricter retry that quotes what went wrong (a safety net; with read-only tools it should not be needed). If the retry still lacks one, both replies are saved as `<stateDir>/challenges/<key>/<time>-<model>-raw.md` and the next reviewer is asked.
- A reviewer that exits with an error, or times out after `explore.challengeMinutes` (exit 124), is skipped for the next one.
- Each skip prints `CHALLENGE_SKIP <model>: <why>` and is logged as `CHALLENGE_SKIP <key> ...`; when no reviewer writes a complete review the command fails (exit 1) with every reason and raw file, logged as `CHALLENGE_FAILED <key> ...`.

Each review is saved as `<stateDir>/challenges/<key>/<time>-<model>.md` (with `- Read access: <dir>`, and `- Attempts: 2` when the stricter retry wrote it), recorded in the lane's `challenges`, logged as `CHALLENGE <key> reviewer=<model> ...`, and printed with `CHALLENGE_SAVED <file> reviewer=<model>`.

### `dori fork-explore <key> --metric M --hypotheses H1 --test T1 --hypotheses H2 --test T2 ... [--gpu N ...|--gpu-all] [--mode agent|cmd] [--minutes N] [--model M]`
Parallel branch exploration: one short, time-boxed task per hypothesis (at least two), all measuring the same metric M. With `--mode agent` (default) each branch is a headless agent run, `explore.branchCommand` in the lane's cwd, told its hypothesis, the metric, its test, the time limit (`--minutes`, default `explore.branchMinutes`), not to edit tracked files, and to end with `METRIC:`, `VERDICT: supports|falsifies|inconclusive` and `EVIDENCE:` lines. With `--mode cmd` each `--test` is a command run with `bash -lc` in the lane's cwd, which prints the same lines. CPU branches start at once. A GPU branch (`--gpu <branch number>`, repeatable, or `--gpu-all`) first takes a heavy slot, the same slots and load limit as `dori heavy`, so GPU branches queue one by one while CPU branches run. A branch that runs out of time is `timeout`; one that fails without a verdict is `error`. It prints `FORK_START ...`, then one markdown table (branch, hypothesis, metric value, verdict, evidence, run time, cpu or gpu with the slot wait), and `FORK_SAVED <file>`. The table and the raw results go to `<stateDir>/explore/<key>/<time>.md` and the lane's `explorations`; each hypothesis goes into the tree as falsified (falsifies), supported (supports) or open with the result noted; the watch log gets `FORK_EXPLORE <key> ...`.

### `dori research-hint <key> [--send]`
A search plan for the lane's stuck symptom, from its records only (no model call): `RESEARCH_HINT <key> on "<metric>": N attempts, ...`, the symptom and last report, what was already tried, four or five queries (papers, GitHub issues, failure-mode write-ups, how other repositories set the same problem up, other causes now that a hypothesis is falsified), and the `dori tree add --kind finding` line to record what was found. Works on closed lanes too.

With `--send` (and at rung 3 of the stuck ladder, when `explore.sendResearchToLane` is on) it types `explore.researchText` into the lane's pane as one line. The text starts with `ulw research `, so omo attaches its ulw-research skill pointer, and the lane runs the search as an ultra research: sources read in the owner's browser, a claim graph, a cited result. omo attaches that pointer only to typed (interactive or rpc) input that names `ulw research` outside quotes, code and links. It never attaches it when the text starts with a `[TAG]` such as `[LEAD]`, nor in a child or team-member session, and a brief that mentions it does not count. `{question}` is the research question built from the lane's records: the exact symptom (the metric that does not improve, the last report), what was tried, what a test ruled out and how, what is still open, and what to look for (papers, GitHub issues and discussions, repos that hit the symptom). The rest of the default text tells the lane to read the ulw-research SKILL.md first, record findings with `dori tree add --kind finding`, have its next plan challenged with `dori challenge`, and report back before the next patch. It prints `RESEARCH_SENT <key>` (or `RESEARCH_SEND_FAILED`, exit 1) and records the send in the lane's `research`.

### `dori research-check <key>`
Did the last ulw research text start the skill? It looks in the lane's session directory (`sessionsDir/--<cwd with / as ->--/`) for the newest `*.jsonl` written since the send that holds a user message starting with the typed text. From the send on, it looks for two markers:

- the pointer: an entry `{"type":"custom_message","customType":"omo-ulw-research:skill-pointer",...}`, or `<omo-ulw-research-pointer>` inside the typed user message (omo appends it there when the agent was busy);
- the skill read: an assistant `toolCall` block that reads the file, not one that only names it: the `read` tool with a path ending in `ulw-research/SKILL.md`, or an `eval`/`bash` call whose code holds the file's path (`/...`, `~/...`, `./...`, `${dir}/...`) as a whole string literal and reads a file with it (`Bun.file`, `readFile`, `readFileSync`, `createReadStream`, or `cat`/`sed`/`head`/`tail`/... on an interpolated path), or runs `cat`/`sed`/`head`/`tail`/`less`/`awk`/... on the path itself. A finding written with `dori tree add`, an `echo`, a memory note, or a log search that quotes the path is a mention and does not count. Only a read after the typed message reached the session counts for this send: a lane still busy with an earlier send may read the skill after the send but before it gets the new text, and that read counts as an earlier read.

Both markers: `RESEARCH_STARTED <key> ...`. Not yet: `RESEARCH_PENDING <key> N min ...: seen=… pointer=… skill-read=…`. Still missing after `explore.researchVerifyMin`: `RESEARCH_NOT_STARTED <key> ...` (exit 6), with what is missing (the text never reached the session log, omo attached no pointer, or the lane did not read the skill; a lane that read it earlier in the same session often does not read it again and answers without the skill's protocol, and the line says so) and the fix (re-send with `--send`, or tell the lane to read the SKILL.md). `dori freshness` runs the same check on every tick for a lane with a pending send and prints `RESEARCH_STARTED` / `RESEARCH_NOT_STARTED`. The decided line goes to the watch log once (source `research`), and the result is kept in the lane's `research.result`.

### `dori repeat-check <key> [--since ISO|Nd|Nh] [--until ISO] [--repo DIR ...] [--backtest]`
Untagged repeats, the inferred half of the stuck count. Lanes rarely tag their fixes, so a tagged count stays low while a lane re-targets one failing gate with prescription after prescription. This reads what the lane leaves anyway: its `[REPORT]` lines (in its own session folder, `<sessionsDir>/--<cwd>--`, and in `scorecard.leadSessions`), the commit subjects on its branches (`worktrees`, its cwd if that is a repository, and `--repo`) and its hypothesis-tree entries. A gate line fails when an item carries a value and `FAIL` (`교착 554 FAIL(≤2)`, or the items of a bare `FAIL 도랑 위 덤프 1·교착 58` list up to a dash), or when a prescription's verdict (`기각`, `판정 불가`, `REJECTED`) names a known metric in its sentence. A new attempt targets it when one sentence (`autoSignals.targetScope`) holds a prescription word and the metric's name or an alias, and is not negated ("안 띄움", "not launched") or only a diagnosis; a failure is never consumed by the report that states it. Each "failed, then a new attempt on it" is one cycle; attempts within `autoSignals.repeatGapMin` are one; a `PASS` of the metric starts it again. From `stuck.researchAt` cycles it prints `INFERRED <key> "<metric>" <n> (from untagged ...; tagged <t>) ...` with every failure and attempt line as evidence, else `REPEAT_NONE` with the counts. In `freshness` the counts and each metric's last PASS are kept in the lane's `inferred`, a grown count's full chain is appended to `<stateDir>/auto-signals/<key>.md`, and every changed metric takes a step of the stuck ladder (its `STUCK` line, if the rung went up). A PASS before the sweep ends the run, so no line. Default window: the lane's current session. `--backtest` replays the window and prints each time a count reached `stuck.researchAt` or grew past it, with its time.

### `dori owner-check <key> [--force | --reread]`
A reviewer of another family than the lane's (`reviewers.models` with `autoSignals.ownerCheck.first` in front, checked like `challenge` reviewers) gets the lane's brief (without the Past signals and tree sections launch adds), the owner's goal, the lead's `[LEAD]` relays that carry the owner's words (a Discord message link, or marked 원문 / verbatim), the owner's own decisions in the lane's `discord:<id>` thread from the inbox (question-card answers and the owner's messages, author `DORI_DISCORD_OWNER`; the inbox is `handover.inbox`, `DORI_DISCORD_INBOX` or `<stateDir>/discord/inbox.jsonl`; the newest `autoSignals.ownerCheck.relays`) and the newest reports, all dated (on one subject the newest owner decision wins, and a later report replaces an earlier report's state) and as written in Korean or any language, and answers in blocks `VERDICT: VIOLATION | CONTRADICTION | GOAL_LOSS`, `OWNER: "<quote>"`, `REPORT: "<quote>"`, `WHY: ...`, or `VERDICT: OK`. The prompt also carries the registry's fact on a done claim (`Done claim on record: none ...` or the claim's time and evidence): a report that only names `dori claim-done` or quotes the footer is not a claim, and only reports that were sent (a `send-keys`, `send-text` or `dori type` call) or received (text typed into the session) are read, so a report template quoted in a goal, brief or note is no report. Every finding is checked against the inputs before it counts. Its owner quote must be in the owner's words: the goal, an owner decision, the quoted parts of the brief and of the relays (`"..."`, `'...'`, `“...”`, `‘...’`, `「...」` of 6+ characters), or an owner message a brief or relay links (`discord.com/channels/.../<message id>`, read from the inbox, author `DORI_DISCORD_OWNER`). Text outside quote marks is the lead's, and so is a card's question (only the owner's choice counts); a `CONTRADICTION` may also quote a fact the brief states. Relays are read only from the lane's own sessions (session files that carry its `[REPORT] <key> |` lines), not from other lanes in the same cwd, and the brief is read without the sections launch adds (Past signals, Hypothesis tree, Lane footer). A finding whose owner quote is not there is dropped and logged as `OWNER_CHECK_UNGROUNDED <key> <kind> owner "..." ... dropped, no rung`. A finding whose report quote (each piece, when it is joined with `…`) is only in reports an earlier check already read (at or before the last check's `lastReportAt`), or in a direction stated before the last check, is dropped too, as `OWNER_CHECK_STALE <key> <kind> report "..." ... not flagged again, no rung`. A check whose findings were all dropped leaves the ladder as it was, and keeps the last finding on record only while that finding's own owner quote still holds. Prints `OWNER_CHECK <key> <kind> owner "..." vs report "...": <why> [reviewer <model>]`; a report quote not found in the reports read adds `(unverified: ...)`, and so does a CONTRADICTION resting on the claim-done command while no claim is on record. An unverified finding goes to the watch log as that `OWNER_CHECK` line and stays off the ladder. A verified finding is the stuck ladder's context rung: it prints and logs one line, `STUCK <key> "@context" rung context (<kinds>: owner "..." vs report "...": <why>; reviewer <model>) -> confirm the finding, then dori owner-check <key> --reread ... [OWNER_CHECK_<kind>]`; a finding on a report (or a stated direction) written after a re-read you confirmed with `--reread` is `rung 4` (`[... ROLLOVER_DUE]`; without a re-read it stays the context rung; the context mark keeps the report under the finding, so the same report never moves it twice), and a clean check (`OWNER_CHECK <key> OK ...`, logged as such) ends the context rung. It runs only when a report is newer than the last check, at most once per `autoSignals.ownerCheck.minIntervalMin` and `maxPerDay` times a day per lane (`OWNER_CHECK_SKIP` says why); `--force` skips the interval and daily limit, never the new-report rule. A reviewer that fails or answers out of format is skipped for the next; none left is `OWNER_CHECK_FAILED` (exit 1). The result is kept in the lane's `ownerCheck` (with the first finding). Nothing is sent to the lane by the check. `--reread` is your confirmation of the last finding: it types `stuck.rereadText` into the lane (its brief path and the finding filled in) and prints `REREAD_SENT` (or `REREAD_FAILED`, exit 1); after a clean check it refuses (`REREAD_REFUSED`, exit 1).

Each owner check also reads the lane's brief against the directive ledger (`dori directive-audit` above, for that lane; the brief includes its `## 추가 지침(리드, launch 뒤)` section, so a directive `dori directives apply` sent is no longer a gap): a directive in scope that is not in the brief, or a lead directive not followed, is an `OWNER_CHECK_DIRECTIVE_GAP <key> <id>: ...` (or `OWNER_CHECK_DIRECTIVE_LEAD`) line in its output and the watch log, even when no reviewer answers; and the owner's words of the directives in scope go to the reviewer under OWNER DIRECTIVES and count as the owner's words a finding may quote, so a report that breaks one is a `VIOLATION`.

### `dori intent-check <key> [--direction TEXT] [--next TEXT] [--goal G]`
Prints the owner's goal (the lane's `goal`) next to the lane's current direction and next step, then runs the owner check on them at once (`dori owner-check`, with no interval and no new report needed but within `autoSignals.ownerCheck.maxPerDay`; the stated direction is in the prompt and counts as evidence a finding may quote): `OWNER_CHECK <key> OK ...`, or a finding with its `STUCK <key> "@context" ...` line. It replaced a count of shared words with the goal, which could not judge a Korean goal at all (an English report of the same step scored 0.00). The direction is what the lane last stated with `--direction` (stored in the lane's `direction` with `--next`), else its last report; the next step is `--next`, else a "next:" in the report, else the test of its first open hypothesis. `--goal` sets the goal of a lane launched without one. `dori freshness` runs the owner check first for a lane whose milestone report matches `explore.stagePattern` (a new stage, phase, pivot or next step).

### `dori scorecard [--date YYYY-MM-DD|today|yesterday] [--post] [--to discord:<id>]`
Prints the day's token scorecard, computed from records only (no model call), for the calendar day in `scorecard.timeZone` (default today):

1. cost per verified completion: the API-priced cost of every assistant call in `scorecard.sessions` (default `sessionsDir`) that day, over the lanes closed that day (a close always re-reads the Done signals);
2. the done-claim rejection rate, always next to line 1, since either alone can be gamed: claims that day, and the `not-done` entries that answered a claim (a lane parked as not-done is not a rejection; a repeated claim counts once);
3. the three lanes with most rework: the lead's messages to the lane (`leadSendPattern` in `leadSessions`) plus freshness nudges (`lanesLog`);
4. first reply to the owner: median and p90 seconds from an owner message in the inbox to the first lead tool result matching `replyPattern` after the message reached the lead session;

plus the lead's context tax: its cost, the share spent re-reading cache, and its median context size. A line whose source is not configured says so. Each run saves the card for the lead to read (`SAVED <path>`): `<stateDir>/scorecard/<date>.json` (the numbers and the card) and `latest.md` (the card); day files older than `scorecard.keepDays` are removed. Nothing is posted unless `--post` is given, which sends the card to `--to`, `scorecard.postTo` or `DORI_DISCORD_CHANNEL`.

### `dori close <key> [--note TEXT]`
Closes a lane now. Refuses (exit 2) unless every `Done =` signal reads back live; when the plan changed after launch and the line is stale, change it with `dori done-set` first. On success it marks the thread done through `hooks.threadDone`, then, when `DORI_DISCORD_TOKEN` is set and the thread is `discord:<id>`, sets the thread's name to the done mark (`✅` or `[done]`, per `discord.statusStyle`) and archives it. An archived thread is unarchived, renamed and archived again, because Discord refuses to rename an archived thread; a thread that already shows done and is archived is left alone. If that fails, `THREAD_DONE_WARN <key> <thread>: <error>` is printed and the close still succeeds. A thread that another open lane also uses, or that has an open question card, is left as it is: `hooks.threadDone` does not run and the thread is not renamed or archived; the lane's result goes there as `<title>: <text>` instead, posted straight to Discord when `DORI_DISCORD_TOKEN` is set, else through `hooks.threadReply` (run with `DORI_CLOSING_LANE=<key>`, so `dori thread reply` does not count the closing lane as working) (`thread left open: open lane <key> uses it too` or `open card <Qn>`, then `result posted`, in the receipt). With the token, once the lane is recorded closed, the thread is asked for waiting through the thread status queue when what is left waits on the owner, an open card or a paused lane (cards and lanes are read again then, so a card answered during the close does not count): it turns ⏸️ (`waiting requested: applied|unchanged|pending|dropped` in the receipt; the queue prints `THREAD_STATUS_APPLIED`). A rename Discord holds back (`pending`, kept for the listener) or refuses (`dropped`) prints `THREAD_STATUS_WARN <key> <thread>: waiting requested: <outcome>` before `CLOSED`. While another lane there is working, not-done or done-claimed (the lead still decides), the mark is left as it is. `dori resume` of a lane in a `discord:` thread asks for working again, so a thread left ⏸️ beside a paused lane turns 🔄. The last lane to close with nothing else on the thread marks it done. Then it closes the tab, and removes the lane's worktrees with a plain `git worktree remove`, which refuses a dirty worktree. When `hooks.threadDone` is set but the lane has no usable thread (`none`, empty, or malformed), the hook is not run and `THREAD_MISSING <key> thread=...` is printed before `CLOSED`, and the receipt records `thread missing`; close that thread by hand, or run `dori set-thread` before closing. The automatic close in `dori watch` prints the same line before `LANE_CLOSED`.

### `dori watch`
Runs forever. Every 30 seconds it prints each new claim once (`LANE_DONE_CLAIMED`). Claims older than `closeAfterMin` are settled: unpushed or uncommitted work and failing signals turn into objections (`LANE_NOT_DONE`); otherwise the lane is closed (`LANE_CLOSED`). The thread gets `discord.doneText` through `hooks.threadDone`, not the claim's evidence (that stays in the lane's record and the `LANE_DONE_CLAIMED` line); `discord.postRawReports: true` posts `Done: <evidence>` as before. The deadline lives in the registry, so a restart picks up where it left off.

With backend `aoe` it also prints `LANE_BLOCKED <key> <state> <pane>` once each time a working (or not-done) lane's agent stops for a human. Unless the screen shows a running turn (`esc to interrupt`), `state` is `waiting` or `error` when `aoe ps --json` says so, `question` when omo's question UI (`Ask user ·`, `(0/1 answered)`) is on screen (aoe shows that as `idle`), and `idle` once the turn has stayed ended for 45 seconds. A lane waiting on something that will wake it is not idle: its status line shows a monitor (`◉ watching`), wake sources on duty (`wake source`), a scheduled goal continuation (`goal continues in`) or an active goal (`Pursuing goal`). The state is kept in the lane's `blocked` and `idleSince` fields, so a restart does not repeat the line; when the lane runs again they clear and the next block is reported again. If `aoe ps` fails, the tick prints `LANE_WATCH_WARN blocked check: ...` and the done flow still runs.

### `dori freshness [--loop MIN]`
For working lanes that have gone quiet: a nudge in the pane after `nudgeAfterMin`, then after `postAfterMin` a short status line in the owner's words posted to its thread: `discord.quietText` with `{min}` as the minutes since the last report. The report itself is a note for the lead, so it is not posted; it goes to `leadPane` as `[DORI] <key>: N min without a new report ... Last report: <report>` for the lead to retell in plain words. Each happens once per silence. With `discord.postRawReports: true` the old behavior returns: the last `[REPORT]` line is posted to the thread, home paths and pane ids scrubbed, and the lead gets no note.

Lanes send `[REPORT]` lines to the lead pane, so the report is read from the last 3000 lines of `leadPane` first and from the lane's own screen second. A report the agent UI wrapped over several lines is joined up to the next blank line. A report that differs from the last one seen (kept in the lane's `lastReport`) counts as hearing from the lane and starts a new silence. Output lines: `NUDGED`, `NUDGE-FAILED` (the text stayed in the pane's input), `POSTED` (ending in `; lead told` or `; lead not told: <why>`), `NO-REPORT`, `STUCK` (one per rung change of the stuck ladder, from a new report tagged `(fix: <metric> / <hypothesis>)` and from the inferred count, which `dori repeat-check` computes over the lane's current session on each new report; see `dori fix-attempt`), `ROLLOVER_DUE` for a measured threshold, and `RESEARCH_STARTED` / `RESEARCH_NOT_STARTED`. Then, for at most `autoSignals.ownerCheck.perTick` lane heard from since its last owner check (a lane whose milestone report started a new stage first), it runs `dori owner-check`; a finding prints its `STUCK ... "@context"` line (OK results go only to the log). Only rung 3 types into the lane (the ulw research text); nothing else here sends anything to the lane.

### `dori dead-panes [--loop MIN]`
Prints `DEAD_PANE <id>` once per hour for a pane whose last lines match `deadPanePatterns`.

### `dori guard [--loop MIN]`
Prints `HOST_GUARD ALERT <reasons>` when load, free memory, free disk or the pane count crosses its threshold, and `HOST_GUARD CLEAR` when it recovers. It also prints `COMPUTE_READY` / `COMPUTE_BUSY` as load crosses `loadOk`. Only changes are printed.

### `dori can-launch`
Prints `CAN_LAUNCH` and exits 0 when the host has room for another lane. Otherwise it prints `HOLD <reasons>` and exits 4. The reasons come from the guard's memory, disk and pane-count thresholds. CPU load alone never holds a launch, because it moves too fast to plan around.

### `dori type <pane> --text TEXT | --text-file FILE`

Types text into an agent pane and confirms the agent took it. Every script that types into a pane (launch prompts, `[LEAD]` notes from `claim-done`, `object-done` and `freshness`, `update` announcements and alerts, `research-hint --send`, same-fix notes, handover prompts, `setups/discord-aoe/self-restart.sh`) goes through the same helper; use this command for your own relays to lanes.

1. Waits for the `❯` prompt (aoe), types the text as one argv argument, waits 1.5 s so a long text lands whole (it arrives as a paste), presses Enter.
2. Reads the input box, the lines between the last two `─` borders, each cut at the column where the borders end (senpi's side panel sits right of it on the same rows, so a FILES line like `?? fp_clay_101.log` is not unsent text). Folded pastes (`[paste #1 +13 lines]`) and a tall box whose `❯` line scrolled out of view count as text still there; the same text in the transcript above does not. Still there after 3 s: one more Enter, and 3 s more.
3. An empty box must show a running turn (`esc to interrupt` on or just above the box), or the text queued above the box as `Steering: <text>` (it was sent while a turn ran), within 15 s.

Prints `SUBMITTED <pane>` (exit 0) or `NOT_SUBMITTED <pane> <reason>` (exit 1); `NOT_SUBMITTED` also goes to the watch log as `submit NOT_SUBMITTED <pane> <reason>`. Text with a backtick or `$(` is refused. `scorecard.leadSendPattern` counts `dori type <pane>` as a lead message to that lane.

### `dori send <slack|telegram|discord> --to TARGET --text TEXT [--thread ID] [--edit ID]`
Posts a message, or edits one with `--edit`. Tokens come from `DORI_SLACK_TOKEN` (plus `DORI_SLACK_COOKIE` for a user token), `DORI_TELEGRAM_TOKEN` or `DORI_DISCORD_TOKEN`. Text containing `$(` is refused, since it can only come from a shell string. Rate limits are retried with the server's wait time; other errors fail at once.

### `dori presence <slack|discord>`
Keeps the account shown as online until stopped.
- **Discord:** the bot connects to the gateway and identifies as online.
- **Slack, user token:** it opens one web-client-type socket and tickles it every minute. Slack shows a user active only while such a socket is open, and auto-aways an idle one after about 30 minutes.
- Run one instance per account. Two writers flip each other's presence.

### `dori inbound slack [--loop MIN]`
Prints `INBOUND <source> <channel> <thread> <ts> <user> <text>`. It reads from three places, each message once:
- `threads-view`: unread replies in threads the account follows (Slack's own Threads view);
- `own-thread`: new replies in any thread the Dori posted in, tagged or not;
- `unread`: DMs, group DMs and channels with unread mentions.

The Dori's own messages and bot messages are skipped. Every message the Dori posts records its thread in `<stateDir>/slack-threads.json`, whichever helper sends it, so a guest's untagged reply under a root posted with a raw API call is still found.

### `dori inbound discord`
Runs until stopped (run it as a service, see `setups/discord-aoe/`). It connects to the gateway with the message-content intent and handles:
- the owner's messages in `DORI_DISCORD_CHANNEL`, its threads, and DMs; everyone else, bots included, is skipped. Each gets the eyes reaction at once, a voice note is transcribed through `hooks.transcribe`, and one row is appended to the inbox file (`DORI_DISCORD_INBOX`, default `<stateDir>/discord/inbox.jsonl`) and printed as `INBOUND discord-<scope> <channel> <id> <author> <text>`;
- the owner calling this Dori anywhere else in the guild: a message in any other channel or thread that mentions its bot user or one of its roles (the roles its bot member has, read again at every gateway READY and printed as `DISCORD_MENTION_IDS user=<bot> roles=<ids>`, plus `discord.mentionRoleIds`; a mention that comes during the read waits for it, and a failed read prints `DISCORD_MENTION_IDS_FAIL <error>` and is tried again by the next mention) gets the eyes and a `scope:"mention"` row with its `channel_id`, a `link` to the message and a `note`: answer in the Dori's own channel or work thread with that link, never in the other channel (it belongs to someone else; read it, do not write there). Another Dori's bot or role is not this Dori's mention, and the owner's other messages in channels the Dori does not own are skipped with no eyes. Mentions elsewhere are not backfilled after a reconnect;
- question-card taps and write-my-own submissions (below), appended as `kind:"answer"` rows and printed as `ANSWER <Qn> <kind> <answer> thread=… session=… tmux=…`;
- the bot's own messages (with `discord.autoUnEye`, on by default): when the bot it runs as writes in a channel, thread or DM, by any helper, the eyes come off every earlier owner message in that same channel, thread or DM, off the message it replies to, and off any message carrying eyes that its text links to (`https://discord.com/channels/<guild>/<channel>/<message>`: how a mention row's eyes come off). Other bots' messages clear nothing. The messages still carrying eyes are kept in `eyes.json` beside the inbox file; the removals for one channel run one at a time and wait out a 429's `retry_after`. It prints `EYES_CLEARED <channel> by=<bot message> <ids>`, or `DISCORD_UNREACT_FAIL <id> <error>` for a message it could not clear;
- after each reconnect, the owner's messages it missed in the channel and its active threads, oldest first. It reads after the newest message among the inbox rows it wrote itself (`dm`, `channel`, `thread`, `mention`), so rows other listeners append to a shared inbox file (another messenger, another channel) never move that point;
- an owner message in a done thread (✅ or `[done]`) reopens it: the thread is unarchived, marked working, and `THREAD_REOPENED <thread>` is printed.
- with `DORI_DISCORD_PAIR_CHANNEL` (a channel shared with a second Dori) and `DORI_DISCORD_PAIR_BOT` (that Dori's bot id): the owner's messages there become `scope:"pair"` rows with the eyes reaction and that bot's `scope:"pair-bot"` rows without it (the Dori rarely answers them, so the eyes would never come off); treat pair-bot rows as information, never as requests. Other bots there are skipped, the pair channel is backfilled too, and both scopes count as this listener's own rows for the backfill point. Unset: that channel is skipped like any other.

`DORI_DISCORD_SHADOW_INBOX=<file>` runs a shadow listener: the same inbox rows go to that file instead of the live inbox (it refuses to start when the two are the same file), but it writes nothing to Discord: no eyes reaction, no reopen, no unreact, no `eyes.json`, and card taps are not answered: for an owner's tap or typed answer it appends the `kind:"answer"` row the live listener would (same fields; `ts` is its own clock) without changing `questions.json` and prints `SHADOW_ANSWER <Qn> <answer>`; anything else prints `SHADOW_INTERACTION_SKIPPED <interaction> <custom id>`. It prints `DISCORD_LISTENER_READY shadow`. Use it beside a running listener to compare rows by message id before switching listeners; stop it before starting the new one for real.

A rejected token or a missing intent stops it (exit 3, or 4 for a disallowed intent); other disconnects retry with backoff up to a minute.

### `dori ask --text Q --option A [--option B ...] [--thread REF] [--session ID] [--tmux NAME]`
Posts a question card, pinging only the owner, and prints `ASKED <Qn> message=<id>`. With `--thread` the card goes inside that work thread and the thread is marked waiting (`[waiting]`, or ⏸️ with emoji status); without it the card goes to `DORI_DISCORD_CHANNEL`. Each option is shown in full as a numbered line with a short pick button beside it, and the first option's button is the highlighted one, so put your recommendation first; a write-my-own button that opens a text box is added last (1 to 9 options). `--thread`, `--session` and `--tmux` travel with the answer so you know where to relay it. Only the owner's answer counts: the card folds into `[answered] <Qn> … → <answer>` (`✅ <Qn> …` with emoji status) in the interaction response, the answer is appended to `<stateDir>/discord/answers.jsonl`. (`DORI_DISCORD_STATE_DIR` moves `questions.json` and `answers.jsonl` for `ask`, `questions`, `reopen`, `resolve` and the listener alike.) A card inside its thread is that thread's record; a card in the channel for a thread also leaves a silent record line in the thread. Once no question in the thread is open, the thread is marked working again (🔄). The listener takes taps from the channel and from the thread a card was posted in, and must be running to receive them. A failed thread rename is printed as `THREAD_STATUS_FAIL <thread> <error>` and does not fail the card. Every status change (ask, answer, reopen, resolve, `dori thread`, `dori close`) goes through the thread status queue: the mark is decided from the open cards when the rename runs, and a rename Discord refuses with 429 stays in `thread-status.json` (`THREAD_STATUS_PENDING <thread> <status> retry_in=<s>s`) until the listener applies it (`THREAD_STATUS_APPLIED`). An owner message in a thread with an open card adds `open_cards` and `note` to its inbox row and prints `CARD_STILL_OPEN <Qn,...> thread=<id> ...`; the card stays open until you resolve it with `--answer`.

### `dori questions [--open]` / `dori reopen <Qn>` / `dori resolve <Qn> [--answer TEXT]`
List tracked questions; put a card's buttons back where it was posted (when a typed answer was not really an answer), marking its thread waiting again; forget a question once its follow-up is done. The folded card stays in the chat as the record. Resolving a card that is still open (the owner answered in a message, or the question was dropped) first edits it, in its thread or channel, into the same record a tap leaves: `[answered] <Qn> … → <TEXT>` (`✅` with emoji status) marked `byReply`, with `repliedInText` when `--answer` is not given; the answer is appended to `answers.jsonl`, and the thread is marked working again once no other question in it is open. A card in a thread that archived itself is edited after the thread is opened (Discord refuses edits there, 50083). A failed edit exits 1 and keeps the question open, so the same command can be run again. It prints `RESOLVED <Qn> folded`; a card already folded by a tap is not edited again and its thread status is left alone (`RESOLVED <Qn> kept`); a question resolved before changes nothing (`RESOLVED <Qn> already`). Since `resolve` forgets the question, `reopen` works only before it.

### `dori lead`
Prints `<aoe-id> <tmux-session>` for the lead, followed by ` stopped` when its tmux session is not running (at boot it is not yet; `dori-lead.service` and `dori.sh` start it from the id). The tmux name comes from `DORI_LEAD_TMUX`, else `leadPane` (`DORI_LEAD_PANE` overrides the config). `DORI_LEAD_AOE_ID` is accepted only when its first eight characters match the tmux name's final eight characters; otherwise the id is found with `aoe list --json`. ### `dori thread map discord:<id> <session|none>` / `dori thread list`
`map` sets the session, keeping the recorded title, and prints `THREAD_MAPPED discord:<id> <session|none>`. `none` stores null. `list` prints one line per mapping: `<id> <session|none> <title>`. The map uses `{"<id>":{"session":null,"title":"..."}}`; `cardDir` is `DORI_DISCORD_STATE_DIR`, else `<stateDir>/discord`, so an existing map there needs no migration. Writes use a temporary file and rename. The exported `threads`, `mapThread` and `dropThread` in `src/messenger/thread-map.ts` take the directory as their first argument and can be imported by a JS kernel.

### `dori thread set discord:<id> working|waiting|done [--open-card]`
Requests the status through the existing `ThreadStatusQueue`, without posting a message. An open lane on the thread that is working (or sent back by an objection, `not-done`) keeps a non-done thread working, past an open card and past `waiting`: waiting means nothing is left on our side (`THREAD_STATUS_APPLIED <id> working open=<cards> working=<lanes>`). With no such lane, open question cards (or `--open-card`) keep it waiting. `done` makes the same check as `dori thread done` below (`THREAD_LEFT_OPEN`, `--force`, `THREAD_DONE_FORCED`); done wins, archives it and drops its mapping after the status is applied. A rate-limited rename stays queued until the listener applies it; the mapping stays until then.

### `dori thread <reply|wait|done> discord:<thread id> <text>`
A ready `hooks.threadReply` / `hooks.threadDone` for Discord: `["dori", "thread", "reply", "{thread}", "{text}"]`. It shows typing, posts the text with emoji removed, and sets the status mark at the start of the thread name: `reply` working, `wait` waiting, `done` done. `done` archives the thread; the others unarchive it. Nothing is renamed when the mark already holds, because Discord allows only about two renames per ten minutes. `done` first makes the same check as closing a lane: while another open lane or an open question card uses the thread, it posts the text and prints `POSTED <id> THREAD_LEFT_OPEN discord:<id>: <holders>; not marked done (--force marks it done anyway)`, and leaves the mark and the archive as they are. The lane whose close runs it is not another user: `hooks.threadDone` runs with `DORI_CLOSING_LANE=<key>`, and `--lane <key>` says the same by hand. `--force` marks the thread done anyway and prints `THREAD_DONE_FORCED discord:<id>: <holders>; marking it done anyway` first.

### `dori send discord --to <thread> [--edit <id>] --status working|done --text <text>`
Writes the text as the progress message in `discord.statusStyle`: `working: <text>` / `done: <text>`, or `⏳ · <text>` / `✅ <text>` with emoji.

### `dori transcribe <audio-file>`
Runs `hooks.transcribe` and prints the transcript. A failed or empty transcription is an error, never an empty message.

### `dori heavy <label> -- <command ...>`
Waits until load is under `heavyMaxLoad` and one of `heavySlots` is free, then runs the command and frees the slot when it exits. A slot held by a process that no longer exists (or a zombie) is taken over. Use it for full builds and test suites. Installs, focused tests and git do not need it.
