# Scripts

`scripts/` is a bun + TypeScript package with one CLI, `dori`. Every external command runs as an argv array; nothing builds a shell string.

## Install and test

```sh
cd skills/dori-mode/scripts
bun install          # dev dependencies only (types, tsc, biome, knip)
bun link             # puts `dori` on your PATH
bun test             # behavior tests with fake herdr/hc/git/gh; nothing real is touched
bunx tsc --noEmit    # typecheck (strict flag set)
bun run ci           # biome lint, typecheck, knip, the 250-line check, then bun test
```

The checks follow upstream #149 (https://github.com/sisyphuslabs/omo-dori-mode-experimental/pull/149) inside this package: `biome.jsonc` (lint; its formatter is off in the fork for now, since formatting all of scripts/ is a diff no review can read), the strict flags in `tsconfig.json` (`exactOptionalPropertyTypes`, `noPropertyAccessFromIndexSignature`, `noUnusedLocals`, ...), `knip.json` (unused files, exports and dependencies) and `check-loc.ts`: no file under `src/` or `test/` may pass 250 lines unless `loc-baseline.json` lists it at its exact line count. Upstream #159 split its last oversize files and dropped its baseline; here every file that came from upstream is under the cap too, and the baseline lists only the fork's own files (their split is a follow-up, docs/follow-ups.md) (`LOC_OVER`, `LOC_GREW`, `LOC_LOOSE`, `LOC_STALE`), so a listed file can only shrink and leave the list. These are dev dependencies only: `dori update` runs git alone and the CLI needs none of them at run time.

`bun test` (run from `scripts/`, where `bunfig.toml` preloads `test/preload.ts`) starts with every `DORI_*` variable removed, so it passes the same inside an aoe window, which carries its Dori's `DORI_CONFIG`, `DORI_ENV_FILE` and `DORI_STATE_DIR`, as in a bare shell; a test that needs one sets it itself. It then sets `DORI_HEAVY_HOLD_DIR` to a directory that does not exist, so a hold this host really has on (`dori heavy hold-local`) never reaches a test. Bun gives a child spawned without `env` the environment the test run started with, so a test whose command stands in for another host passes the cleaned environment explicitly (`heavy-queue.test.ts`: `env -i`).

Needs: bun 1.3+, herdr, git, and the GitHub CLI (`gh`) for `merged`/`closed` signals (npm for `published`). The `command`, `file` and `url` signals need nothing extra. The full list of signal kinds is in `sessions.md`. A `command` signal runs with git's `core.quotepath` off (set through `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>`, after any entries the environment already has), so `git status`, `git log --name-only` and `git diff --name-only` print a Korean or other non-ASCII path as it is (`보고서.md`, not `"\353\263\264..."`) and a `stdout~` regex or a `grep` on it can match. The host guard reads `sysctl`, `memory_pressure` and `df` on macOS; on Linux it reads `/proc/loadavg`, `/proc/meminfo` (free memory is MemAvailable over MemTotal) and `df`, and swap reads as unknown. Memory that neither `memory_pressure` nor `/proc/meminfo` gives reads `memory free unknown` and holds nothing, as before (dori-superagent #90).

Tokens and ids come from the environment. Every command first reads `~/.dori/dori.env` (or the file in `DORI_ENV_FILE`, or another Dori's file when the working directory is one of its `instances`), `KEY=VALUE` per line; a variable already set wins, except when the file's token (`DORI_DISCORD_TOKEN`, `DORI_SLACK_TOKEN`, `DORI_TELEGRAM_TOKEN`) is another bot than the inherited one (a Discord token's bot id, a Telegram token's id before the colon, else the whole token; a rotated token of the same bot is the same bot). Then the environment is another Dori's (a tmux server or unit that loaded its `dori.env`), and every inherited `DORI_DISCORD_*`, `DORI_SLACK_*`, `DORI_TELEGRAM_*`, `DORI_LEAD_*` (not `DORI_LEAD_PANE`), `DORI_ASR_*`, `DORI_GOOGLE_*`, `DORI_KAKAO_*` and `DORI_USAGE_*` value is dropped before the file is read, with one `DORI_ENV_FOREIGN dropped <n> ...` line on stderr; `DORI_CONFIG`, `DORI_ENV_FILE`, `DORI_STATE_DIR`, `DORI_LEAD_PANE` and `DORI_DISCORD_SHADOW_INBOX` stay. To run with another bot's token (scratch QA), point `DORI_ENV_FILE` at a file holding that token, not at the real one. Every Discord write (`send discord`, thread starts, renames, posts, cards, the listener, presence) first checks the token's bot (the base64 user id before its first dot): not `discord.botId` when that is set, or the pair Dori's bot (`DORI_DISCORD_PAIR_BOT`), is `DISCORD_BOT_MISMATCH <why>` with exit 2 and nothing sent (`launch` prints it in its `THREAD_START_FAILED` line). `aoe` and `tmux` always run without any `DORI_*` variable, because the tmux server they may start hands its environment to every pane. The Discord commands need `DORI_DISCORD_TOKEN`, `DORI_DISCORD_GUILD`, `DORI_DISCORD_CHANNEL` (the one channel the Dori talks in) and `DORI_DISCORD_OWNER`. Every `dori.env` variable (needed or not, secret or not, what it turns on), which files stay local, and how to add another Dori on the same host: [Settings per Dori](../setups/discord-aoe/README.md#settings-per-dori).

### Backend `aoe`

With `"backend": "aoe"` lanes run as [agent-of-empires](https://github.com/njbrake/agent-of-empires) sessions instead of herdr panes. Needs `aoe` and `tmux`. What differs:

- A pane id is the session's tmux name, `aoe_<title>_<first 8 of the aoe id>`; `leadPane` and `ignorePanes` take these names. Panes are the live sessions in `aoe list` that have a tmux session; `aoe_term_*` terminals and stopped sessions are not panes. `workspace_id` is the aoe profile, so leave `workspaces` empty or list profiles.
- `launch` runs `aoe add <cwd> -t <key> --tool <agentCommand[0]> -l --extra-args "--model <model>"`, waits up to 3 minutes for the agent's `❯` prompt, then types the lane prompt. `agentCommand`'s other arguments and `laneWorkspace` are not used. aoe refuses a title+path pair that already exists, even in its trash.
- Text goes in through `dori type` (it runs `tmux send-keys -t =<name>: -l -- <text>` and a separate `Enter`, each an argv array, then checks the input box; a text over 4,000 bytes is typed as several `send-keys -l` pieces of whole characters before the one `Enter`, because tmux refuses one argument much over 16 KB); lanes report to the lead the same way, never with a raw `send-keys`. Only the agent's input box (the lines between the last two `─` borders, cut where the borders end, so senpi's FILES/TOOLS/MEMORY side panel on the same rows is not read) counts as unsent text, so the same text echoed in the transcript does not trigger extra Enters, while a paste folded into `[paste #1 +13 lines]` or a tall box whose `❯` line scrolled away does. Into a pane with a live handover quiet mark (a lane or the lead being moved), the text is also kept in `<stateDir>/handover/quiet/<pane>.typed.jsonl` and `HANDOVER_HELD <pane>` goes to stderr: a lane handover hands the lead's lines among it to the new session when it commits, and the file goes with the quiet mark.
- `close` runs `aoe session stop <id>` and `aoe rm <id>`: the session goes to the aoe trash and can be restored. It is never purged.
- The session id comes from the agent's `--session-id` argument (aoe pins one for omo when `pi` is on `aoe add`'s PATH; `launch` makes sure it is), or `--session <session file>` after an aoe restart, found under the tmux pane's pid; the environment and session-file rules follow as with herdr.
- `claim-done` without a key finds the lane by the tmux session it runs in. `guard` and `can-launch` count aoe sessions as panes.
- `watch` also reads `aoe ps --json` and the lane screens and prints `LANE_BLOCKED <key> <state> <pane>` for a working lane whose agent waits for a human (see `dori watch` below).
- `launch` reports `STARTUP_ERROR` with the agent's own message as soon as a startup error or `Pane is dead` shows while it waits for the prompt.
- PATH and node: tmux gives a new session the PATH of the client that opened it (`aoe add`), so a lane launched from a systemd unit or timer gets that unit's bare PATH, and without node senpi task's model probe and omo's hooks (`#!/usr/bin/env node`) exit 127 (GongDori's hypothesis lanes, 2026-10-26). `launch`, lane `handover` and the lead's `handover` therefore run `aoe add` with node on PATH: a caller PATH whose `node` is real is kept as it is; otherwise nvm's node, picked as `self-restart.sh` picks it (`$NVM_DIR` or `~/.nvm`: the default alias, else the newest version whose node runs), goes in front of a `node` that is only a link to bun, or at the end of PATH when there is none; a bun link with no nvm stays. With no node anywhere they refuse before `aoe add` (`NO_NODE ...`; launch exits with it, a handover prints `HANDOVER_FAIL ... NO_NODE ...` and nothing moves). `adopt` opens no session, so an adopted pane keeps its PATH.
- `launchEnv`: aoe does not hand its own environment to the session it opens; tmux copies only the variables its `update-environment` option names from the client (`aoe add`, `aoe session restart`) into a new session. So with a non-empty `launchEnv`, `launch` and lane `handover` first append each name to the global `update-environment` (once), then run `aoe add` with the values set, or, for a `--use-gpu` lane, with those names removed, and read the new session's environment back (`tmux show-environment`). A session that lacks a value gets no lane prompt (`STARTUP_ERROR ... launchEnv not in the session`), and a handover's new session is closed while the old one stays the lane (`HANDOVER_FAIL ... lacks launchEnv`). The running session of an adopted pane keeps the environment it started with. A restart makes a new tmux session from the restarting client's environment, which is why `self-restart.sh` asks `dori launch-env` first. `--use-gpu` drops every `launchEnv` variable, so keep `launchEnv` to what keeps lanes off the GPU. Limits: omo's task subagents run inside senpi's RPC host, whose environment senpi builds from a fixed allowlist (`PATH`, `HOME`, `LC_*`, `XDG_*`, `SENPI_*`/`OMO_*`/`PI_*`, proxies, API keys; senpi 2026.10.13 `host-daemon-env`), so they and the commands they run do not get `launchEnv` and still see the GPU (measured 2026-10-14: the lane's own bash `False`, its quick subagent's bash `True`); the lane's own tools and eval kernels do get it. aoe's own auto-resume after a reboot starts sessions from aoe's environment, not through dori (a lane gets `launchEnv` back at its next handover or `self-restart.sh`); emptying `launchEnv` later leaves its names in tmux `update-environment` until the tmux server restarts or `tmux set-option -gu update-environment` restores tmux's default list. Sessions start as before meanwhile, since dori and `self-restart.sh` then run aoe without those variables.

### Backend `herdr` with omo

With `"backend": "herdr"` and `agentCommand` starting with `omo`, dori drives omo in herdr panes the way it does in aoe sessions (owner card Q462, 2026-11-03: every Dori moves to herdr). What differs from aoe:

- Each session primitive picks its backend from the pane id: a herdr pane id holds `:` (`w1:p2`), a tmux session name never does (tmux refuses it). A Dori that moves to herdr keeps its open aoe lanes working, and `dori handover --lane` opens the new session in the configured backend, so a lane moves from aoe to herdr at its next handover. `leadPane` and `ignorePanes` take herdr pane ids.
- Closing a pane (`herdr tab close`, `herdr pane close`: `dori close`, the lane handover) ends every process of the pane's terminal session, not only its process tree: `nohup job &` and an orphaned `bash -c 'job &'` end with it, only a job in a session of its own (`setsid`, `systemd-run`) survives (measured on herdr 0.9.5, 2026-11-03). omo's eval kernel runs in a session of its own, which ends with the agent, and what a cell left behind goes with it. So on Linux the process table carries the session id (`ps -o sid=`) and `dori handover --lane` counts a job in the session of the pane's shell or of any process still in the pane's tree as a local chain, not as a detached job that keeps running (rollover.md, "Local chain").
- omo's state is read from its screen (the running-turn, question and wake marks), not from herdr's `agent_status`: herdr 0.9.5 has no omo rule and reads omo as idle (upstream #62/#63).
- A herdr pane is live while an agent runs in it (herdr's foreground process, else the topmost agent process under its shell), dead when only its shell is left (herdr keeps no exit status), gone when herdr has no such pane. `dori type`, `launch`'s startup check, the lane death check, `dead-panes`, `pause`/`resume`'s goal step and the watch sweeps read that, as on aoe.
- `dori type` checks a herdr omo pane as an aoe one (gone, dead or frozen pane, the `❯` prompt, pieces of at most 4,000 bytes, transcript evidence) with `herdr pane send-text` and `herdr pane send-keys <pane> enter|ctrl+u`.
- `launch` creates a tab labelled with the key (in `laneWorkspace` when set; a fresh server with no workspace gets one) and runs `agentCommand` there with its own `--session-id`; `launchEnv` reaches the agent through `env(1)` on its command line, since a pane takes the herdr server's environment, not the caller's. A handover's new session (lead or lane) opens the same way, with `--model`/`--thinking` and that new id. `close` closes the tab when the pane is all it holds, else the pane.
- A herdr server that stops ends every agent in its panes and gives back the same pane ids with fresh shells. So the lead's omo session is kept in `<stateDir>/herdr-sessions.json` (read from its running agent by `dori lead` and by `dori watch` every 10 minutes, in the order `sessions.md` gives: the session its newest child carries goes before its arguments, which keep the launch session after a `/new` or `/resume`; the model is what the session runs now, the last `model_change` / `thinking_level_change` in its log (the file omo hands its bash and eval children as `PI_SESSION_FILE`, else the one its `--session` / `--session-dir` / `sessionsDir` names, read from its arguments with their word boundaries (Linux `/proc/<pid>/cmdline`, a Windows command line), else the log recorded before for the same session; a log that cannot be read keeps the session's recorded model; on macOS, where `ps` loses the word boundaries, no log is looked for from the arguments, so only `PI_SESSION_FILE` and the recorded log are read, docs/follow-ups.md), so a `/model` or `/thinking` in the lead is kept, else its `--model`), and `dori watch`'s lead revive (`leadReviveMin`) starts that session again in the same pane (`omo --session-id <id> --model <model> --thinking <level>`, the model and level read from the session's log again at the revive, else the recorded ones) and types the revive line, without a systemd unit; `dori lead` prints `<omo session id> <pane>[ stopped]`.
- With another herdr agent (`agentCommand` not omo) the herdr path stays as upstream has it: the lane prompt on the agent's command line, bare `send-text` + `enter`, no lane death check. Right before typing, `dori type` reads the pane once more and types nothing when no agent runs in it (`PANE_DEAD`), the agent waits on a confirmation (`PANE_BLOCKED`), herdr reports it in a state other than `idle`, `working`, `blocked` or `done` (`unknown`), or `herdr pane process-info` shows an interactive shell in front of it (the agent exited or was suspended with Ctrl+Z, which herdr still reports as idle) or cannot be read or names an entry without a name. Every shell in front holds the text, whatever its arguments: `sh -c`, `bash -lc`, PowerShell `-Command` and `cmd /c` included, since a command line proves nothing about who reads the input (upstream dori-superagent #69 lets a shell running a command through; here the agent gets the text once that child has ended, and the lead sees `NOT_SUBMITTED` until then). An omo pane gets its own checks above instead (a suspended omo is a stopped agent there).

Hooks are argv templates for your messenger CLI. `{thread}`, `{text}` and `{key}` are filled into each argument separately, so the text stays one argument whatever it contains.

## Commands

### `dori update [--pull] [--dry-run]`

Applies the clone's current HEAD. `--pull` first runs `git -C <update.repo> pull --ff-only`. The first run saves HEAD and sorted known dotted config keys to `<stateDir>/update.json`, prints and logs `UPDATED first-run`, and restarts and announces nothing. If HEAD equals the saved `applied` SHA, it prints `UP_TO_DATE` without writing a watch-log line.

Only `update.branch` is applied. When the clone is on another branch or a detached HEAD (a lane switched branches or checked out an old commit in it, which also starts the path unit), the run prints and logs one `UPDATE_SKIPPED off-main <branch|detached> at <sha7>: only <branch> is applied` line before any pull, and restarts, announces and records nothing. When HEAD is an ancestor of the applied SHA (the branch moved back), it prints and logs `UPDATE_SKIPPED behind <sha7> is an ancestor of applied <sha7>` the same way, so services never go back to older code. Back on the branch, the next run applies its HEAD as usual.

One update runs at a time per `stateDir`: a run first takes `<stateDir>/update.lock` (its pid and start time) and removes it when done, and a second run (a manual `dori update --pull` moves the branch ref, so the path unit starts one at the same moment) waits for it before it pulls or reads HEAD. If the run it waited for already applied that HEAD, it prints and logs one `UPDATE_SKIP <sha7> already applied by the dori update this run waited for` line and restarts and announces nothing; a newer HEAD is applied as usual, so no commit is missed. A lock whose pid is gone is taken over; one still held after `readyTimeoutSec` x services + 300 seconds ends the run with `UPDATE_FAIL update lock: another dori update is running (pid ...)`.

On a new HEAD it diffs the saved SHA against HEAD. Every service with a matching `update.services.paths` prefix is restarted once. It notes the service log's byte size before restarting and waits only for a new complete line matching `ready`, not an old ready line. With an empty `ready`, it checks user-unit activity instead. Each attempt prints and logs `RESTARTED <unit> <sha7>` or `RESTART_FAIL <unit> <reason>`; it attempts every affected service and then records the HEAD even when readiness failed. `UPDATED <old7>..<new7> changed=<n> restarted=<units>` lists successful restarts.

Keys this code knows but the saved code did not, and which are not set in the raw config file, print and log `CONFIG_NEW_KEY <key> unset in <config path> (default used)`. The known keys are saved for the next run. A restart failure sends `[ALERT] dori update: RESTART_FAIL ...` to `update.alertPane`, including new-key notices; without a restart failure the key notices do not trigger an alert. Git failures (including rejected pulls) print and log `UPDATE_FAIL` with stderr and alert the same pane, preserving the previously applied SHA.

After restarts, one `[UPDATE]` summary goes to `leadPane` (`DORI_LEAD_PANE` overrides it). It contains merged PR titles from old..new (or commit subjects if there are no merges), changed `references/`, `SKILL.md`, and `setups/**/README.md` paths under this skill, new config keys, restart results, and `update.announce` (`update.maintainerAnnounce` when `update.maintainer` is true). So an update is not repeated to the owner by every Dori: the other leads only take it in, and the maintenance Dori tells the owner once after every Dori runs it (owner 2026-11-03, ledger `update-notice-once`). Delivery prints and logs `ANNOUNCED <pane>` only after the pane-send helper saw the text submitted (see `dori type`), else `ANNOUNCE_FAIL <pane> <reason>` next to the helper's `NOT_SUBMITTED` line. A missing lead pane logs `ANNOUNCE_FAIL` without sending anything. Alerts and announcements use the same argv pane-send helper as lanes.

`--dry-run` prints planned local changes and restarts with a `DRY_RUN` prefix; it does not pull, restart, send, or write state/watch logs. A failed update/restart exits 1. The generic systemd path unit can run `dori update` after a pull; see the Discord + aoe setup.

### `dori notify-change --summary TEXT [--file PATH ...]`

Sends one `[UPDATE]` message containing the supplied summary and changed guidance paths, followed by `update.announce` (also on the maintenance Dori: this is one Dori's own change, not a shared update), to `leadPane`. Use it when a Dori's own memory or AGENTS guidance changes outside the script clone. Prints and logs `ANNOUNCED <pane>` or `ANNOUNCE_FAIL <pane> <reason>`; failed delivery exits 1.

### `dori handover [--note FILE] [--title T] [--model M] [--keep-old] [--no-monitors] [--minutes N] [--dry-run]`

The inbox probe carries `scope:"channel"` and `kind:"handover-probe"`, so monitors accepting ordinary channel rows also receive the check. The setup README's default inbox filter (`^\{`) accepts every JSON row.

Lead handover also retargets `update.alertPane` in each config listed in the handing-over Dori's `instances`, only when it equals the old lead pane. A targeted value replacement preserves formatting and every other key, and the resulting JSON is parsed before writing. Each changed file is backed up as `.bak-handover-<stamp>` and emits `HANDOVER_ALERTPANE <config> <old> -> <new>`. Verification failure reverses those changes through the same repoint path; files already targeting another pane, including the new lead, stay untouched.

Moves the lead to a new agent session when its conversation got long (backend `aoe`). In order:

1. **Note.** Writes `<stateDir>/handover/<stamp>.md` (and `.json`): the open lanes with status, pane, thread and last report; every monitor the old session still runs, persistent or not, read from omo's manifest `<sessionsDir>/--<cwd>--/extensions/terminal/<session id>.json` (a monitor whose recorded process is gone is left out; the new session re-arms each one as persistent, except a path watch marked `ENDED`: its folder is gone, so omo refuses it, or it waits for its file to be created and the file is already there); the configured `handover.watchers`; open question cards; the old session's unfinished todos and goal; the open `dori worklog` items, one `OPEN <id> "<title>" source="<ref>" next="<next step>"` line each under "Open worklog items" with any `WORKLOG damaged` / `warning` / `unreadable` line (never a refusal; `HANDOVER_NOTE` counts them as `open worklog items`); timers matching `handover.timers`; the owner's messages of the last 24 hours in the inbox (all of them, rows whose author is `DORI_DISCORD_OWNER` or `DORI_KAKAO_OWNER_ID`; until 2026-11-09 the newest 8, which cut 56 of the owner's 64 messages from ZzangDori's lead handover 20261106-213407), and the owner's words another Dori relayed in the pair room in that time (a `pair-bot` row saying 원문, as `relayed in the pair room by <bot id> (message <id>), the owner's original <link>` with the whole relay: a short quote or the words around it can be the order); the path of the old session's log; the quotes in the messages the old lead got that neither its summary nor those owner messages hold ("Quotes in the old conversation", the newest 60, `owner's words` only with proof as in the audit below, else `lead's words`; the audit then counts them carried); and the file given with `--note`, the old lead's summary under the headings `dori handover --template` prints (Owner's words and constraints, quoted exactly; Decisions and why; Promised follow-ups; In progress; Next step; a `--note` without them is refused). It refuses (`HANDOVER_REFUSED`, exit 2, nothing changed) when `leadPane` has no live aoe session, when `DORI_LEAD_PANE` is set in the environment (it overrides the config file, so lanes would keep reporting to the old pane; drop it, also from a wrapper script that exports it), when another handover holds `<stateDir>/handover/lock` and its process is alive, when a `handover.watchers` check fails for the old lead (`configured watchers not running`; `--no-monitors` does not skip it), or when neither a running monitor nor a configured watcher was found (the line names the manifest it read, or says the omo session could not be told; `--no-monitors` hands over without them). The session id comes from omo's `--session-id <id>` or `--session <session file>` argument (the uuid at the end of the file name), else a child's `PI_SESSION_ID`, else the session file made at start. When the old lead's path is a symlink it prints `HANDOVER_CWD_SYMLINK <path>, a symlink to <real path>; the new session opens in <cwd>`.
2. **New session.** Opens `aoe add <cwd> -t <title>` (`handover.cwd`, else the old lead's path with symlinks resolved), waits for the prompt, tells the old lead to stay quiet, and types `handover.prompt` plus "read the handover note at <path>". The note tells the new session to re-arm every monitor, to start each watcher whose `arm` says how, to answer `HANDOVER_PROBE <id>` lines with `dori handover ack <id>`, and to answer the audit's `HANDOVER_SUPPLEMENT` lines (step 4).
3. **Repoint.** `leadPane` in the config file (and `update.alertPane` if it named the old lead), `DORI_LEAD_TMUX` and `DORI_LEAD_AOE_ID` in `dori.env`, added when the file lacks them (each file backed up as `.bak-handover-<stamp>`), every open lane's brief footer (the old pane name replaced) plus a `[LEAD]` message with the new report command, and open question cards whose `tmux` was the old lead. Then it restarts `handover.services`, because `dori watch`, `freshness` and `dead-panes` read `leadPane` once at start. Lines: `HANDOVER_CONFIG`, `HANDOVER_ENV`, `HANDOVER_LANE <key> brief=rewritten|unchanged|missing told=yes|no`, `HANDOVER_CARDS`, `HANDOVER_RESTARTED`. A lane that did not take the `[LEAD]` message (`told=no (freshness retries it)`) waits in `<stateDir>/handover/lane-tells.json`: each `dori freshness` tick counts it told once the lane's transcript has the message (omo held a copy and delivered it later), types it again only while a turn runs in the lane (a text typed while its main turn waits on its children stays in omo's input queue), and prints `HANDOVER_LANE_TOLD <key> <pane>: ...`; after 20 minutes without it the lead gets one `[DORI] HANDOVER_LANE_UNTOLD <key>: ...` line with what to do (`HANDOVER_LANE_UNTOLD` in the watch log). A lane closed or moved to a new session drops its wait.
4. **Checks**, within `--minutes` (default `handover.verifyMin`): every monitor of the old session runs in the new one (same command as the shell reads it, quotes and backslashes resolved, in an ssh remote command or a bash -c string too, and the same filter, or same path; the description only for a monitor with neither; a monitor whose command starts work, marked `LAUNCHES_WORK` in the note, by a watch-only one with its description or filter instead, never by its own command again; a path watch that has ended, marked `ENDED` in the note or whose create event has fired since (its file is there), is not checked; persistent, not suspended, its process alive; the new session's manifest is read under the new cwd), `HANDOVER_MONITORS_OK`; every open todo of the old session is in the new session's todo list (the note's step 1 has it put them there before the commit; its words without phase and status, in any task of the list, done or not; read from the new session's log under the new cwd), `HANDOVER_TODOS_OK`, a missing one `todos not in the todo list of <pane>: ...` rolls the move back as a missing monitor does, and the list is read again just before the commit with the monitors (`todos left the todo list of <pane> after the first check: ...`), since a new session can put them in and then write its list anew (since 2026-11-09: in ZzangDori's audit of 11-02..08 five todos were in the note but not in the new sessions' own lists, and only the audit after the commit found them); a missing one is listed with why (armed but ended, armed with another command or filter and where it differs, or not armed); the monitors are checked once more after the probes, just before the commit, and one that ended in between rolls the move back (`monitors stopped in <pane> after the first check`); every `handover.watchers` check exits 0 with the new pane and session filled in, `HANDOVER_WATCHERS_OK`; a freshly loaded config routes reports to the new pane; then a `[REPORT] handover-probe ... HANDOVER_PROBE <id>` line typed into the pane the config names, and a `{"kind":"handover-probe"}` line appended to the inbox file, are both acked by `dori handover ack <id> --state <stateDir>` run from the new pane; no restatement is asked before the commit (owner Q476, 2026-11-03: the note carries the records and the owner's words word for word, and the audit after the commit checks what the new lead holds). The probe line carries `--state`, so a Dori whose `dori` wrapper sets another state dir acks into the right one. An ack from any other pane (the old lead also sees the inbox) does not count.
5. **Freeze.** Only when every check passed: the old lead's agent and every process under it get SIGSTOP (`HANDOVER_OLD_FROZEN <pane> agent <pid>: N processes stopped (...)`), so it uses no tokens and does nothing; no signal of a freeze, a thaw or a resume goes to pid 0, 1 or -1, a non-integer, dori's own process or its own process group (`kill(0)` stops the caller's whole group: a pid 0 in a QA frozen record stopped handover-simplify's omo on 2026-11-04 for two hours with no record); such a target prints `SIGNAL_REFUSED <sig> <pid>: <why>` on stderr and counts as not sent; a monitor that started work (`LAUNCHES_WORK`) is left running with everything under it while that work runs (`HANDOVER_WORK_KEPT <pane>: ...`), and the record's `keepFor` names the work's pids; its pane and its conversation log (JSONL) stay, a record goes to `<stateDir>/handover/frozen/<pane>.json`, then `HANDOVER_DONE` and the new lead gets `[LEAD] HANDOVER_COMMITTED`. After the commit (here and in a lane's handover, closed, frozen or kept), the old session's own tasks still open in their senpi record with their `host_pid` alive (a task in the frozen old agent is left: it is stopped with it) are ended through the new session: `[LEAD] HANDOVER_TASKS_CANCEL <id>: ... End each one with task_cancel (task_id ...)`, acked like a probe (`handover.ts` `endStrayTasks`, up to 3 minutes); the records are read again, the note gets "Background tasks of the old session ended at the handover" (id, what it was asked, status, record), and the watch log `HANDOVER_TASKS_CANCELLED <key|lead> <id> "<what>" -> <note>` `HANDOVER_TASKS_ENDED <key|lead> <id> <status>` for one that finished by itself before the request, or, for one still open, `HANDOVER_TASK_ALIVE <key|lead> <ids>: <why>`. A task whose record already says completed is not asked about: another session's `task_cancel` leaves it as it is. It is closed as soon as the audit after the commit passed, else `handover.frozenCloseH` hours later (below); with `--keep-old` (or `handover.frozenCloseH` 0) it stays frozen until closed by hand, a passed audit included (`HANDOVER_OLD_KEPT_FROZEN <pane>: the audit passed, but it is kept until it is closed by hand ...`). Before the commit the old lead is only told to stay quiet (the quiet mark), and a rolled-back move stops nothing. When nothing can be stopped (no agent under the pane, the signal refused) it prints `HANDOVER_FREEZE_FAIL`, resumes what it stopped and closes the old session as before (`HANDOVER_CLOSED`; with `--keep-old` it stays open and is told it is no longer the lead). A failed check prints `HANDOVER_VERIFY_FAIL <reasons>`, runs step 3 the other way round (config, env, lanes, cards back to the old lead, services restarted), tells the old lead it stays the lead, leaves the new session open to look at (`HANDOVER_ROLLED_BACK`) and exits 3.

A real run (lead or `--lane`) needs `--approved-by` (rules in `references/rollover.md`). The lead's own decision is `lead:<reason and the signal behind it>` (a STUCK rung, an intent-check finding, a measured threshold), or, when the owner asked for the move ("open this lane with model X"), `lead:<reason>, owner <message id>` or `lead:<reason>, owner <link to the message>` (`형` works for `owner`). The cited message has to be in the inbox (`handover.inbox`, else `DORI_DISCORD_INBOX`) with `author_id` one of `DORI_DISCORD_OWNER` / `DORI_KAKAO_OWNER_ID`, and in the link's channel; a made-up id, another author's message, a link into another channel, a fake id next to a real signal, or no owner id set up is refused (`HANDOVER_REFUSED ... cites the owner, but ...`). Every other check runs as before, and the owner is told afterwards as for any lead decision. A `lead:<reason>` with no signal and no owner citation gets the measured signal of that session added from the records (stuck rung, crossed threshold, last proposal), printed as `HANDOVER_APPROVAL_FILLED` and logged filled; with nothing measured it is refused as before (rollover.md, "The rule").

The owner's answer on a question card counts as his message: the listener writes a `kind: "answer"` inbox row only for a tap or typed answer by `DORI_DISCORD_OWNER` (`discord-cards.ts` `handle` answers anyone else with `ownerOnly` and records nothing), so `lead:<reason>, owner <answer id>`, `owner <link to it>` or `owner Qn <id or link>` (the card named: the row must be that card's answer) passes; a link's channel is the card's thread. A bare link as `--approved-by` is checked the same way (the inbox has it from the owner, his message or card answer), not by its shape alone. `--dry-run` with `--approved-by` checks it too: `HANDOVER_APPROVAL_OK <ref>`, or the refusal, with nothing written to the rollover log.

**One waiting handover per lane.** A lane run approved by the lead or the owner that is refused because the lane is busy (blocked `busy` or `work`) does not end there: it prints `HANDOVER_PENDING <key>: ...` after the refusal, asks the lane for its safe point (the same `[LEAD]` request an automatic rollover sends, starting `The lead moves <key> to a new session`), and `freshness` starts the same request again by itself (busy: at its next sweep, the run waits for the idle moment; work: once the lane marks ready or the named chains and tasks ended), once per refusal and never given up (`HANDOVER_READY_RESUMED`; still waiting after `handover.readyMin`: `HANDOVER_PENDING_STALE`, the lead told once). While it waits, `freshness` starts no automatic rollover of that lane, and an automatic run's refusal logged after it does not replace it; an automatic run already started gives way under the lane's lock (`HANDOVER_YIELDED`). The start again carries `--request-at <time> --request-pane <pane>`, and under the lock the run moves only while that request still waits in that pane (`HANDOVER_REQUEST_GONE` otherwise: a `--force` finished it meanwhile, nothing is moved twice). A run that finds the lane's lock held by a live run (`<key>.lock`) leaves its request (approval, `--force`) in `<key>.takeover-<pid>-<id>.json` instead of refusing: a run waiting for the lane's idle moment steps aside at its next look (`HANDOVER_STEPPED_ASIDE`, exit 2, no rollover row) and the leaving run goes on to move the lane itself (`HANDOVER_TAKEN_OVER <key>: ... this run moves the lane`), with its own result and exit code. A holder that is moving the lane (its lock, or its pending journal `<key>.pending.json`) takes nothing within 15 s: the request is withdrawn and the run is refused as before, without a rollover row, so the lane's waiting request stays its last and outlives that holder dying mid-move. A run takes the lock before it writes anything others read (the handover note and its facts, one pair per run even in the same second), and once locked reads the lane again: a run beside it that locked first leaves it nothing written, and it goes the takeover way instead. Once the holder is gone the run starts over (an interrupted move it left is repaired first, `HANDOVER_INTERRUPTED`, under the lane's lock with the journal read again there, so a repair never runs beside another run's; `freshness` repairs nothing itself); a lane whose pane changed while the run waited (another run that waited beside it moved the lane first) is not moved again: `HANDOVER_ALREADY_MOVED <key>: ...`, exit 0. A run keeps the pane it first found through every wait, however often it waits. No run is reserved as the one that goes on (lead, 2026-11-03: the waiting run steps aside and the forcing run starts over from the top): when two forcing runs wait at once, the first to take the lock moves the lane with its options and the other ends with `HANDOVER_ALREADY_MOVED`, or, when it asked for the other choice of keeping the old session, with `HANDOVER_CONFLICT <key>: ... by a run that kept|closed the old session; this request asked to keep|close it and is not moved again` (exit 2), so a request that did not get what it asked for never reads as done. A waiting run that was started by `freshness` and died without writing another rollover row (no lock, no row) is started again by the next sweep once 2 minutes have passed, with no new ready mark needed: the decided request goes on by itself. A lead note that did not reach the lead is sent again on the next sweep; `HANDOVER_PENDING_STALE` comes for busy and work refusals alike. The refused row keeps the safe-point ask (`safePoint`: what it was for, and whether the pane took it); an ask the pane did not take (a herdr question open) is typed again by each sweep until it is, once per request (`HANDOVER_SAFE_POINT_ASKED`, `<key>.safe-point.json`). A later refusal of the same request (the resumed run, which asks nothing itself) carries an ask not yet delivered, so the asking goes on until the pane takes it; a backtick or `$(` in the quoted command lines is written as `'` and `$ (`, since no text holding them is typed into a pane, and a text a pane refuses is a failed delivery for the next sweep, never an error that stops the sweep.

Every line also goes to `watchLog` with source `handover`, and the outcome to `<stateDir>/handover/<stamp>.result.json`. Run from inside the lead's own tmux session, it re-runs itself as a `systemd-run --user` unit (`HANDOVER_DETACHED unit=... log=<stateDir>/handover/run.log`), because freezing the old lead stops every process under its agent (and closing it ends every process in it); with `--keep-old` too. `--dry-run` writes the note and prints the plan (`HANDOVER_DRY_RUN`) without opening or moving anything.

After verification succeeds and the switch commits, before freezing the old lead, handover ends the old manifest's re-armed command monitor trees under its agent. Each monitor process group gets SIGTERM, then SIGKILL if still alive after 250 ms, with another 250 ms to exit: `HANDOVER_OLD_MONITORS_ENDED <n> (<pids>)`. A failure emits `HANDOVER_OLD_MONITORS_END_FAIL ...; freezing what remains` and the freeze still proceeds. This releases locks, ports and single-reader resources instead of leaving their owners stopped. Monitors whose launched work must continue are left running; a lane kept frozen for such work ends its other re-armed monitors the same way (the normal lane close already ends its chains). Thaw resumes the old agent but does not restore ended monitors: their replacements belong to the new session.

A frozen pane reads nothing, so `dori type` (and every script that types into a pane) sends a text for a pane that has a frozen record to the session that replaced it, followed through later handovers: `FORWARDED <old> -> <new>` on stderr and in the watch log, then `SUBMITTED <new>`. A late report a lane types into the old lead reaches the live one. A frozen session closed before its close time (the audit passed, or closed by hand) keeps forwarding until that close time (`<stateDir>/handover/forward/<pane>.json`, written before the first close attempt so a failed close and its retry keep it, removed by the first tick after that time or by a thaw), so a lane told of the lead change only by the 20-minute escalation still reaches the new lead.

`dori handover frozen` lists the frozen old leads (`FROZEN <pane> since ... (agent, processes, close time, the lead that replaced it, its log)`). `dori handover thaw <pane>` resumes one frozen by mistake, children first and the agent last, and forgets its record (`HANDOVER_OLD_THAWED <pane>: n/m processes resumed`); it is still not the lead (the lead's pane is `leadPane`), so tell it what to do. `dori handover close-frozen [<pane>]` closes that one, or without a pane every one whose close time passed: resumed first (a stopped process does not act on the hangup), then `aoe session stop` and `aoe rm` (`HANDOVER_OLD_CLOSED ...; its log stays at <path>`); its log is never deleted. A close that fails or throws after the resume stops it again, so the old and the new lead never both run, and keeps its record (`HANDOVER_OLD_CLOSE_FAIL <pane>: <why>; stopped again (n/m processes), ...`); one the clock closes (it has a close time, the audit's early close included) is due again at once, so the next freshness tick tries again, and one kept by hand waits for the next `dori handover close-frozen <pane>`. A record with `keepFor` (the work a monitor of the old session started, lead or lane) waits for that work instead of its close time: `dori handover frozen` shows `closes once the work its monitors started ends (<pids>)`, and the first tick after every one of those pids ended closes it (`HANDOVER_OLD_CLOSED ... (the work its monitors started ended: <pids>)`); `close-frozen <pane>` closes it now and ends that work. A lane's handover whose old session runs such work freezes that session in the same way instead of closing it (`HANDOVER_WORK_KEPT <key> <pane>: ...`, `HANDOVER_DONE ...; old session kept until the work its monitors started ends`, result `done-frozen`), its local chains left running too, and tells the new session that the work runs on and closes by itself. `dori freshness` runs the same close every tick, so a frozen lead whose audit did not pass is closed `handover.frozenCloseH` hours after its handover; one whose audit passed was already closed by the audit (`HANDOVER_OLD_CLOSED ... (the audit after the handover passed)`, else `HANDOVER_OLD_KEPT_FROZEN <pane>: ...`). `dori sync` and `dori dead-panes` skip frozen panes. Every freeze and thaw goes through one signal path that keeps the agent its tty's foreground job: an agent typed into a pane's interactive shell is stopped with that shell stopped first, only once the shell reads stopped (a SIGSTOP lands asynchronously; a shell not stopped within 1 s is resumed and the freeze fails with `SIGNAL_REFUSED`), and resumed with the shell resumed last, so bash never sees its job stop, never takes the tty back and never cooks it (without that, a thawed omo ran on as a background job and stopped again on the next key). Each thaw that leaves the agent running (`dori handover thaw`, a rollback, a failed open or freeze, an interrupted run repaired, a slipped-in turn) then checks it is the running foreground job, continuing it or giving its tty raw mode back without typing anything (`AGENT_RESUMED` / `AGENT_RESUME_FAIL` after `HANDOVER_THAWED` / `HANDOVER_OLD_THAWED`).

`dori handover --template` prints the headings of the old lead's summary. `dori handover ack <id> [--state DIR]` records the pane it runs in for that probe or supplement id under `<DIR or stateDir>/handover/acks/` (`HANDOVER_ACK <id> pane=<pane>`).

### `dori handover audit <note.md|key|lead> [--dry-run] [--no-send] [--force]` / `dori handover gap <key|lead> --kind K --text T [--fixed]` / `dori handover audit-summary [--days N] [--send]`

The audit after a committed handover (lane or lead), `rollover-audit.ts`; [rollover.md](rollover.md) "After the commit: the audit ledger" has the why. `dori freshness` starts it by itself `handover.auditAfterMin` minutes after a handover's `result.json` says it was committed (`done`, `done-frozen`, `done-kept-old`, `kept-new-old-gone`), for handovers at most `handover.auditWindowH` hours old, once each (`<note>.audit.json` marks it queued, started, done; `ROLLOVER_AUDIT <key> <stamp>: started unit=dori-handover-audit-...` in the freshness output, the run in `<stateDir>/handover/run.log`). By hand it takes the note, or a lane key (or `lead`) for that one's latest committed handover; a done audit is not run again without `--force`.

It reads the old session's log (user messages only) for quotes the lead put next to `형`, `owner` or `오너` (commands, paths and short words are skipped). Such a quote is `owner's words` only with proof: a message id or Discord link next to it that the inbox (`handover.inbox`, `DORI_DISCORD_INBOX`) holds as written by `DORI_DISCORD_OWNER` (or `DORI_KAKAO_OWNER_ID`), or a question card `Qn` before it that is answered; what the lead told him (`형에게 ...라고 했어`) and every quote without proof is `lead's words`. For a lane it also reads the lead's `[LEAD]` instructions of the last `handover.auditLeadH` hours, judged on their own words without the quotes and ids in them (a bare relay is none; nudges, handover and check lines and the directive top-up are left out). An item counts as carried when its text is in the brief, the handover note, the restatement (`<stamp>.understood.md`: before owner Q476, or what an audit round added), a `.md` file any of those names, the cwd's `AGENTS.md` or `CLAUDE.md`, or the directive ledger's words for that lane (a quote by its first 80 characters, an instruction by half its words). What is left is sorted by a reviewer model (`reviewers.first`, `reviewers.models` and `reviewers.command`, another family than the session's): `STANDING HIGH|MEDIUM|LOW`, `CARRIED` (it holds, but the new session has it in other words: the reviewer reads its restatement, its brief and the ledger's rules too), `DONE` or `CHATTER`; only standing items are gaps (`HANDOVER_AUDIT_UNSORTED` and no row when no reviewer answers). It also checks the old session's open todos against the new session's todo list (done ones count) and restatement, its goal (the new session registered one), its monitors (the new manifest has the same command or path, ended ones included) and, for a lane with a restatement written before owner Q476, the summary's decisions and the tried fixes against it. It prints what it cost, `HANDOVER_AUDIT_COST <key> <stamp>: <s> s, <n> model call(s), ~<t> tokens (estimated from the text size)`, and for a lead handover closes the frozen old lead when it passed.

Each gap is one line in `<stateDir>/handover/audit.jsonl`: `{at, lane, who, handover, stage: "audit", kind, text, source, fixed, risk?, note}` (`text` at most 160 characters, token-shaped strings and `password=`/`token:`-style values masked). The items the supplement rounds before the commit filled in are recorded too (`stage: "supplement"`, `fixed: true`). Gaps of risk HIGH or MEDIUM, and every todo, goal and monitor gap, go to the new session once through the handover's supplement path (`[LEAD] HANDOVER_SUPPLEMENT <id> (round 1/1)`, file `<stamp>.audit-supplement-1.md`, the same ack), with the request to write what only the conversation held into its `AGENTS.md` or memory; `fixed` is the check after its ack (it gets 10 minutes, since it keeps working meanwhile). LOW ones are recorded only. Nothing left out: no line (`HANDOVER_AUDIT_OK <key> <stamp>: nothing left out`), else `HANDOVER_AUDIT <key> <stamp>: N left out (kinds); fixed F, sent <file>; conversation-only items C: standing S, carried K, done D, chatter X [model]`. `--dry-run` prints the rows (`AUDIT_ROW {...}`) and writes and sends nothing; `--no-send` records without sending.

`dori handover gap <key|lead> --kind K --text T` records what a session found later that it did not know (`stage: "reported"`, the latest handover of that key, `by` the lane when run in its own pane, else the lead; `--fixed` when it is already put right) and prints and logs `HANDOVER_GAP <key> <kind>: <text> (by ..., after the handover <stamp>)`. Both handover notes tell the new session about it. Since the first weekly summary (owner's words the most lost kind), a lane handover note also carries the owner's own messages since the lane's last handover, from the inbox (`rollover.ts` `ownerMessagesFor`: rows written by `DORI_DISCORD_OWNER` / `DORI_KAKAO_OWNER_ID` in the lane's `discord:` thread or cited by id in the old conversation, with id and link when `DORI_DISCORD_GUILD` is set, at most 40).

`dori handover audit-summary` prints the summary of the last `--days` (7): handovers and how many were audited, rows by stage, fixed or not, the most frequent kinds and lanes. `--send`, and `dori freshness` at the first sweep after `handover.auditSummaryAt` (`Mon 08:30` in `scorecard.timeZone`) each week, append it to the lead's inbox (`handover.inbox`, `DORI_DISCORD_INBOX`, else `<stateDir>/discord/inbox.jsonl`) as one row `{"kind":"rollover-audit","id":"rollover-audit-<week>","content":"[ROLLOVER_AUDIT] ..."}`, never to the owner's channel, and log `ROLLOVER_AUDIT_WEEKLY`; `<stateDir>/handover/audit-weekly.json` holds the week sent.

### `dori launch <key> --title T --brief FILE --done "..." --thread REF|new | --no-thread "<reason>" [--model M] [--cwd DIR] [--tag T ...] [--done-weak-ok] [--goal G] [--challenge-before STEP ...] [--use-gpu] [--ui] [--dry-run]`
Opens a lane: appends the footer to the brief, opens a tab, starts the agent, and checks the pane for startup errors after 20 seconds. Exit 3 on `STARTUP_ERROR`. A failure word (rate limit, quota, usage limit, No API key, ...) counts only on one of the agent's own error lines: `Error: ...` (or bun's `error: ...`), `The <provider> account usage limit has been reached`, `All <name> accounts for <provider> are currently blocked`, or tmux's `Pane is dead`, at most one space in and above the `❯` input box. Prose that only starts with such a word does not count. It does not count while a turn runs, or once the newest model reply in the lane's own session, written since this launch began, ended without an error; a resumed session's older replies do not count. A lane that quotes a log, its brief, or a file, and the status lines under the box (session title, goal, account usage bars), therefore never reads as `STARTUP_ERROR` (dori-superagent PR #51 review, reproduced here (MIT)). An agent with no API key, which keeps the prompt in its box, is reported as `STARTUP_ERROR ...: No API key`, not as an unsent prompt. With backend `aoe` no failure word is not enough: `STARTUP_OK` needs the session still running and its agent showing a running turn, a wake mark or its `❯` input line; a session that ended is `STARTUP_ERROR`, and a screen with none of these (a trust dialog, a crash dump, a blank pane) is `STARTUP_UNCONFIRMED <key> <pane>: ...; last lines: <its last 3 lines>`, also exit 3: look at the pane before relaunching, since the lane may still be starting (ported from dori-superagent [40034ad](https://github.com/sisyphuslabs/dori-superagent/commit/40034ad1a557b92a34aa1450565adcafd3352c96), MIT). A running agent is still not a good start without its goal, since a lane that never sets one does its first turn and stops: on both backends `STARTUP_OK` also needs omo's goal store (the file `dori pause`/`dori resume` read, `<session dir>/extensions/goal/<session id>.json`) to hold a goal for the exact session the lane's agent runs under, read from the agent's command line once its prompt shows: with backend `aoe` the `--session-id` aoe pinned (a restart resumes it with `--session <that session file>`, the same id), with `herdr` the `--session-id <new id>` launch puts after the program when `agentCommand` runs `omo` and names no session itself (`--session`, `--session-id`, `--continue`/`-c`, `--resume`/`-r`, `--fork`, `--rebind`, `--no-session`); any other command runs as it is. Only an exact id counts: `--session-id <id>`, `--session <session file>` or a whole uuid, never a partial uuid omo resolves itself, and a command with its own `--session-dir` keeps its goals outside `sessionsDir`, so neither is read. The goal file is read under the lane's cwd or its real path, and the id goes into the registry (`session`, `sessionVia: launch`). No session is inferred, so a sibling lane in the same directory, a lead that quoted the prompt, or another Dori instance's launch of the same key never lends its goal. That goal record reads the same at any pane width, while omo cuts its `Pursuing goal` footer to the pane's (a ~31-column pane shows `Pur...`), so the goal is never read from the footer (dori-superagent [issue #122](https://github.com/sisyphuslabs/dori-superagent/issues/122), fixed by [PR #123](https://github.com/sisyphuslabs/dori-superagent/pull/123), MIT). launch never adds `--session-id` to aoe's `--extra-args`: aoe then refuses every restart of the session (`already contains native session selector`). aoe pins an omo session only when a `pi` command is on the PATH `aoe add` runs with, so a PATH without one (a systemd unit's) gets the `node_modules/.bin` holding the `pi` of the agent's own install at its end. An agent whose command line names no session id is `STARTUP_UNCONFIRMED <key> <pane>: the agent runs but its command line names no session id, so its goal cannot be read; last lines: ...` (exit 3): look at the pane. The agent is read before its goal every time, so a goal an agent left as it ended is no start either. Launch never waits out a first turn: a ulw lane reads its brief and runs a discovery wave before it sets its goal (on 213 real lanes, 2026-11-02, 81% set it later than 80 s; 201 before their first turn ended, median 146 s, p90 260 s, p99 849 s, longest 1383 s; 11 only after a user's nudge; one after a 19 s idle gap), and waiting that long would hold up the lead's launch and the backlog pass. Right after the 20 s check a goal is `STARTUP_OK`; a first turn still on, its turn running (`esc to interrupt` on the input box) or the agent waiting on a background job of its own (an eval or bash the harness detached, a task, a monitor: the jobs `dori watch` already reads for blocked lanes), is `STARTUP_PENDING_GOAL <key> <pane>: its first turn is still on and has set no goal yet; ...` (exit 0), and the lane's record gets `pendingGoal`, which `dori watch` finishes (see `dori watch`); an idle turn is read again every 10 s, and three idle reads in a row with no goal (so a gap between tool calls does not count) are `STARTUP_NO_GOAL <key> <pane>: the agent runs but no goal in its session: its first turn ended <n> s after its prompt; last lines: ...` (or `no goal found for its session` when that session's transcript is not there yet) (`<n>` is read from the clock, so on a loaded host it gives the real wait, not the planned 40 s; dori-superagent PR #83, https://github.com/sisyphuslabs/dori-superagent/pull/83), exit 3: look at the pane and tell the lane to set its goal. An agent that ends (aoe: its tmux session; herdr: no agent under the pane) or shows a startup failure is `STARTUP_ERROR`. So the goal check adds at most 20 s to the launch (dori-superagent [issue #50](https://github.com/sisyphuslabs/dori-superagent/issues/50) reproduced here, MIT). With backend `aoe` the session starts with `launchEnv`; `--use-gpu` (a lane that needs the GPU, e.g. a training run) starts it without, and the lane keeps `useGpu: true` in the registry so its handovers and restarts do the same.

A lane runs its lead's model: without `--model` it starts on the model and thinking level the lead runs now (`<provider>/<model>:<level>`, the `model` of the lead pane's entry in `<stateDir>/herdr-sessions.json`, which `dori lead` and `dori watch` read again after a `/model`), and every later `dori handover --lane` (by hand or automatic) starts it on the lead's model of then, so a lead moved to another model takes its lanes along at their next move. On herdr, `launch` first reads the configured current lead pane's session transcript again (so a `/model` since the last record counts, and a failed read leaves the record as it was); if neither the transcript nor the record yields a model, it stops with `LAUNCH_LEAD_MODEL_MISSING <pane>` before writing the brief, opening a thread or tab, or registering a lane, never silently using `defaultModel`. A model-less session-record rewrite keeps the pane's last known model. Only the session log (its last `model_change`, so a `/model` counts) or this same session's record name the lead's model: when only the agent's startup `--model` tells it, the record keeps it as `modelFrom: "argv"` for a revive, and no lane follows it (launch stops as above). The record's `modelAt` is when the model was last read: reads that only see the session (an owner row's lead-limit check) move `at` but not `modelAt`, and `dori watch` reads the lead's model again 10 minutes after `modelAt`. The backlog resolves that model once per start, checks the quota of its provider (a missing one holds the start with `LAUNCH_LEAD_MODEL_MISSING`), and launches on that same model. The level goes to omo as its own `--thinking`. The registry's `model` names what the lane's session runs after each move, and an interrupted move that `recover` sends back to the old pane gives it back its old model. `--model` (on `launch` or on `handover --lane`) chooses the lane's own model instead: the registry keeps `modelPinned: true` and later moves keep that model.

The first message carries what a compaction must keep of the task, on one line after the brief instruction: `Keep these word for word through every context compaction, and after a compaction re-read the brief at <brief> before your next step: [목표] ... | Done = ... | Owner's words: "..."` (the brief's `[목표]` or `[Goal]` line, the Done line, `--goal`; each cut at 1,200 characters with a pointer to the brief; backticks become `'`). omo's compaction summary quotes the user's requests word for word and keeps them through later compactions (its "User Requests (Verbatim)" section and task intent), while the brief is only a file the lane read: in the week to 2026-11-07, 2 of 5 lane compactions kept the brief path and none the goal or Done line (owner Q530). omo has no other way in: its automatic compaction takes no instructions from outside, and an extension can only cancel or replace the whole summary. A lane handover's first message ends with the same anchor. With a running `compactionTrial` the lane also gets its arm (`trialArm`, see `dori compaction-trial`).

Every launch decides its work thread first, because the owner's long work gets one (directive long-work-thread): `--thread <adapter>:<id>` for the open thread the work continues in, `--thread new` for a new one, or `--no-thread "<reason>"` for a lane the owner did not ask for (an internal check, a scratch test). With neither, or with `--thread none`, it prints `LAUNCH_NO_THREAD <key>` (and a watch-log line) and exits 4 before anything is written, opened or registered; `--dry-run` stops the same way. `--thread new` needs `DORI_DISCORD_TOKEN` and `DORI_DISCORD_CHANNEL`: once every other check passed, it opens a working thread named for `--title` in that channel (the Dori's own), maps it like `dori thread open`, prints `THREAD_OPENED <key> discord:<id>` and puts that ref in the footer and the registry, so a refused launch leaves no empty thread. `--no-thread` keeps its reason in the registry (`noThread`) and the watch log (`LAUNCH_THREADLESS`), and `dori directive-audit` does not count such a lane as a thread gap; an empty reason, or `--no-thread` with `--thread`, is refused. A `discord:<id>` that is this Dori's channel, the pair channel or a watched channel is refused as `LAUNCH_THREAD_IS_CHANNEL` (exit 4): status marks only go on threads. `dori adopt` and handovers are not gated, so an older lane without a thread can still be registered or moved.

`--thread new` first looks for related open threads, so related lanes stay in one thread (directive related-thread): every thread of the registry with a lane still open or closed less than `related.recentH` hours ago, and any lane thread an owner message the brief links is in, however old (a channel id is never one). A thread is shown when the brief links an owner message that is in it, or one its lanes' briefs link too (these come first), or when the brief's title and text share enough rare words with one of its lanes (`related.minScore`). Each one is a `LAUNCH_RELATED_THREAD <key> <ref> <n>/<m> "<title>" (...)` line with its evidence under it (the link, `the brief uses ~/.dori/qa/<key>/`, `the brief names lane <key>`, the shared words and their similarity, a shared tag, the same cwd, its lanes and when they closed), then `LAUNCH_RELATED_THREAD_CHOOSE`; it exits 4 with nothing written, opened or registered (`--dry-run` too) and the watch log gets the lines. Pass `--thread <ref>` of one of them to continue the work there, or `--thread new --why-new "<reason>"` when it is other work: it opens the new thread and keeps the reason in the registry (`whyNew`) and the watch log (`LAUNCH_NEW_THREAD_WHY`). `--why-new` goes with `--thread new` only and needs a reason. Nothing is joined on its own: a wrong thread is worse than a new one, so the lead decides. With no related thread, `--thread new` opens at once as before; `--thread <ref>` and `--no-thread` are not looked at.

With `--thread discord:<id>` and `DORI_DISCORD_TOKEN` set, it then writes the lane's first message in that thread, so a thread opened for the lane never sits empty: `discord.laneStartText` with the title, the `--goal`, the first lines of the brief, the Done line, the key and the pane. It prints `THREAD_START_POSTED <ref> message=<id>`; a thread that already has a message is left as it is (`THREAD_START_SKIP`); without a token it prints `THREAD_START_NO_TOKEN` and a Discord error `THREAD_START_FAILED`, and the lane runs either way. Before that, once the lane is registered, a thread it now works in that shows ✅ or 🔔 or is archived (a lane closed in it before) is opened again and marked 🔄 through the thread status queue (Discord's rename limit parks it for the listener), and its `threads.json` record comes back: `THREAD_REOPEN <key> <ref>: working requested: <applied|unchanged|pending|dropped>`, or `THREAD_REOPEN_WARN` on an error; `dori adopt` and `dori set-thread` do the same. `launch` opens a thread itself only with `--thread new`: for work that is the same as or continues an earlier lane, pass the ref of the thread that work already has, so it stays in one place; several open lanes may share a thread, and a close leaves a shared `discord:` thread open while another open lane uses it.

Before the footer it adds a `## Past signals (written by dori launch)` section when earlier lanes in the same area have a record: lanes with the same `--cwd` (unless it is `defaultCwd`) or a shared tag. The key's first word is always a tag (`rl-e8` shares `rl` with `rl-e7`); `--tag` adds more and is stored in the lane. Up to `signals.launchLanes` lanes, newest first, one line each (numbered attempts, root-cause switch, fixes, rejected claims, re-sends and nudges) plus their warnings, so the new lane does not repeat a fix that already failed.

Before Past signals comes `## Lessons for every lane (written by dori launch)` when the lead has current global lessons (`dori lesson add --global`, from dori-superagent #97, https://github.com/sisyphuslabs/dori-superagent/pull/97): up to 4 `pending` or `helped` ones in every brief, whatever its `--cwd`, newest first, in the same line form as below; the two kinds have their own caps, so global rules never push repo lessons out. Then comes `## Lessons for this repo (written by dori launch)` when the lane's `--cwd` (any, `defaultCwd` too) has current lessons (`dori lesson`): up to 8 `pending` or `helped` ones, newest first, one line each as `- [<outcome>; <lane>; <id>] <rule>`, the id for `dori lesson mark`. A lesson whose rule the brief already says word for word (a directive the ledger put in, the lead's own text) is left out, so the owner's words are never said twice. A damaged journal line prints `LESSON_WARNING` (also in the watch log) and never stops the launch. Each lessons section, like Past signals, the tree and the footer, is not the lead's or the owner's words: the directive audit, `intent-check` and the rollover audit leave it out, and a brief launched again gets its lessons section made anew (a lesson marked since is gone), not a second copy, while text added after its footer (backlog's read-only rule, an owner's answer) stays.

After Past signals comes `## Hypothesis tree (written by dori launch)` when the area's tree (the lane's `--cwd` unless it is `defaultCwd`, else its first tag, plus its other tags) has open entries: a few lines each of open, supported and falsified hypotheses, untried directions, research due, findings and recent attempts (see `dori tree`).

The footer tells the lane to report with `["dori","type","<leadPane>","--text","<report line>"]` (an argv array; `NOT_SUBMITTED` means send it once more), for herdr and aoe alike. `--goal "<the owner's words>"` is stored in the lane as `goal` and written into the footer with the instruction to run `dori intent-check` at each stage change; without it `launch` prints `LAUNCH_NO_GOAL <key>: ...` and goes on. `--challenge-before "<step>"` (repeatable) is stored as `challengeBefore` and tells the lane to put that step's plan through `dori challenge` first; `claim-done` refuses (`CHALLENGE_MISSING`, exit 5) until a challenge is on record. Require it for steps that cost hours or a GPU queue, change the approach, or follow a falsified hypothesis. `--dry-run` prints the brief exactly as the lane would read it (your text, Past signals, Hypothesis tree, footer) followed by `DRY_RUN <key>: ...`; it writes nothing, registers nothing and opens nothing.

When every `Done =` signal only checks that files exist or contain text (a `file` signal, or a command that is only `grep`/`test`/`cat`/`ls`/`wc`/`jq`..., directly, via `sh -c` or in a readable shell script), it first prints `LAUNCH_DONE_WEAK <key>: ...` asking for a signal that measures behavior, then launches anyway. `--done-weak-ok` silences it. A script it cannot read is not called weak.

Every launch checks the brief for the eight step headings of the template in `references/sessions.md` (`1. 조사:` ... `8. 보고:`): with none it inserts the whole block from that file, byte for byte, after the paragraph of the four fields ([목표] ... [넘으면 안 되는 선]), or after the `ulw` line (else at the top) when there are no fields, and prints `LAUNCH_STEPS_ADDED <key>: ...` and a watch-log line; with all eight it changes nothing; with some of them it adds nothing and prints `LAUNCH_STEPS_PARTIAL <key>: ... (missing N, ...)` and a watch-log line. `--dry-run` prints the same line. With `--ui` the brief reads `ulw`, the UI steps, the four fields, the eight steps.

`--ui` is for UI work (a screen, a design, a dashboard, a page, an app's UI): it puts the owner's seven UI steps, the block between the markers in `references/ui-work.md`, at the top of the brief, right after its first line when that line starts with `ulw`, else above everything; a brief that already has them gets no second copy. Without `--ui`, a brief that reads like UI work (two UI words such as UI, UX, dashboard, frontend, 대시보드, 프론트엔드, 디자인, 웹페이지, 화면, at least one of them not 화면; a word inside a hyphenated name such as a lane key, a quoted word and a directive's name do not count) prints `LAUNCH_UI_HINT <key>: ...` and a watch-log line; with the directive ledger on (directive `ui-steps`) the steps go in anyway and the lane launches with them (`--waive ui-steps "<reason>"` keeps them out of a brief that is not UI work), without a ledger it launches as is.

`REF` is `<adapter>:<id>`, e.g. `discord:<thread id>` (digits only) or `telegram:<chat>/<topic>`. An empty id (`discord:`), a bare `--thread`, a ref without an adapter, or whitespace in the id is refused before anything opens: exit 1 with a one-line reason, and no lane is registered. Leaving `--thread` out is fine; the lane is registered with thread `none`. `adopt` checks `--thread` the same way.

**The directive ledger.** Every launch also reads the directive ledger (`directives.common` and `directives.local`). It decides what the brief is about from the lead's text with quoted words, directive names and scope labels left out (a brief that only names "UI 7단계" is not UI work): UI work (`--ui`, or two UI words), a kind of work (`minHits` hits of that kind's regex), the repo of `--cwd` (its `origin` remote's name, else the directory's name) and keywords. A scope with `briefOnly` narrows only what a lane's brief gets: an owner row still leaves the entry out and a thread the lead opens still gets it, as for an every-lane entry without keywords. When `directives.pickModel` is set (default a small Claude), launch fixes the entries for every lane, the blocks, the require entries and the repo's own entries, and that model reads the lead's text three times at once and the lane gets all it named in any run. The lane's `directives.pick` keeps the merged list, the reasons and how many runs answered. Runs that fail add nothing; when no run answers with the JSON and at least one known id, the scope rules decide (`LAUNCH_DIRECTIVE_PICK_FALLBACK`, `directives.pickFallback`). `dori directive-audit` then counts as a gap only what was chosen and is not in the brief; what a scope rule calls and the model left out is `DIRECTIVE_PICK_SKIPPED`, listed with `--dry-run` and not counted. An `inject` directive in scope that the brief lacks goes in under one heading, `## 형 지침 (지침 장부에서 dori launch가 넣음)`, at the end of the lead's text: an owner directive with words as its `prompt` under the tag `[형 지침 <id>, <date>]` (the lead's rewrite of his words as the standing rule a lane follows from now on, like a general prompt: imperative or declarative, no question; a task he asked to be done once in that message, a description of that situation and asides are left out; every condition, target and strength word (반드시 꼭, 앞으로 항상, 절대로) kept, nothing added; his `words` and `original` stay in the ledger as the record; no summary, no rule, no context; an owner decision on record without his sentence is tagged `[형 결정 <id>, <date>, 원문 없음: 리드 기록]` with the rule), a lead rule as `[리드 규칙 <id>]` and its rule; the trigger and the basis stay in the ledger and `dori directives`, and launch prints `LAUNCH_DIRECTIVE_ADDED <key>: <id> (<why>), ...` and a watch-log line; the `eight-steps` and `ui-steps` blocks are placed as above (a brief that reads like UI work without `--ui` gets the UI steps too, with `LAUNCH_UI_HINT`). A `require` directive in scope the brief does not meet (the four fields) stops the launch before anything is written or opened: `LAUNCH_DIRECTIVE_MISSING <key> <id>: ...` and a watch-log line, exit 4 (`--dry-run` prints the brief and exits 4 too). `--waive <id> "<reason>"` (repeatable) leaves that directive out: `LAUNCH_DIRECTIVE_WAIVED <key> <id>: ...` in the watch log, the waiver in the lane's `directives.waived` in the registry, and `discord.waiveText` to the owner (`DIRECTIVE_WAIVE_SENT`, or `DIRECTIVE_WAIVE_NOT_SENT` and why). A waiver of an id not in the ledger is refused, and so is a ledger that does not validate. The lane records `directives.applied` (the ids in scope) and `ui`.

### `dori directives [table|prompts|check [--static]|apply <key> [--dry-run]|hint <text>|links [--push]]`
`hint <text>` prints what an owner message with that text carries in its inbox row (below, `dori inbound discord`): `DIRECTIVE_HINT <id> (<why>): <tag> <text>` for every entry a keyword calls and the other matches up to five entries in all, or `DIRECTIVE_HINT_NONE`. An every-lane entry (`scope.all`) is in it only when its own `keywords` are in the text; one without keywords never is, since every lane gets it anyway.
`links` prints the `{ id, source }` rows of this Dori's local ledger for fork ids (the owner's message links); `--push` writes them to every `directives.linkPeers` file (above), only where it differs, and exits 1 when a peer failed.
`table` (the default) prints the ledger as one markdown table for the owner: id, name, the owner's words, the prompt briefs get, date, source, scope, how it is enforced, layer. `prompts` prints only his words next to the prompt (`| id | 형 원문 | 지침문 |`), for him to read. `check` validates both layers (ids, dates, modes, kinds, regexes; every owner entry with words has a `prompt`, and no prompt asks: a `?` or a question ending such as 않아, 할까, 하니 is `prompt is a question`), then has a reviewer of another family than `defaultModel` (`reviewers.models`, `reviewers.first` first, `reviewers.command`) compare each new or changed prompt with his words (leaving out a one-time task or the situation of that message is not a loss; a dropped or added condition, target or strength is): `DIRECTIVES_MEANING_OK <id>`, or `DIRECTIVES_BAD directive <id>: prompt does not mean what his words mean: MISSING|ADDED|STRENGTH|QUESTION: ...` for a dropped condition, an added requirement or a changed strength (반드시 to 가능하면), or `DIRECTIVES_MEANING_FAILED <id>` when no reviewer answered; any of those exits 1. A SAME verdict is kept in `<stateDir>/directives/meaning.json` per (id, original, words, prompt), so only a new or edited prompt is read again. `--static` skips the reviewer (launch runs the static part only). All good: `DIRECTIVES_OK <n> directives (<fork>, <local>) in <files>`.

`apply <key>` is for a lane launched before a directive was in the ledger (or before it was in scope). It judges the lane's scope again as `directive-audit` does (its brief, the repo of its cwd, `ui`) and takes every directive in scope its brief lacks, in launch's format: `[형 지침 <id>, <date>]` and the prompt, `[리드 규칙 <id>]` and the rule, a built-in block (the eight steps, the UI steps) as its text. They go to the lane's pane as one `[LEAD] 지침 보충: ...` message (the lane keeps its work and follows them from now on); once it is SUBMITTED, the same texts go into the brief under `## 추가 지침(리드, launch 뒤)`, after the lead's text and before what launch appended (past signals, tree, footer; nothing above is changed), the ids into the lane's `directives.applied`, and `DIRECTIVES_APPLIED <key>: <ids> ...` into the watch log. Nothing missing: `DIRECTIVES_APPLY_NONE <key>` and no change, so a second run is a no-op. Not submitted: `DIRECTIVES_APPLY_NOT_SENT <key> <pane>`, exit 1, brief unchanged. A `require` directive (the four fields) is not a text to send: `DIRECTIVES_APPLY_REQUIRE <key> <id>` asks the lead to write it in. `--dry-run` prints what would be sent and changes nothing. The words in that section never change the lane's scope (launch's and the audit's scope text leaves it out, like `## 형 지침`). Either section starts only at its heading on a line of its own: a brief that quotes the heading inside a field (a lane about this command) keeps the rest of its fields.

### `dori directive-audit [--since 24h|Nd|ISO] [--dry-run]`
The daily check that nothing slipped past the ledger (the `freshness` loop runs it once a day, below; a host timer may run it too, `--since 24h`). For each lane opened since then: every directive in scope that is not in its brief (`DIRECTIVE_GAP <key> <id>: ...`; waivers on record are left out) and a lead directive the lead did not follow (`DIRECTIVE_LEAD <key> lane-thread: ...` for a lane launched without `--thread`). The lead's own threads are read too: a thread in `<cardDir>/threads.json` made since then (its `openedAt`, else the time in its Discord id) that no lane in the registry works in and that `dori thread open` did not mark with the directives it read (opened before that check, or mapped by hand) is `DIRECTIVE_LEAD thread:<id> -: the lead's thread "<title>" ... was opened without reading the directive ledger`. Two are not the lane's gaps: a directive that entered the ledger after the lane opened (`DIRECTIVE_LATE <key> <id>: entered the ledger <time>, after the lane opened <openedAt>`; for a fork entry the time is the first commit that added the id to either ledger file, never before the start of the entry's `date` in KST; a fork entry no commit shows has its date alone; a local entry is read live and committed later, so its commits do not count: it has the earliest owner message its `source` links (the message id of a `discord.com/channels/<guild>/<channel>/<message>` link, read from its snowflake) when that is later than the start of its date, and its date alone when the source has no such link), and one the lead typed into the lane after it opened in a `[LEAD]` line that names its id or carries its text, read from the lane's own session files as `dori intent-check` reads its relays (`DIRECTIVE_RELAYED <key> <id>: the lead's [LEAD] line of <time> ...`). They are counted in the closing line (`... <n> gaps (<m> not counted: ...)`) and listed with `--dry-run`. Then the owner's messages since then (the inbox, author `DORI_DISCORD_OWNER`) that match the ledger's `standing` regex and that no entry cites by message id and `reviewed` does not list: `DIRECTIVE_UNLEDGERED <link> "<text>": ...`, a directive the lead did not put in the ledger the same day. Gaps go to the watch log, one line each, and one `[DIRECTIVE_AUDIT] <n> directive gaps ...` summary is typed to `leadPane` (`DIRECTIVE_AUDIT_SENT`, or `DIRECTIVE_AUDIT_NOT_SENT`). No gap: one `DIRECTIVE_AUDIT_OK ...` line on stdout and nothing else. `--dry-run` prints the lines and writes and sends nothing.

The audit runs on every Dori without a timer of its own (not where `directives.dailyAudit` is `false`): the `freshness` loop (`dori-lanes.sh`) runs it when no audit ran in the last 24 hours (the time of the last run, the timer's included, is in `<stateDir>/directives/audit.json`; it reads from that run on, at most 7 days back), and prints `DIRECTIVE_AUDIT lead <line>`. It reads the ledger tolerantly: a line of `directives.local` that would break the ledger (a source-only line for an id the fork does not have, a field that fails the checks, a line with no id, a file that is not JSON) is left out with `DIRECTIVES_LOCAL_SKIP <id>: ...` (the fork entry it overrode stands) and the rest is audited (`DIRECTIVE_AUDIT_DONE since <time>: ... <n> gaps, <m> local ledger lines left out` ends the list); launch and `dori directives check` still refuse such a line. Skipped lines count like gaps: in the watch log and in the summary. Every `[DIRECTIVE_AUDIT]` summary also goes into the lead's inbox (a `kind: "directive-audit"` row in the inbox it reads). An audit that cannot run at all (a fork ledger with problems) prints `DIRECTIVE_AUDIT_FAILED since <time>: <why>`, puts it in the watch log, the lead's inbox and pane, and exits 1, so it never stops in silence. Launch and adopt store the brief as an absolute path (the audit, intent-check and freshness run from another directory than the lead's); a lane stored with a relative brief before that is read from its `cwd`.

### `dori backlog [list [--all]|add <id> ...|drop <id>|decide <id> [--question Q --hash H] --text T|tick [--force]|show <id>]`

The list of work the owner or the lead puts by hand, started as lanes as soon as there is room (the idea of dori-superagent's hourly loop, #23, rewritten for `dori launch`; no GitHub issue import). `add <id> --title T --brief FILE --done "..." [--priority 1-9] [--cwd DIR] [--thread REF|new | --no-thread "<reason>"] [--why-new R] [--goal G] [--tag T ...] [--ask "<question>"] [--read-only] [--owner-link URL] [--by owner|lead]` copies the brief and checks what `dori launch` would refuse (a registered `bl-<id>` key, a Done line that cannot be checked, a bad thread ref): `BACKLOG_ADDED`, or `BACKLOG_REPLACED` for an open item of that id (the fix of a held one); `--thread new` is the default, as for the owner's long work. Work that needs the owner's word before it writes is added with `--ask`. `list` prints `id | status | p<n> | by | title | state` and `BACKLOG_ON` / `BACKLOG_OFF`; `drop` refuses a running item (close its lane, `dori close bl-<id>`); `decide` appends the owner's answer to the item's brief under `## 형 결정` and clears the question.

With `backlog.enabled` the `freshness` loop runs a pass on every tick (a `flock` on `<stateDir>/backlog`, held by a child process the kernel lets go of if the pass dies, keeps one pass at a time, and `add`, `drop` and `decide` wait for it; `tick` runs one by hand, `--force` a sweep now, even when off). A running item whose lane closed is done (`BACKLOG_DONE`); an item with a question puts one `kind: "backlog-ask"` row in the lead's inbox and never starts before `decide` (`BACKLOG_ASK`); the open items start at once by priority (then age) through the same launch as `dori launch` (its directives, eight steps, footer and work thread; tag `backlog`) under the lane key `bl-<id>`, which `dori launch` refuses for any other lane, while fewer than `backlog.maxLanes` backlog lanes of this Dori and `backlog.hostMaxLanes` of all Doris on the host run, at most `backlog.maxStarts` a pass, and, checked again before each start, a model account of `defaultModel`'s provider is free in omo's credential pool and `dori can-launch` and `guard.loadOk` allow (`BACKLOG_STARTED` and a `backlog-start` row). An item added `--read-only` launches with a read-only rule appended to its brief from its state. Why nothing starts (`BACKLOG_HOLD`, `BACKLOG_WAIT`, `BACKLOG_IDLE`) is printed when it changes and at each sweep only. A launch its input makes impossible (any `LaunchError` but `LaunchFailed`, e.g. `LAUNCH_RELATED_THREAD`, a bad Done line) holds the item at once and is never taken as a start; a backend failure (`LaunchFailed`: the aoe or herdr session could not be opened) or any other error is tried again and holds it after two tries (a work thread `--thread new` already opened is kept on the item, so the next try continues there) (`BACKLOG_HELD` and a `backlog-held` row) until `add` replaces it or `drop`. Each line is in the watch log (source `backlog`). State: `<stateDir>/backlog/` (items, briefs, `last-run.json`).

`backlog.feedCommand` (YooDori: the dashboard's `todo-list --open --json`, `[]` off) is read at each sweep, its entries becoming items `todo-<todo_id>` (`by feed`, no work thread, Done `backlog.intakeDone`): an entry the owner approved by card (`approved_at` with `auto_applied: false`) works within its own scope, its lane told to send `X-Dori-Owner-Todo: <todo_id>` as the gate proof for writes inside the owner's account (and, on the cytoplasm node gate, to end `mail-attachment`, `mail-attachment-text` and `drive-save` with `--origin-todo <todo_id>`, which reads only that todo's source mail) (the gate checks the dashboard and the owner's ✅ on the card at each write, while the todo is open, until it is finished, held or deleted; `setups/egress-gate/README.md`), any other (taken in by the board without a card) only reads and drafts and asks the lead before any write, the gate's refusals included; the limit is worked out at each launch from the item's state and bound to a hash of the entry's content (status, progress, times, `card_approved_at`, `note` and `note_truncated` are not content), so changed content voids the approval and asks again with a new question id (`decide <id> --question <qN> --hash <h> --text ...` answers that one question; an older one does nothing), and a draft approved after its lane ran gets one follow-up `appr-<id>` that starts from the draft's report. An entry on hold (`보류`) gets no item and holds its open one (`BACKLOG_FEED_PAUSED`, `BACKLOG_FEED_RESUMED`); one listed done, or no longer listed (finished or deleted on the dashboard, or cut from a full list of 200), drops its open items (`BACKLOG_FEED_DONE`, `BACKLOG_FEED_GONE`; a running one is left to its lane) and they come back when it is listed open again (`BACKLOG_FEED_REOPENED`); a failing command, or a list with an entry that is not a todo with an id (the whole list is then not read), is one `BACKLOG_FEED_SKIPPED` line; a `dori backlog drop` is final, the entry listed again does not bring it back. `backlog.pairRepairPattern` (a regex, `""` off; SooDori: `수돌, 수리 요청` with a relay head or the old name 고돌 allowed) takes the other Doris' #dori-pair posts (`scope: "pair-bot"`, a bot in `DORI_DISCORD_PAIR_BOT`) on every tick, each post that starts a repair request an item `pair-<message id>` (`by pair:<bot id>`, no work thread) that starts at once without an owner link, the owner's standing rule `fix-to-soodori` being its approval (with `backlog.writeNeedsOwnerLink` also on, config loading says `CONFIG_BACKLOG_REPAIR_EXEMPT` once). The first pass only notes where it starts (`BACKLOG_INTAKE_FROM`) and never moves it: every later post is taken once, by the item its id names, however late it reaches the inbox. A reply (a post with `reply_to`) is not taken: one `BACKLOG_INTAKE_SKIPPED reply` line, kept as a dropped item so it is judged once; its request's lane reads the thread, and the lead has the reply as a `pair-bot` row and puts it into that lane if it is needed. A request the lead already took up is not started either: at every pass, before any limit or start, it looks for this Dori's own post that replied to it (`dori send discord --reply <id>` records the target with the post, kept a day) and for a lane, not a `bl-` one, that says the request is its own: `#dori-pair <message id>` in its brief's `[목표]` line (as the lead writes `[목표] 공돌 수리 요청(#dori-pair <id>): ...`) or the id in its `--no-thread` reason (an id quoted elsewhere in a brief does not count); either drops it with one `BACKLOG_ALREADY_HANDLED pair-<id> <reply <post>|lane <key>>` line. `dori backlog drop pair-<message id>` works before the post is taken in too (`BACKLOG_DROPPED ... before intake`): it is kept as a dropped item, which the intake skips. Not taken either: other requests between the Doris (they stay the lead's). These rows are the backlog's alone: one that cannot start waits on the list, it is never handed back to the lead. `backlog.orderKinds` (YooDori: `["dashboard-order"]`) takes the owner's own orders from the inbox on every tick, read from where the last pass stopped (an append position in `<stateDir>/backlog/intake.json`, kept once the rows are taken; a rotated inbox is read from its start), so an order is not lost however much else the inbox got while the backlog did not run: each new row of those kinds becomes an item under its row id (priority 2, `by owner`, no work thread; its brief carries the row as the owner's order, the order number as the gate's proof for writes in his account, and the board's status steps); the first pass only notes where it starts (`BACKLOG_ORDERS_FROM`; the start never moves, and a row is taken once by its id however late or out of order it reaches the inbox), and an order stamped before that is the lead's; every later one is the backlog's alone (the lead leaves order rows to it). A pass runs at most one lane per board todo (an order's `todo_id`, a feed entry's or its follow-up's own id): another item of that todo waits (`BACKLOG_WAIT … is worked on by lane …`) until that lane closes, and a pass looks at every waiting item until its starts are used, so one that waits does not hold back the items behind it. An owner's order about a todo whose lane runs does not wait: in the same pass it is dropped and handed to the lead with a `backlog-held` row (`BACKLOG_ORDER_TO_LEAD … put it into that lane`), so a stop or a change reaches that lane now; The backlog never touches it again. An order with no room waits on the list like any item. `backlog.dayReportAt` (`"HH:MM"` in `backlog.timeZone`) puts one `backlog-day` row a day in the lead's inbox: done and started that day, waiting on the owner, held, open more than 7 days, titles listed twice.

### `dori adopt <key> --pane ID --title T --brief FILE --done "..." [--thread REF] [--tag T ...] [--goal G] [--challenge-before STEP ...] [--use-gpu]`
Registers a lane that is already running; `--goal`, `--challenge-before` and `--use-gpu` are stored as for `launch`. The running session keeps its environment: with backend `aoe` and a `launchEnv` it prints `ADOPT_ENV <key>: ...` saying the lane's setting applies from its next handover or restart.

### `dori set-gpu <key> on|off`
`on`: the lane's next session (handover, `self-restart.sh`) starts without `launchEnv`; `off`: with it. The running session keeps its environment. Prints `GPU_SET <key> <old> -> <new>: ...`. Mark a lane that trains on the GPU `on` before its next handover or restart.

### `dori launch-env <tmux-session>`
Prints, one per line, the `env(1)` arguments a restart of that session needs to start the way dori opens it: `NAME=VALUE` for an open lane, `--unset=NAME` for a `--use-gpu` lane, a closed lane, the lead or any other session (unsets first, as `env` reads options only before the first assignment). It appends the names to tmux `update-environment` first. Nothing without `launchEnv`. `setups/discord-aoe/self-restart.sh` runs `aoe session start|restart` under these arguments.

### `dori set-thread <key> <adapter>:<id>`
Points an open lane at another work thread, for example one created after the lane was launched. The ref is checked as for `launch`; a bad one exits 1 and leaves the lane unchanged. Prints `THREAD_SET <key> <old> -> <new>`.

### `dori done-set <key> --done "<signals>" --reason "<why>"`
Changes an open lane's `Done =` line when its plan changed after launch and the old signals can no longer read back live, though the work is done (an owner's later instruction replaced a service with a dashboard tab and a timer, say). The new line is checked as for `launch` (an unreadable signal, no `--reason`, or the line the lane already has exits 1 and changes nothing), then every new signal is read once and printed as `SIGNAL OK|NOT <signal> -> <detail>`, ending in `DONE_SET <key> live <k>/<n>: ...`. The change is kept either way: the lane's `doneChanges` in the registry holds the earlier line, the new one, the reason, the time and whether it read back live; the watch log gets `done-set DONE_SET <key> live k/n; reason: ...; was: ...; now: ...`; the brief's `- Done =` footer line is replaced, with a `- Done changed ... Earlier: Done = <old>` line under it (`BRIEF_UPDATED`, or `DONE_SET_BRIEF_WARN` when the brief cannot be written); and the lane is told in its pane (`LANE_TOLD`, or `DONE_SET_NOT_SENT`). `dori signals` and later lanes' Past signals show the change. Nothing is skipped: `dori close` and the watcher read the new line, and every signal still has to read back live.

### `dori sync [--write]`
Prints `key | thread | pane | session | status` for every open lane and every unregistered agent pane, followed by a `SIGNALS <key> [<outcome>] ...` line for each open lane that has a record (see `dori signals`) and drift. Read-only unless `--write`, which stores session ids.

### `dori checkpoint <key> --step ID --result TEXT --evidence PATH [--remote-effect RECEIPT]...` / `dori checkpoints <key>`
Run by a lane after each completed step, and on resume before doing work (ported from dori-superagent #61 and #68: `src/checkpoints.ts`, with two fork changes below). Each step is one line in `<stateDir>/lane-state/<key>/checkpoints.jsonl` (apart from the registry's `<stateDir>/lanes/<key>.json`, so a key such as `foo.json` cannot collide with it) with its result, evidence and the receipts of remote effects it completed (a push, a merge, a deploy), one `--remote-effect` per receipt: a second bare receipt after one `--remote-effect` is refused (`checkpoint: unexpected argument ...`) instead of dropped. Recording the same step again with the same data returns the original, unchanged (`"unchanged":true`); different data for a recorded step is refused (`conflicting checkpoint step`), and so is a receipt another step already recorded. Writes fsync the journal (and its directory when they create it) and append a record whole or not at all: a write the disk takes only part of is cut off again and refused, so the journal keeps its valid lines. An identical replay is flushed before it is acknowledged. The writer lock is a kernel flock on `checkpoints.jsonl.lock`, whose file records the holder's pid, host and time: a held lock is refused with that pid and age, however old it is, and the kernel drops it when the holder's process dies, so a writer killed mid-write never locks the lane. Upstream instead takes a lock over by its record and age; that check-then-delete could remove a live writer's lock (reviews of #297), so these points differ from upstream. `checkpoint` needs an open registered lane; `checkpoints` prints the journal as JSON (`[]` when empty) and writes nothing.

A lane reads its checkpoints before resuming and never repeats a recorded remote effect. A crash between a remote action and its checkpoint is not covered by the journal: read the live remote state first, and use the service's idempotency key where it has one.

### `dori claim-done [<key>] --evidence TEXT [--summary TEXT]` / `dori object-done <key> --reason TEXT ...`
The two halves of the done flow. `--summary` is what the owner's work thread gets when the lane closes (2 to 5 plain lines in his language: what changed, what is left, when it reaches where it is used); it is kept with the claim, and one with a local path, a commit hash, backticks, a report head, or ~요/~니다 speech when this Dori talks to the owner in 반말 (`discord.ownerSpeech`) is refused (`SUMMARY_REFUSED <key>: <why>`, exit 2, nothing claimed). Without it the close has a model write one (see `dori close`). Both message the lane's pane and check that Enter registered. A claim on a paused lane is recorded and printed as `LANE_DONE_CLAIMED_PAUSED <key> <pane> <evidence>` (and once by `dori watch`), but it never closes the lane on a timer; the lead closes it or objects. A lane launched with `--challenge-before` that has no `dori challenge` on record gets `CHALLENGE_MISSING <key>: ...` and exit 5 instead of a claim.

### `dori pause <key> <reason>` / `dori resume <key>`
Parks a working or not-done lane that waits on a human, for example on the owner's approval. The status becomes `paused`, the previous one is kept in `pausedFrom`, and `PAUSED: <reason>` goes into the lane's history. While paused, `dori freshness` neither nudges nor posts for it, `dori watch` reports no `LANE_BLOCKED` and does not auto-close it, and `dori dead-panes` skips its pane. `dori resume` restores the previous status with a `RESUMED` history entry and restarts the silence clock, so the first nudge comes a full `nudgeAfterMin` later; when a claim arrived during the pause it prints a `NOTE` saying so. Pausing a lane that is not working or not-done, or resuming one that is not paused, exits 1.

With backend `aoe` the pause also stops the omo goal of the lane's session, since an active goal makes omo start the next turn on its own and the lane would keep working (ported from dori-superagent [0057f49](https://github.com/sisyphuslabs/dori-superagent/commit/0057f49de9ae32f1bd0e38fe097d7430224bcb29), MIT). Before the registry changes, `pause` types `/goal pause` into the session and reads the result back from the goal file omo keeps next to the session's transcript (`<session dir>/extensions/goal/<session id>.json`), or, when that file cannot be found, from a new `Goal paused` line on screen. A running turn is not interrupted: it ends, and no goal turn follows it. A second line says what happened to the goal:

- `GOAL_PAUSED <key> <pane>: goal store reads paused`: the goal was paused; the lane remembers it (`pausedGoal`), and `resume` types `/goal resume` and reads back `active` (`GOAL_RESUMED`) before the lane goes back to work.
- `GOAL_SKIPPED <key> <pane>: <why>`: nothing to pause (no goal in the session, a goal the agent or the owner already paused, completed or blocked, or no live session). `resume` then leaves the goal alone.
- `PAUSE_UNVERIFIED <key> <pane>: <why>; lane left <status>` (exit 3): the goal was not read back paused (the command could not be typed, or omo did not take it within 10 s), so the lane may still go on by itself and stays as it was: look at the pane and run `pause` again. `RESUME_UNVERIFIED` (exit 3) is the same for `resume`; the lane stays paused.

### `dori fix-attempt <key> --metric M --hypothesis H [--hypotheses H1 --test T1 ...] [--improved] [--no-hypotheses REASON]`
Records a fix you asked the lane for, in the lane's `fixes`, and takes one step of the stuck ladder. Prints `FIX_RECORDED <key> attempt=<n> on-metric=<m> stuck=<s> (tagged t, inferred i)` (n: this metric and hypothesis; m: this metric; s: the stuck count) and the `STUCK` line when the metric's rung went up. `dori freshness` records the lane's own reports tagged `(fix: <metric> / <hypothesis>)` the same way; a fix you recorded that the lane then reports counts once. Before it records, it prints what the area already tried on that metric: `PRIOR_FIX <lane> "<metric>": <hypothesis> xN, ...` per lane (this lane, its cwd, its tags), or `PRIOR_FIX none on "<metric>" in this area`, under the metric's name in `autoSignals.aliases` as the stuck count uses it (`--metric deadlocks` lists the fixes recorded as `교착`; `HYPOTHESES_REQUIRED`, `STUCK_BRANCH` and `HYPOTHESES_OVERRIDE` use that name too), and `PRIOR_ATTEMPTS <key> numbered attempts 1-N, root-cause switch: <time|none>` when the lane's reports number their attempts. See `sessions.md`, "Repeated fixes".


The stuck ladder: failed attempts on one metric are counted whatever the hypothesis (a fix you asked for that the lane then reports counts once), in the lane's current session, since the last one recorded with `--improved` (the previous fix moved the metric) and since the last PASS of the metric its reports showed; the inferred count (`dori repeat-check`, under the same `autoSignals.aliases` name) counts too, and the larger one is the stuck count. Each rung change prints and logs one line, `STUCK <key> "<metric>" rung N (tagged t, inferred i, hypotheses h[, fixated][, inferred only]) -> <what to do> [<old names>]` (source `stuck`), once per rung; a count that went down (PASS, `--improved`) lowers the mark silently, so the next stuck run alerts again. The old names at the end (`HYPOTHESES_REQUIRED`, `RESEARCH_DUE`, `ROLLOVER_DUE`, `SAME_FIX_3` when fixated, `REPEAT_SUSPECT` when the inferred count reached `stuck.researchAt`) stay for one release so monitors that grep them still match.

- Rung 2, from `stuck.hypothesesAt` (2): `fix-attempt` refuses unless you give at least `explore.minHypotheses` (3) distinct competing hypotheses with `--hypotheses`, each followed by one cheap discriminating experiment with `--test`, in the same order. A refusal prints `HYPOTHESES_REQUIRED <key> attempt N on "<metric>" ...` with the command to run instead, logs the same line, exits 5 and records nothing. An accepted branch prints and logs `STUCK_BRANCH <key> attempt N on "<metric>": H4 ... (test: ...) | ...` and puts every hypothesis with its test into the area's tree as open. `--no-hypotheses "<reason>"` goes on without them and logs `HYPOTHESES_OVERRIDE <key> ...: <reason>`. Every recorded attempt also goes into the tree as tried. A lane's own unbranched second report is rung 2 too: the `STUCK` line tells you to re-instruct it with hypotheses.
- Rung 3, from `stuck.researchAt` (3): a research entry goes into the tree (so the next brief in the area shows it), and with `explore.sendResearchToLane` the lane gets `explore.researchText`: ulw research on the exact symptom, then a `dori challenge` of its next plan, before the next patch, in the same session. No rollover at this rung: a lane that is researching cannot be moved, and a moved one would re-read the research. An inferred count starts it too. Rung 3 is already done, and nothing is typed, when the lane ran both on its own after the repeat that made rung 3 due: ulw research (a real read of the ulw-research `SKILL.md` in its session log, or a research folder `<cwd>/.omo/ulw-research/<YYYYMMDD-HHMMSS>` started after it) and a `dori challenge` on record after it, on that symptom (the metric or one of its `autoSignals.aliases` names in a plan one of those challenges reviewed, or in a research folder's `brief.md`). The line then says `already done after attempt 3: <research> and <challenge>; nothing sent, wait for the next attempt's result` and carries `RESEARCH_DONE` instead of `RESEARCH_DUE`; a failed attempt after that research and challenge is rung 4 (at the first scan too, when the count jumps past it). A paused lane gets nothing typed either: the line says so, and `dori research-hint <key> --send` sends it after `dori resume`.
- Rung 4: an attempt that failed after rung 3, one hypothesis tried `stuck.fixatedAfter` (3) times after the lane branched (`fixated`), or an intent-check finding still there after a re-read the lead confirmed (`"@context"`, see `dori intent-check`). A count that jumps (the first untagged scan of a long loop) prints one line with the skipped rungs' old names and `first count` or `from rung N`. `--improved` restarts both halves (the inferred cycles counted so far become a baseline), a PASS too, and the `fix-attempt` gate uses this same count. The line says to decide a rollover (`dori rollover-propose`, then `dori handover --lane <key> --approved-by "lead:<reason and signal>"`). Nothing switches by itself unless `handover.autoRolloverLanes` is on: then `freshness` starts the rollover at rung 4 like at a measured threshold (`ROLLOVER_AUTO`).
### `dori signals [--lane K | --cwd DIR | --tag T ...]`
What earlier lanes in one area tried and how it went, from records only (no model call). Read it before you re-instruct a lane. The options combine as "any of". The first line is the area: lanes, done claims rejected over claims, and rework (your messages to the lanes plus freshness nudges, per lane). Then per lane, newest first:

- its outcome (`open`, `paused`, `not-done`, `done-claimed`, `closed, verified`, `closed by the lead`), cwd, tags, re-sends (`scorecard.leadSendPattern` in `scorecard.leadSessions`) and nudges (`scorecard.lanesLog`);
- numbered fix attempts: a `[REPORT]` line or a message you typed into the lane matching `signals.numberedAttemptPattern` ("adjustment 2", "조정 2/2욌째"), with the words around the first mention and the latest mention before the root-cause switch;
- the root-cause switch: the first such message after an attempt that matches `signals.rootCausePattern` (a message about the root cause is never itself an attempt);
- tagged fixes by metric with each hypothesis and its count (the lane's `fixes`, or the `(fix: M / H)` tags in its reports when the sweep never recorded them);
- rejected done claims with the reasons;
- warnings: `SAME_FIX` (one metric and hypothesis `stuck.fixatedAfter` times), `REPEAT` (one metric over several hypotheses, or numbered attempts up to `stuck.fixatedAfter` with no root-cause switch), `REJECTED` (two or more rejected claims).

Without an option it prints one `SIGNALS <key> [<outcome>] fixes N, attempts 1-N, rejected R/C, re-sends S, nudges U` line per open lane with a record. Session files older than the oldest lane asked about are not read.

### Exploring when stuck

The point of these commands: when a fix does not move a metric, the next step is to find out which explanation is true, not to patch again. Each has its own section below; how the lead uses them is in `sessions.md`, "Stuck: branch, look outside, check intent", and the E7 example in `operating-lessons.md`.

### `dori tree [show|add|falsify|support|close|reopen] [ID] [--lane K | --cwd DIR | --tag T] [--kind K] [--text T] [--test X] [--metric M] [--result R]`
The hypothesis tree of one area: a JSON file per repo (`<stateDir>/trees/cwd-<path>.json`) or tag (`tag-<tag>.json`). A lane's area is its cwd unless that is `defaultCwd`, else its first tag. Without an area option it uses the lane of the pane it runs in, else the current directory. Entries have an id by kind: `H` hypothesis, `D` untried direction, `F` finding, `R` research due, `T` an attempt tried; and a status: `open`, `falsified`, `supported`, `closed`.

- `show` (default) prints `TREE <area>: N entries` and the entries by group: open hypotheses with their tests, supported, falsified (do not retry), untried directions, research due, findings, attempts tried, then closed ones.
- `add --kind hypothesis|direction|finding|research --text T [--test X] [--metric M] [--result R]` prints `TREE_ADDED <id>`, or `TREE_EXISTS <id>` when the same kind already says the same thing (a missing test is filled in).
- `falsify|support|close|reopen <ID> [--result R]` sets the status and prints `TREE_SET <id> <status> -> <result>`.

Fed automatically by `fix-attempt` (tried attempts, branched hypotheses, research due), `freshness` (the lanes' tagged fix reports), and `fork-explore` (results). `launch` attaches the compact form to new briefs.

### `dori challenge <key> --plan FILE [--model M] [--all]` and `dori challenge --check [<key>]`
Adversarial review before a big step. It sends the plan (up to 60,000 characters), the lane's title and goal, and the area's tree to a model of another family than the lane's own model, in a fresh context (no session, skills, context files or lane history): `explore.challengeCommand`, by default `omo -p --no-session --tools read,grep,find,ls --no-extensions --no-skills --no-context-files --omo-senpi-disabled --system-prompt <reviewer instructions> --model <reviewer> <prompt>`, run in the plan's repository (the git top level of the plan's directory, else that directory). A prompt over 30,000 bytes (the area's tree alone can pass the 128 KiB Linux allows in one argument, and Windows allows 32,767 characters in the whole command line) goes to omo on stdin, with `-` in place of `{prompt}`, so the spawn does not fail with E2BIG; the same holds for every omo `{prompt}` argument of `reviewers.command`, `explore.branchCommand` and `dori review`. The reviewer can read and search files there to check what the plan cites; it cannot change files or run anything. Its final reply is the review, under three headings: "Reasons this will fail", "Missing alternatives", "Cheapest falsifying test". Only a reply with all three is saved. Families come from the model id (`claude`/`opus`/`sonnet`/`fable` anthropic, `gpt`/`o3`/`codex` openai, `grok` xai, `gemini` google, `qwen`, `kimi`, `glm`, `deepseek` ...), whatever provider serves it.

Why read-only tools: `omo -p` runs the reviewer as an agent, and an agent run ends at the first reply without a tool call. With `--no-tools`, a reviewer given a plan that cites files and results answered "I'll read the cited evidence first, then write the review" and that sentence was its whole output (reproduced 5 of 5 on a real plan; with read-only tools the same prompt wrote the review 4 of 4, reading 7-8 times first).

Order: by default the best GPT, then the best Claude, then the best Grok model that omo offers with a subscription login (`chatgpt-subscription/gpt-6-astra`, `anthropic-subscription/claude-fable-5-1`, `xai/grok-4.7`), then a second model of each family (`gpt-6.1-sol`, `claude-opus-5-5`, `grok-4.6`). Why these: `gpt-6-astra` is OpenAI's top tier in omo's catalog (priced 5x `gpt-6.1-sol`, and omo's escalation model above it), `claude-fable-5-1` is Anthropic's (priced 2.5x `claude-opus-5-5`, newer than `claude-fable-5`), and `grok-4.7` is the newest xai model (4.3 to 4.7 cost the same). On another machine, run `dori challenge --check` and put its best callable model of each family first. The lane's own family is skipped, so on a Claude lane the order is GPT, then Grok. With `reviewers.allowSameFamily` true (an account setting; false by default) only the lane's own model is skipped (compared without provider and thinking suffix): on a `claude-opus-5-5` lane with `reviewers.models` `["chatgpt-subscription/gpt-6-astra:xhigh", "anthropic-subscription/claude-fable-5-1:xhigh"]`, `--all` asks both. It changes `challenge` only; `intent-check`, `directives check`, the close summary and the rollover audit still take another family, because their point is a second reader who does not share the lane's blind spots. Without `--all` the first reviewer that writes a review is the only one asked (fallback order). With `--all` one review is collected from each family in list order, the next model of a family standing in for one that fails; each review is saved and recorded, and a family with none is reported. `--model` asks that one model (refused when it is the lane's family, or with `reviewers.allowSameFamily` only when it is the lane's own model).

Before any call, each id is checked on this host: `explore.modelsCommand` lists the models each provider offers and `explore.authCommand` says whether a provider is logged in. An id whose provider offers it and is logged in is called as listed; one whose provider is not logged in (or does not offer it) is called on a logged-in provider that offers the same model (`github-copilot/gpt-6-astra` -> `chatgpt-subscription/gpt-6-astra`); one no logged-in provider offers is skipped with the reason. Ids are compared exactly as `omo --list-models` prints them (a `:high`-style thinking suffix aside): omo itself runs an inexact id as whatever it matches (`xai/grok-4` ran as `grok-4.7`), so such an id is skipped rather than silently doubled. `dori challenge --check [<key>]` prints this per id, without a review: `REVIEWER_OK <id> [-> <id called>] (<family>): <why>` or `REVIEWER_SKIP <id> (<family>): <why>`; with a key, only the ids of another family than that lane's model. It exits 1 when none can be called.

- A final reply that lacks a heading gets one stricter retry that quotes what went wrong (a safety net; with read-only tools it should not be needed). If the retry still lacks one, both replies are saved as `<stateDir>/challenges/<key>/<time>-<model>-raw.md` and the next reviewer is asked.
- A reviewer that exits with an error, or times out after `explore.challengeMinutes` (exit 124), is skipped for the next one.
- Each skip prints `CHALLENGE_SKIP <model>: <why>` and is logged as `CHALLENGE_SKIP <key> ...`; when no reviewer writes a complete review the command fails (exit 1) with every reason and raw file, logged as `CHALLENGE_FAILED <key> ...`.

Each review is saved as `<stateDir>/challenges/<key>/<time>-<model>.md` (with `- Read access: <dir>`, and `- Attempts: 2` when the stricter retry wrote it), recorded in the lane's `challenges`, logged as `CHALLENGE <key> reviewer=<model> ...`, and printed with `CHALLENGE_SAVED <file> reviewer=<model>`.

### `dori review <owner/repo#N> [--dir CHECKOUT] [--model M] [--lane K] [--no-test "<reason>"]` and `dori merge <owner/repo#N> [--dry-run] [--delete-branch]`
A PR merges only at the exact head commit a review receipt names (ported from dori-superagent's review and merge gate, MIT). The gate is for repositories without CI: dori-superagent refuses an empty check list outright, which would refuse every merge here, so a passing local test run at the head stands in for checks, and a PR that has GitHub checks or an auto-merge request is refused by both commands as unsupported (`unsupported:checks`, `unsupported:queue`). Porting check handling is follow-up work for when a gated repo gets CI. GitHub branch protection is not used (the owner's decision of 2026-11-02): lanes merge with the owner's admin account, and protection that binds admins would also block the owner's own pushes; `claim-done` and the close catch a plain `gh pr merge` instead.

Before the tests, `review` checks the PR's commits (from dori-superagent PR #44, `dori verify-pr`, taken into `review` instead of a command of its own, with the rules of upstream main's `verify-pr.ts`; the follow-ups of its open issue #57 are not taken in): the commit list comes from GitHub (`gh api repos/<repo>/pulls/<N>/commits`, which must end at the head) and each commit's names, emails and files come from git in the checkout. Either check failing is `REVIEW_CHECKS_FAILED <pr> head=<sha>: <reasons>` (exit 1): no tests run, no reviewer is asked, and an earlier test receipt at that head is taken back, so `merge` refuses it too. (1) Identity: with a `mergeGate.identities` entry for the repo, every commit's author and committer must have that name and email (email in any case); GitHub's `noreply@github.com` passes only as the committer of a merge commit. Without an entry it prints `IDENTITY_SKIP` and goes on. Refusals show an address only masked (`ab***@cd***`). (2) Fix with a test: a commit whose subject starts `fix:` or `fix(<scope>):` (lower case, `!` allowed) and that changes source needs some non-merge commit of the PR to add, change or rename a test that is still there at the head. A test is a file named as one (`*.test.*`, `*.spec.*`, `test_*.py`, `*_test.go|py`) or a code file under `test/`, `tests/` or `__tests__/` (not `setup.*`, `conftest.*`, `test-utils.*`, nor a fixtures, helpers, fakes or mocks file), never under a fixtures, helpers, fakes or mocks directory; a test is never source. Source is code by extension, or a file executable at the head (an extensionless script like `dori-file-relay`); docs and fixtures are not source, so a docs-only fix needs no test. A test changed in one commit and renamed unchanged in a later one still counts at its new path. `--no-test "<reason>"` lets a fix without a test through (`FIXTEST_WAIVED`), its reason kept as `waiver` in the tests receipt; nothing waives the identity check. A fix whose test sits in another commit passes with `FIXTEST_NOTE`. A pass prints `CHECKS_OK <pr> head=<sha> identity=<ok(N)|skipped> fix-test=<no-fix|tested|waived>`.

`review` reads the PR's head (`gh pr view --json headRefOid`) and refuses (`REVIEW_REFUSED`) unless `--dir` (default: the current directory) is a git checkout at that head with no changes, so the review and the tests read the code that would merge. It runs `mergeGate.testCommand` there first: a failing run writes no receipt and stops (`REVIEW_TESTS_FAILED`, no review); a passing one prints `TESTS_OK`. Then a fresh reviewer run (`explore.challengeCommand`: no session, read-only tools, cwd the checkout) of a `reviewers.models` id of another family than the lane's model (the pane's lane, or `--lane`; `--model` picks one, also of another family: `reviewers.allowSameFamily` is for `challenge` only) gets the diff (and, when an earlier head of the PR was reviewed, that review's findings and the diff since it, to check the fixes first; each part has a byte budget that keeps the prompt under the 128 KiB a single argument may have, and a cut names the saved file with the rest) and ends with `VERDICT: CLEAR` or `VERDICT: BLOCK` on its last line; ids the host cannot call, or a reply without a verdict, go on to the next reviewer. The checkout and the PR head are read again after the tests, after the diff and after the review: a test run that changes files or a push meanwhile writes no receipt. It prints `REVIEW <pr> head=<sha> verdict=<v> reviewer=<id> in <s> s review=<file>` and exits 1 on `BLOCK`. Receipts are `<stateDir>/receipts/<owner>__<repo>_<N>@<sha>.<review|tests|attempt|merge>.json` (repo lowercased; `attempt` records a merge whose outcome was not read back, `merge` one read back as done; only `merge` counts), the review text and the diffs under `<stateDir>/receipts/reviews/` (state-git keeps the receipts and the review text, not the `.diff` files: GitHub rebuilds them, and a PR's test fixtures look like tokens).

A reviewer that gives no verdict (exit 0 with no `VERDICT` line, or a nonzero exit) writes no receipt; its stdout tail (the last 200 lines, at most 16000 characters, known secret patterns masked) goes to a private file `<stateDir>/reviewer-output/<label>-<uuid>.txt` (mode 0600, folder 0700, never backed up by `state-git`), and its `REVIEW_SKIP` / `REVIEW_FAILED` part ends `reviewer stdout kept in <path>` (`reviewer stdout was empty` when there was none; a nonzero exit is named by its code and its masked stderr, never its stdout); `intent-check` (`INTENT_CHECK_FAILED`) and `directives check` (`DIRECTIVES_MEANING_FAILED`) do the same, instead of quoting the reply's first 80 characters (dori-superagent #71). Masking lowers the risk; it does not prove every secret or personal detail is gone.

`merge` refuses with `MERGE_REFUSED <reason>` (exit 1, nothing merged) when the PR is not open, is unsupported, the current head has no review receipt (when an earlier head has one it says the last review was at that commit, so commits came after it), the review is `BLOCK`, or there is no passing test receipt at that head. Then `gh pr merge --squash --match-head-commit <head>`: GitHub refuses it when the head moved after the gate read it (`MERGE_FAILED`). The PR is read back whatever gh said: merged at the reviewed head is `MERGED <pr> head=<sha> merge=<merge sha>` with its merge receipt even when gh then failed on `--delete-branch`; a merge GitHub only queued is turned off again with `--disable-auto` and refused; a read-back that fails is `MERGE_UNCONFIRMED`: the attempt is recorded (`attempt` receipt) but does not count, because GitHub cannot tell a `dori merge` from a plain merge by the same account; the lane tells the lead, who decides with `dori done-set`. `claim-done` and the close (after the signals read back live) look for the merge receipt (`mergeGate.repos`), so a lane that claims before its merge and then merges with plain `gh` is still refused at the close. `--dry-run` prints `MERGE_OK` and merges nothing.

### `dori fork-explore <key> --metric M --hypotheses H1 --test T1 --hypotheses H2 --test T2 ... [--gpu N ...|--gpu-all] [--mode agent|cmd] [--minutes N] [--model M]`
Parallel branch exploration: one short, time-boxed task per hypothesis (at least two), all measuring the same metric M. With `--mode agent` (default) each branch is a headless agent run, `explore.branchCommand` in the lane's cwd, told its hypothesis, the metric, its test, the time limit (`--minutes`, default `explore.branchMinutes`), not to edit tracked files, and to end with `METRIC:`, `VERDICT: supports|falsifies|inconclusive` and `EVIDENCE:` lines. With `--mode cmd` each `--test` is a command run with `bash -lc` in the lane's cwd, which prints the same lines. CPU branches start at once. A GPU branch (`--gpu <branch number>`, repeatable, or `--gpu-all`) first takes a heavy slot, the same slots and load limit as `dori heavy`, so GPU branches queue one by one while CPU branches run. A branch that runs out of time is `timeout`; one that fails without a verdict is `error`. It prints `FORK_START ...`, then one markdown table (branch, hypothesis, metric value, verdict, evidence, run time, cpu or gpu with the slot wait), and `FORK_SAVED <file>`. The table and the raw results go to `<stateDir>/explore/<key>/<time>.md` and the lane's `explorations`; each hypothesis goes into the tree as falsified (falsifies), supported (supports) or open with the result noted; the watch log gets `FORK_EXPLORE <key> ...`.

### `dori research-hint <key> [--send]`
A search plan for the lane's stuck symptom, from its records only (no model call): `RESEARCH_HINT <key> on "<metric>": N attempts, ...`, the symptom and last report, what was already tried, four or five queries (papers, GitHub issues, failure-mode write-ups, how other repositories set the same problem up, other causes now that a hypothesis is falsified), and the `dori tree add --kind finding` line to record what was found. Works on closed lanes too.

With `--send` (and at rung 3 of the stuck ladder, when `explore.sendResearchToLane` is on) it types `explore.researchText` into the lane's pane as one line. The text starts with `ulw research `, so omo attaches its ulw-research skill pointer, and the lane runs the search as an ultra research: sources read in the owner's browser, a claim graph, a cited result. omo attaches that pointer only to typed (interactive or rpc) input that names `ulw research` outside quotes, code and links. It never attaches it when the text starts with a `[TAG]` such as `[LEAD]`, nor in a child or team-member session, and a brief that mentions it does not count. `{question}` is the research question built from the lane's records: the exact symptom (the metric that does not improve, the last report), what was tried, what a test ruled out and how, what is still open, and what to look for (papers, GitHub issues and discussions, repos that hit the symptom). The rest of the default text tells the lane to read the ulw-research SKILL.md first, record findings with `dori tree add --kind finding`, have its next plan challenged with `dori challenge`, and report back before the next patch. It prints `RESEARCH_SENT <key>` (or `RESEARCH_SEND_FAILED`, exit 1) and records the send in the lane's `research`.

### `dori research-check <key>`
Did the last ulw research text start the skill? It looks in the lane's session directory (`sessionsDir/--<cwd with / as ->--/`) for the newest `*.jsonl` written since the send that holds a user message starting with the typed text. From the send on, it looks for two markers:

- the pointer: an entry `{"type":"custom_message","customType":"omo-ulw-research:skill-pointer",...}`, or `<omo-ulw-research-pointer>` inside the typed user message (omo appends it there when the agent was busy);
- the skill read: an assistant `toolCall` block that reads the file, not one that only names it: the `read` tool with a path ending in `ulw-research/SKILL.md`, or an `eval`/`bash` call whose code holds the file's path (`/...`, `~/...`, `./...`, `${dir}/...`) as a whole string literal and reads a file with it (`Bun.file`, `readFile`, `readFileSync`, `createReadStream`, or `cat`/`sed`/`head`/`tail`/... on an interpolated path), or runs `cat`/`sed`/`head`/`tail`/`less`/`awk`/... on the path itself. A finding written with `dori tree add`, an `echo`, a memory note, or a log search that quotes the path is a mention and does not count. Only a read after the typed message reached the session counts for this send: a lane still busy with an earlier send may read the skill after the send but before it gets the new text, and that read counts as an earlier read.

Both markers: `RESEARCH_STARTED <key> ...`. Not yet: `RESEARCH_PENDING <key> N min ...: seen=… pointer=… skill-read=…`. Still missing after `explore.researchVerifyMin`: `RESEARCH_NOT_STARTED <key> ...` (exit 6), with what is missing (the text never reached the session log, omo attached no pointer, or the lane did not read the skill; a lane that read it earlier in the same session often does not read it again and answers without the skill's protocol, and the line says so) and the fix (re-send with `--send`, or tell the lane to read the SKILL.md). `dori freshness` runs the same check on every tick for a lane with a pending send and prints `RESEARCH_STARTED` / `RESEARCH_NOT_STARTED`. The decided line goes to the watch log once (source `research`), and the result is kept in the lane's `research.result`.

### `dori repeat-check <key> [--since ISO|Nd|Nh] [--until ISO] [--repo DIR ...] [--backtest]`
Untagged repeats, the inferred half of the stuck count. Lanes rarely tag their fixes, so a tagged count stays low while a lane re-targets one failing gate with prescription after prescription. This reads what the lane leaves anyway: its `[REPORT]` lines (in its own session folder, `<sessionsDir>/--<cwd>--`, and in `scorecard.leadSessions`), the commit subjects on its branches (`worktrees`, its cwd if that is a repository, and `--repo`) and its hypothesis-tree entries. A gate line fails when an item carries a value and `FAIL` (`교착 554 FAIL(≤2)`, or the items of a bare `FAIL 도랑 위 덤프 1·교착 58` list up to a dash), or when a prescription's verdict (`기각`, `판정 불가`, `REJECTED`) names a known metric in its sentence. A new attempt targets it when one sentence (`autoSignals.targetScope`) holds a prescription word and the metric's name or an alias, and is not negated ("안 띄움", "not launched") or only a diagnosis; a failure is never consumed by the report that states it. Each "failed, then a new attempt on it" is one cycle; attempts within `autoSignals.repeatGapMin` are one; a `PASS` of the metric starts it again. From `stuck.researchAt` cycles it prints `INFERRED <key> "<metric>" <n> (from untagged ...; tagged <t>) ...` with every failure and attempt line as evidence, else `REPEAT_NONE` with the counts. In `freshness` the counts and each metric's last PASS are kept in the lane's `inferred`, a grown count's full chain is appended to `<stateDir>/auto-signals/<key>.md`, and every changed metric takes a step of the stuck ladder (its `STUCK` line, if the rung went up). A PASS before the sweep ends the run, so no line. Default window: the lane's current session. `--backtest` replays the window and prints each time a count reached `stuck.researchAt` or grew past it, with its time.

### `dori intent-check <key> [--direction TEXT] [--next TEXT] [--goal G]`, `dori intent-check <key> --reread`
Prints the owner's goal (the lane's `goal`) next to the lane's current direction and next step. The direction is what the lane last stated with `--direction` (stored in the lane's `direction` with `--next`), else its last report; the next step is `--next`, else a "next:" in the report, else the test of its first open hypothesis. `--goal` sets the goal of a lane launched without one. Then a reviewer of another family than the lane's (`reviewers.models` with `reviewers.first` in front, checked like `challenge` reviewers) gets the stated direction and next step, the lane's brief (without the Past signals and tree sections launch adds), the owner's goal, the lead's `[LEAD]` relays that carry the owner's words (a Discord message link, or marked 원문 / verbatim), the owner's own decisions in the lane's `discord:<id>` thread from the inbox (question-card answers and the owner's messages, author `DORI_DISCORD_OWNER`; the inbox is `handover.inbox`, `DORI_DISCORD_INBOX` or `<stateDir>/discord/inbox.jsonl`; the newest `autoSignals.intentCheck.relays`; when other lanes in the registry share the thread, only the messages tied to this lane: one the lead linked in a `[LEAD]` relay to it or in its brief, a reply to its own post (the `SENT` / `POSTED` id its sessions printed) or to a card its pane asked (`questions.json`), an answer to its card, one naming its key, or one sent while no other lane had the thread open; one tied to another lane the same way is left out, and one tied to none, or both ways, goes to the reviewer as context only, and a finding that quotes either is dropped as `INTENT_CHECK_SHARED` with the message id and why, no rung) and the newest reports, all dated (on one subject the newest owner decision wins, and a later report replaces an earlier report's state) and as written in Korean or any language, and answers in blocks `VERDICT: VIOLATION | CONTRADICTION | GOAL_LOSS`, `OWNER: "<quote>"`, `REPORT: "<quote>"`, `WHY: ...`, or `VERDICT: OK`. The prompt also carries the registry's fact on a done claim (`Done claim on record: none ...` or the claim's time and evidence): a report that only names `dori claim-done` or quotes the footer is not a claim, and only reports that were sent (a `send-keys`, `send-text` or `dori type` call) or received (text typed into the session) are read, so a report template quoted in a goal, brief or note is no report. Every finding is checked against the inputs before it counts. Its owner quote must be in the owner's words: the goal, an owner decision, the quoted parts of the brief and of the relays (`"..."`, `'...'`, `“...”`, `‘...’`, `「...」` of 6+ characters), or an owner message a brief or relay links (`discord.com/channels/.../<message id>`, read from the inbox, author `DORI_DISCORD_OWNER`), or the owner's built-in blocks the brief carries (the eight steps, the UI steps; a line in parentheses under a step is the lead's rule). Other text outside quote marks is the lead's, and so is a card's question (only the owner's choice counts); a `CONTRADICTION` may also quote a fact the brief states. Relays are read only from the lane's own sessions (session files that carry its `[REPORT] <key> |` lines), not from other lanes in the same cwd, and the brief is read without the sections launch adds (Past signals, Hypothesis tree, Lane footer). A finding whose owner quote is not there is dropped and logged as `INTENT_CHECK_UNGROUNDED <key> <kind> owner "..." ... dropped, no rung`. A finding whose report quote (each piece, when it is joined with `…`) is only in reports an earlier check already read (at or before the last check's `lastReportAt`), or in a direction stated before the last check, is dropped too, as `INTENT_CHECK_STALE <key> <kind> report "..." ... not flagged again, no rung`. A check whose findings were all dropped leaves the ladder as it was, and keeps the last finding on record only while that finding's own owner quote still holds. Prints `INTENT_CHECK <key> <kind> owner "..." vs report "...": <why> [reviewer <model>]`; a report quote not found in the reports read adds `(unverified: ...)`, and so does a CONTRADICTION resting on the claim-done command while no claim is on record. An unverified finding goes to the watch log as that `INTENT_CHECK` line and stays off the ladder. A verified finding is the stuck ladder's context rung: it prints and logs one line, `STUCK <key> "@context" rung context (<kinds>: owner "..." vs report "...": <why>; reviewer <model>) -> confirm the finding, then dori intent-check <key> --reread ... [INTENT_CHECK_<kind>]`; a finding on a report (or a stated direction) written after a re-read you confirmed with `--reread` is `rung 4` (`[... ROLLOVER_DUE]`; without a re-read it stays the context rung; the context mark keeps the report under the finding, so the same report never moves it twice), and a clean check (`INTENT_CHECK <key> OK ...`, logged as such) ends the context rung. It runs whenever the lane asks: no interval and no new report needed (the stated direction is in the prompt and counts as evidence a finding may quote). A reviewer that fails or answers out of format is skipped for the next; none left is `INTENT_CHECK_FAILED` (exit 1). The result is kept in the lane's `intentCheck` (with the first finding). Nothing is sent to the lane by the check. `--reread` is your confirmation of the last finding: it types `stuck.rereadText` into the lane (its brief path and the finding filled in) and prints `REREAD_SENT` (or `REREAD_FAILED`, exit 1); after a clean check it refuses (`REREAD_REFUSED`, exit 1).

The owner's words of the directives in scope (the directive ledger, judged on the lane's brief, cwd repo and `--ui` as `dori directive-audit` does) go to the reviewer under OWNER DIRECTIVES and count as the owner's words a finding may quote, so a direction or report that breaks one is a `VIOLATION`; a directive missing from the brief is the audit's `DIRECTIVE_GAP`, not this check's.

It replaced a count of shared words with the goal, which could not judge a Korean goal at all (an English report of the same step scored 0.00). Until 2026-11-02 the same reviewer also ran from `freshness` on every lane's new reports (`dori owner-check`); the owner removed that (card Q442: one finding in 1,066 runs over 30 days stood after review), so a reviewer reads a lane only when it states its direction here.

### `dori scorecard [--date YYYY-MM-DD|today|yesterday] [--post] [--to discord:<id>]`
Prints the day's token scorecard, computed from records only (no model call), for the calendar day in `scorecard.timeZone` (default today):

1. cost per verified completion: the API-priced cost of every assistant call in `scorecard.sessions` (default `sessionsDir`) that day, over the lanes closed that day (a close always re-reads the Done signals);
2. the done-claim rejection rate, always next to line 1, since either alone can be gamed: claims that day, and the `not-done` entries that answered a claim (a lane parked as not-done is not a rejection; a repeated claim counts once);
3. the three lanes with most rework: the lead's messages to the lane (`leadSendPattern` in `leadSessions`) plus freshness nudges (`lanesLog`);
4. first reply to the owner: median and p90 seconds from an owner message in the inbox to the first lead tool result matching `replyPattern` after the message reached the lead session;

plus the lead's context tax: its cost, the share spent re-reading cache, and its median context size. A line whose source is not configured says so. Each run saves the card for the lead to read (`SAVED <path>`): `<stateDir>/scorecard/<date>.json` (the numbers and the card) and `latest.md` (the card); day files older than `scorecard.keepDays` are removed. Nothing is posted unless `--post` is given, which sends the card to `--to`, `scorecard.postTo` or `DORI_DISCORD_CHANNEL`.

### `dori close <key> [--note TEXT] [--summary TEXT] [--lesson TEXT [--evidence PATH]]...`
Closes a lane now. Refuses (exit 2) unless every `Done =` signal reads back live; when the plan changed after launch and the line is stale, change it with `dori done-set` first. `--note` goes into the lane's record only. A lane with a work thread then needs a summary for the owner: `--summary`, else the one the lane gave with `claim-done --summary`, else one a reviewer model writes (`reviewers.first`, then `reviewers.models`, at most three, with `reviewers.command` and `reviewers.minutes`) in the owner's language (`discord.locale`, in `discord.ownerSpeech`; a lane's summary refused as it is, e.g. in 존댓말 for a 반말 owner, is rewritten from that summary alone, its facts kept) from the lane's last report, its claim and the end of the `REPORT.md` next to its brief: what changed, what is left, when it reaches where it is used. A text with a local path, a commit hash, backticks or a `[REPORT]` head, over 700 characters, or not in Korean under a `ko` locale does not count (`--summary` such a text: `SUMMARY_REFUSED`, exit 2). None: `CLOSE_SUMMARY_MISSING <key>: <why>`, exit 2, nothing posted or changed. The summary is posted in the thread first, straight to Discord when `DORI_DISCORD_TOKEN` is set and the thread is `discord:<id>`, else through `hooks.threadDone`; a post that did not go out is `CLOSE_SUMMARY_NOT_SENT <key> <thread>: <error>`, exit 2, and the thread keeps its mark (no thread hook and no token: the same, nothing can post). Only after it went out (`CLOSE_SUMMARY <key> from the lane|model <id>`) is the thread marked done: when `DORI_DISCORD_TOKEN` is set and the thread is `discord:<id>`, it sets the thread's name to the done mark (`✅` or `[done]`, per `discord.statusStyle`) and archives it. An archived thread is unarchived, renamed and archived again, because Discord refuses to rename an archived thread; a thread that already shows done and is archived is left alone. If that fails, `THREAD_DONE_WARN <key> <thread>: <error>` is printed and the close still succeeds. A thread that another open lane also uses, or that has an open question card, is left as it is: `hooks.threadDone` does not run and the thread is not renamed or archived; the lane's summary goes there as `<title>: <summary>` instead, posted straight to Discord when `DORI_DISCORD_TOKEN` is set, else through `hooks.threadReply` (run with `DORI_CLOSING_LANE=<key>`, so `dori thread reply` does not count the closing lane as working) (`thread left open: open lane <key> uses it too` or `open card <Qn>`, then `summary posted`, in the receipt; a post that fails is `CLOSE_SUMMARY_NOT_SENT` and the lane stays open). With the token, once the lane is recorded closed, the thread is asked for waiting through the thread status queue when what is left waits on the owner, an open card or a paused lane (cards and lanes are read again then, so a card answered during the close does not count): it turns ⏸️ (`waiting requested: applied|unchanged|pending|dropped` in the receipt; the queue prints `THREAD_STATUS_APPLIED`). A rename Discord holds back (`pending`, kept for the listener) or refuses (`dropped`) prints `THREAD_STATUS_WARN <key> <thread>: waiting requested: <outcome>` before `CLOSED`. While another lane there is working, not-done or done-claimed (the lead still decides), the mark is left as it is. `dori resume` of a lane in a `discord:` thread asks for working again, so a thread left ⏸️ beside a paused lane turns 🔄. The last lane to close with nothing else on the thread marks it done. Then it closes the tab, and removes the lane's worktrees with a plain `git worktree remove`, which refuses a dirty worktree. When `hooks.threadDone` is set but the lane has no usable thread (`none`, empty, or malformed), the hook is not run and `THREAD_MISSING <key> thread=...` is printed before `CLOSED`, and the receipt records `thread missing`; close that thread by hand, or run `dori set-thread` before closing. The automatic close in `dori watch` prints the same line before `LANE_CLOSED`.

`--lesson TEXT` keeps a lesson for the lane's repo (see `dori lesson`) once the lane is recorded closed, its evidence `--evidence PATH` or else the lane's `Done =` line: `LESSON <id>`. Give `--lesson` once per lesson to keep several (one `LESSON <id>` line each, in order): each takes the `--evidence` in its place (`--lesson A --evidence a --lesson B --evidence b`), one `--evidence` serves them all, none means the `Done =` line; any other count of `--evidence` is refused before the close (`LESSON_EVIDENCE_MISMATCH <key>: ...`, exit 2, nothing closed). A lesson never blocks or undoes the close: one that cannot be kept prints `LESSON_WARNING <key>: <why>` before `CLOSED`, and the others are still kept. A refused close keeps no lesson.

### `dori lesson add <key> --rule TEXT --evidence PATH [--cwd DIR]` / `lesson add --global --rule TEXT --evidence REF` / `lesson list [--cwd DIR]` / `lesson mark <id> --outcome ...`
From dori-superagent #65 and #97 (global lessons, https://github.com/sisyphuslabs/dori-superagent/pull/97; `src/lessons.ts`, ported unchanged). A lesson is one rule a lane learned about its repo (a test needs `env -u DORI_STATE_DIR`, a pager hangs a command), tied to the evidence that taught it and to the repo: the lane's `cwd` (or `--cwd`), resolved to a real path. A `--global` lesson is the lead's standing rule for every lane, whatever its repo: it has no `cwd`, is recorded as `lane: "lead"`, and `dori launch` puts up to 4 current ones into every brief. Since it reaches every future brief, it is the lead's: `--global` with a lane key or `--cwd` is refused and writes nothing. So are `--global` and `lesson mark` on a global lesson when run from a pane that a registered open lane owns (`$HC_TERMINAL_ID`, else `$HERDR_PANE_ID`, else the tmux session, found as `claim-done` finds its lane); repo lessons stay markable from lanes. The pane check is a convenience that stops a lane from adding or reviving a global lesson by accident or on routine instruction, not a security boundary: `env -u HERDR_PANE_ID` gets past it, and a direct write to `lessons.jsonl` skips the CLI. `lesson list` shows the global lessons with any `--cwd`. `add` works for a closed lane too and prints the record. The next `dori launch` with the same `--cwd` puts up to 8 of the newest `pending` or `helped` lessons there into the brief (see `dori launch`). `mark` records whether a lesson `helped`, had `no-effect`, was `harmful`, or is now `encoded` in a test, lint or doc; only `pending` and `helped` reach new briefs. Lessons live in `<stateDir>/lessons.jsonl`, one record per change: a mark appends, it never rewrites history. A rule is one line of at most 400 characters. A damaged line (not JSON, an unknown field, a malformed field, or a change to a lesson's fixed fields) is skipped and named: `lesson list` and `launch` print `LESSON_WARNING <path>:<line>: <why>` and the other lessons still load. A standing instruction of the owner is not a lesson: it goes into the directive ledger.

### `dori worklog add <title> --source REF` / `next <id> <text>` / `note <id> <text>` / `close <id> --result TEXT` / `list [--open]`
From dori-superagent #96 (https://github.com/sisyphuslabs/dori-superagent/pull/96, `src/worklog.ts`, ported unchanged). The lead's record of owner requests, so an open request survives a restart, a compaction or a handover. `add` records a request when it arrives, with its source (`discord:<channel>/<message>`, `slack:<channel>/<ts>` or any reference to the message) and prints the item with its 8-hex-digit id. `next` replaces the item's next step, `note` adds a dated note (a decision, who owns it), `close` records the result and ends the item; a closed or unknown item is refused. Each text is one line, without control characters (C0, DEL, C1) or the Unicode line and paragraph separators. `list` prints the items as JSON (`--open` only the open ones), oldest first.

The record is `<stateDir>/worklog.jsonl`, one append per change, so the lead and a lane can write at the same time without losing one; a write cut off halfway damages only its own line, which every reader skips quietly as a normal result of the design (a line that does not parse but begins like a record, `{"op":"`). Fork change (review of orientpine#352): every append starts with its own newline, in the same write, so a torn record another writer leaves at any moment never swallows the next record; the blank lines between records are skipped. An `op` that is not one of the four own names (`toString`, `__proto__`) is damage, never a close. Any other bad line is real damage: `list` names it as `WORKLOG_WARNING <path>:<line>: <reason>` and skips it. If two writers close the same item at once, the first close in the record wins and a later `close` is a no-op; a `next` or `note` after the close lost the same race: it is skipped and `list` still names it as a `WORKLOG_WARNING`. After every change `<stateDir>/worklog.md` is rendered from the whole record (temp file and rename) for the lead to read: one heading per item with Source, Opened, Next, Notes and, once closed, Closed and Result, open items first. A render that raced another writer's append renders again, so the file always ends up holding every item. Edit through the command, not the file: a `worklog.md` that the command did not write (no marker on its first line) is never replaced (the marker is checked before the append and again right before the rename, and a publish that finds it gone is skipped), and every change is refused until it is moved aside.

### `dori boot`
Run by the lead after a restart or a compaction, before trusting remembered lane state. Boot is read-only: it does not write the registry or state files, relaunch a lane, stop a watch, or restart a service. It prints:

- `RUNTIME <kind> (from <source>)` first: the runtime new lanes open on and why (`env`, `config`, `detect:HC_TERMINAL_ID`, `detect:HERDR_PANE_ID`, `detect:path`, or `default`). `RUNTIME unavailable: <fix>` when none can be chosen, and boot then exits non-zero before any other check.
- `SLACK authenticated user=... team=...` from `auth.test` when `DORI_SLACK_TOKEN` is set (`SLACK skipped` otherwise). This proves the token, not message delivery. It runs last, after the local checks, and gives up after 10 seconds (`SLACK auth.test timed out after 10000 ms`). A response without a user or team id, a request failure, or a timeout is `SLACK auth failed` (a timeout names its deadline) and makes boot incomplete. Provider error text is not printed.
- `PANES` with the lead pane's state, then `VANISHED <key> pane=...` for each unfinished lane whose pane is gone and `UNREGISTERED <panes>` for live sessions no open lane owns. Sessions are listed on every runtime a lane lives on (`herdr pane list` / `hc ls`); if that list fails, the result is `PANES unavailable (session list failed)`, never evidence that every lane vanished.
- `DRIFT n=<count> <keys>`: lanes not `closed` whose session the runtime's own probe reports gone (`herdr pane get`, `hc get`). Only lanes missing from the session list are probed. Any drift fails boot; a probe that errors is `DRIFT probe-failed <key> (...)`, is not counted as drift, and also fails boot.
- `CONFIG_WARN workspaces=[...] does not include laneWorkspace=...` when `config.workspaces` is set and leaves out `laneWorkspace`, or `CONFIG_WARN workspaces=[...] match none of the <n> live agent sessions ...` when live agent sessions (in `laneWorkspace` when set, the lead and `ignorePanes` aside) exist and none is in `config.workspaces`: `dead-panes` and `sync` filter on that list and would watch nothing. Checked only on a runtime with workspaces (herdr; hc has none). It fails boot.
- `REPORT <key> kind=... at=... state=...` for each launched (`jsonl-v1`) lane's last report, next to its registry status. A journal that holds only harness activity is `NO-REPORT <key> ... (journal holds harness activity only)`, and a launched lane with no journal is `NO-REPORT <key> ... (no journal)`. An adopted lane's journal is not read. An unreadable journal is `JOURNAL-ERROR <key>: ...` for that lane only; the other checks still run.
- `WORKLOG open=<n>` and an `OPEN <id> "<title>" source="<ref>" next="..."` line for each open worklog item. A damaged line is `WORKLOG damaged <path>:<line>: <reason>` and fails boot; a `next`/`note` after a close is `WORKLOG warning ...` and does not. A torn write left by a crash and a duplicate close left by racing writers are not damage.
- `MONITORS cleanupCandidates=... deliveryPaused=... expired=...` and, for each persistent watch tied only to finished lanes, `CLEANUP <keys> match=...` plus `STOP in the owner session only: kill_bash(...)`. Expired watches are `EXPIRED ...; nothing to stop`. Metadata is read from `<sessionsDir>/*/extensions/terminal` and the current session's `PI_SESSION_DIR` / `PI_SESSION_FILE`; an unreadable manifest is `MONITORS unreadable <path>` and does not hide the others.
- `BOOT checked read-only; nothing restarted, written or stopped` when every input could be read, else `BOOT incomplete ...` and exit 1.

Open worklog items are printed by `dori boot` and can also be read with `dori worklog list --open` (or `worklog.md`). `dori handover` puts them into the new lead's note under "Open worklog items" (see `dori handover`).

### `dori watch`
Runs forever. Every 30 seconds it prints each new claim once (`LANE_DONE_CLAIMED`). A claim is taken back when the lane gets new work before it is settled: the lead types into the lane with `dori type` (`type LANE_CLAIM_REOPENED <key> <pane> the lead typed a new instruction into the lane (dori type)` in the watch log), or (omo on aoe or herdr) the lane's main turn runs again after it sat idle for 45 s since the claim (`LANE_CLAIM_REOPENED <key> <pane> the lane ran a new turn after it sat idle since <time>`; the turn that answers the claim's `[LEAD]` line and a goal wake come before that and do not count). The lane is working again, is told `[LEAD] your done claim for <key> is taken back: ...` and claims again when that work is done; nothing closes it on a timer meanwhile. Claims older than `closeAfterMin` are settled: unpushed or uncommitted work and failing signals turn into objections (`LANE_NOT_DONE`); otherwise the lane is closed (`LANE_CLOSED`). The thread gets the lane's summary for the owner as `dori close` posts it (the claim's `--summary`, else one a model writes; see `dori close`), never the claim's evidence (that stays in the lane's record and the `LANE_DONE_CLAIMED` line), and is marked done only after it went out (`CLOSE_SUMMARY <key> from ...` before `LANE_CLOSED`). No summary or a post that failed prints `CLOSE_SUMMARY_MISSING` / `CLOSE_SUMMARY_NOT_SENT` for the lead and objects to the claim: the lane hears `[LEAD] not done: ...` with the `claim-done ... --summary` line to send, and a new claim starts a fresh window. ### Lane caps and hung calls (`supervision`, `dori caps`)
Ported from dori-superagent #61 (`src/supervision.ts`) and rewritten on this fork's registry and freshness sweep. Upstream appends a blocker to a per-lane report journal (its #30), which this fork does not have; here the lead gets a note instead.

Each `freshness` sweep looks at every working lane with a pane, and at every lane told not done (it keeps working):
- **Caps.** `wallMinutes` since the lane opened, and the `tokens` and `costUsd` it used. The caps in force are `supervision.defaults`, then `supervision.lanes.<key>`, then the lane's own (`launch --wall-minutes N|none --token-limit N|none --cost-limit N|none`, or later `dori caps <key> ...`). `null` (`none`) turns one off. All are off by default, so with no config nothing is capped. Reaching a cap prints `LANE_CAP <key> <name> ceiling reached (<cap>); lead told` and types one `[DORI]` note into `leadPane`. The lane is never stopped, closed or typed into: the lead decides whether it goes on (raise or clear the cap with `dori caps`), wraps up, or closes. Each alert goes out once. A note that did not reach the lead (or found no `leadPane` configured) is sent again on the next sweep, and a raised cap alerts again only when the new one is reached.
- **Usage.** Tokens and cost are read only when a token or cost cap is set, or `supervision.usageArgv` is. By default they come from the omo transcripts of every session the lane had: its current `session` and the `priorSessions` a handover keeps on the lane, found by id anywhere under `sessionsDir` (ids are unique, so a symlinked cwd or an adopted lane's own cwd does not matter). Whenever a lane's `session` changes, by any path (handover, a move kept after the old session died, recovery of an interrupted move, `sync --write`), the registry keeps the outgoing one in `priorSessions`. A move whose new session is not known yet leaves the lane with no current session, and its usage reads unknown until `sync --write` finds it. A lane with no recorded session reads the transcript of the session in its pane. The total is the assistant turns' `usage.totalTokens` and `usage.cost.total` since the lane opened. A session whose transcript is missing leaves the usage unknown. `supervision.usageArgv` replaces that with a command (`{key}`, `{session}`, `{cwd}`) printing cumulative `{"tokens": N, "costUsd": N}`. Unknown stays unknown, never 0: a cap that cannot be checked prints `USAGE_UNKNOWN` and tells the lead once. Readings go to `<stateDir>/lane-state/<key>/cost.jsonl`.
- **Hung calls.** A `Working` or `Running` timer on the lane's screen (omo's `Running bash (25m ...)`) can keep growing from the same start for `supervision.hungAfterMinutes` (20) while there is no new report, checkpoint or file change for `supervision.staleAfterMinutes` (20). An `activityPaths` entry that is a symlink counts both writes through it (its target's size and times) and a retarget of the link itself, and these entries are always looked at, ahead of git's changed files. Then freshness prints `STALLED <key> ...` and tells the lead once; nothing is sent to the lane. A cap and a hung call are told apart, each once: a lane already told about its cap that then hangs is told that too. File changes are git's changed files under the lane's `cwd` (`supervision.gitActivity`; git's paths are taken from the repository's top, so a lane in a subdirectory counts), every untracked file listed (a file written inside an untracked directory counts; at most 5000 paths are looked at), leaving out `node_modules` and paths outside `cwd`, plus `supervision.activityPaths` and `launch --activity-path FILE`. `hungAfterMinutes: 0` turns this check off.

A malformed `supervision` entry stops every command with `CONFIG_INVALID ... invalid supervision...`, so a typo cannot turn a cap off. That covers a misspelt name such as `toknes`, a cap that is not a number >= 0 or null, a `lanes` entry that is not an object, and an argv that is not a list of strings. An unreadable `supervision.json` (a crash mid-write) is started over and printed once as `SUPERVISION_ERROR <key> ... started over`. ### `dori state-git [init|commit|log [N]|restore <time|commit> [--file PATH ...]|loop|check|backup <step>|push-check] [--dir DIR ...]`

On one host: ZzangDori `~/.dori` and `~/.zzangdori`, OkDori `~/.okdori`, MooDori `~/.moodori`. The repos stay on the host unless `stateGit.backup.repo` names this Dori's private GitHub repo; the `pre-push` hook (`state-git push-check`) refuses every other push.

A file committed before a new default covered it is taken out of the index on the next run and stays on disk (`STATE_GIT_UNTRACK <dir> <n> file(s) ...`).
- `commit` stages what changed and commits `state: N files: <names>` (`STATE_GIT_COMMIT <dir> <sha> <n> file(s) <ms>`); nothing changed is `STATE_GIT_NOCHANGE`, no commit. A staged file named like a secret or whose content has a token shape (Discord, GitHub, Slack, API keys, Google, AWS, Telegram, private keys, `Bearer`, `*_TOKEN=`, `password:`/`비밀번호:`) is not committed, the rest is: `STATE_GIT_REFUSED <dir> <file> <kind>`, once per content. A manual `git commit` in the repo is checked the same way by the `pre-commit` hook (`state-git check`).
- `restore` takes a commit or a time git reads (`"2026-10-16 21:00"`, `"yesterday 21:00"`, `"3 hours ago"`) in `stateGit.timeZone` (default `scorecard.timeZone`), for every repo of this Dori; it commits what is there first, puts the tracked files (all, or `--file`) back as they were at the last commit at or before it, commits that, and prints `STATE_GIT_RESTORED <dir> to <sha> (<time>); undo: dori state-git restore <sha> --dir <dir>`. Ignored files (env, inbox, logs) are never touched, also when the commit restored to still held them (a file committed before an exclude covered it).
- `loop` is what `dori-lanes.sh` runs beside the other sweeps: `STATE_GIT_READY <dirs>`, then every `stateGit.everyMin` minutes `init` and `commit` for each directory in its own process; git runs under `nice -n 19 ionice -c3` and is killed after `stateGit.timeoutSec`, a failure is one `STATE_GIT_WARN <dir> <why>` line, an `index.lock` older than twice the timeout is removed (`STATE_GIT_UNLOCK`), nothing changed prints nothing, and it never exits (`everyMin: 0` prints `STATE_GIT_OFF` and idles). No lane or lead step waits on it.
- `backup` (owner 10-18 00:19 KST: "로컬 도리들은 비공개 레포로 올려두기 그리고 푸시는 대기 상태일때 새벽6시에 수행"): one private repo per Dori, one branch per directory (`~/.dori` -> `dot-dori`, `~/Documents/zzangdori` -> `documents-zzangdori`). What is pushed is a snapshot of the repo's HEAD with every refused file left out, committed on `refs/dori-backup/<branch>` (one commit per push that changed something); the local history never leaves. Steps: `create` makes the repo with `gh repo create --private` and checks it is private (`BACKUP_REPO_OK` / `BACKUP_REPO_NOT_PRIVATE`); `preview` prints `BACKUP_SECRETS <n> secret values (never printed)` and per directory `BACKUP_PREVIEW <dir> -> <repo>:<branch> <n> files, left out <m>, history secrets <k>`, with the paths, what is left out and why, and history hits in `<stateDir>/state-git/backup-preview/<branch>.txt`; `approve --by "lead: <why>" [--history-ok "<dir>:<path>" ...]` records the lead's go for the first push (`<stateDir>/state-git/backup-approved.json`); `push` pushes now; `tick [--clock <ISO time>]` runs one step of the schedule.
- The loop runs the schedule after its commits: from `at` (06:00 in `stateGit.timeZone`) it checks for a quiet moment (the lead's and every open lane's pane not mid-turn, no live heavy slot, no `index.lock` or `dori-state.lock`); busy is `STATE_GIT_PUSH_DEFER <day> <time> busy: <why>; next try <time>` and another try `retryMin` later, none left at `until` is `STATE_GIT_PUSH_SKIP` for the day. A push is `STATE_GIT_PUSHED <dir> <repo>:<branch> <sha> <n> files`, nothing new `STATE_GIT_PUSH_NOCHANGE`, no approval yet `STATE_GIT_PUSH_WAIT_APPROVAL`, a failure one `STATE_GIT_PUSH_WARN` line; nothing waits on it.
- Checked before every push: the repo is `private` on GitHub (`gh api repos/<repo>`; anything else is `STATE_GIT_PUSH_REFUSED`), and every file of the snapshot: a secret's name, `briefs/`, a token shape, a real secret value on this host (`KEY=VALUE` lines named like a token, secret, password, key or webhook in `secretFiles` and the env files, `gh auth token`, token-shaped strings in `messageFiles`), or one of the owner's inbox messages of `ownerMinChars` or more word for word, except in `ownerQuoteOk` files (`STATE_GIT_PUSH_LEFT_OUT <dir> <path> <why>`, once). A secret in the local history (a past blob or commit message) holds that repo (`STATE_GIT_PUSH_HELD`) until the lead accepts the path with `approve --history-ok`. A push by hand goes through the `pre-push` hook: only the remote `backup` at `https://github.com/<repo>.git`, private, approved, with no hit in any pushed commit.
- Rebuilding a host: `git clone -b <branch> https://github.com/<repo>.git <dir>` for each directory, then the env files (never in the backup) by hand; `dori state-git init` puts the hooks back.

An account without a `gh` login can push to an existing private backup repo using only its write-enabled deploy key: set `git config --global url."git@github.com:<repo>.git".insteadOf "https://github.com/<repo>.git"` (`<repo>` is `owner/name`). When `gh` is missing or reports an authentication error, visibility is checked with an unauthenticated GitHub API GET (10-second timeout): HTTP 200 uses its `visibility` (public is refused); only HTTP 404 followed by a successful `git ls-remote` through that same URL rewrite (20-second timeout, `GIT_TERMINAL_PROMPT=0`) establishes private access. A failed git probe is missing; network errors, other HTTP statuses and invalid answers stay unknown and block pushes. A logged-in `gh` result, including its 404, keeps its existing behavior.

### `dori send <slack|telegram|discord> --to TARGET --text TEXT | --text-file FILE [--thread ID] [--edit ID] [--reply ID] [--again]`
Posts a message, or edits one with `--edit`. Tokens come from `DORI_SLACK_TOKEN` (plus `DORI_SLACK_COOKIE` for a user token), `DORI_TELEGRAM_TOKEN` or `DORI_DISCORD_TOKEN`. `--text-file FILE` posts the file's text (trimmed, real line breaks kept) exactly as `--text` would, through the same send (and the same handling of a long text); both at once is an error. Text containing `$(` is refused, since it can only come from a shell string. A text with a literal `\n` (a backslash and an n) and no real line break, outside inline code and code blocks, is refused before anything is sent: `SEND_LITERAL_NEWLINE send: ...` on stderr, exit 2, pointing at `--text-file`; shell double quotes do not turn `\n` into a line break, and the reader would see the two characters (2026-10-19, E7 thread). The same check guards `dori thread reply|wait|done`, `dori thread open --first`, `dori ask --text` and the `--summary` of `claim-done` and `close`. Rate limits are retried with the server's wait time; other errors fail at once.

For Telegram, `--thread` and `--edit` accept only a positive whole-number topic or message id. An empty, whitespace-only, bare, malformed, negative, zero, fractional or unsafe-integer value is refused before any request, so a bad topic id cannot silently post to General and a bad edit id cannot become a new post or a null-id edit (upstream #132). A string flag left without a value is refused explicitly before any command runs, such as `--text needs a value`, a bare `--thread`/`--edit` on Slack and Discord, or a repeatable flag such as `dori serve --only`. A bare flag passes on only to the commands that check it themselves before any side effect: telegram `--thread`/`--edit`, `send --ping`, `send` and `thread reply|wait|done` `--file` (`SEND_FILE_REFUSED`), `--loop` on inbound, freshness, guard and dead-panes, and the empty `--thread`/`--no-thread`/`--why-new`/`--ask`/`--channel`/`--reply-to` refusals of launch, adopt, backlog add and ask, so nothing is posted or opened first; `--help` before a command prints the usage and exits 0 without running that command, while `dori send --help` keeps the command-specific help (upstream #187).

`dori send slack --to CHANNEL --file PATH [--file PATH ...] [--text TEXT | --text-file FILE] [--thread TS]` uploads files (Slack's `files:write`): each file gets its own URL from `files.getUploadURLExternal` and its bytes are sent there (read only when its turn comes, one file in memory at a time), then one `files.completeUploadExternal` shares them all as one message in the channel, with the text as its message (`initial_comment`, optional with `--file`) and in the thread with `--thread`. It prints `SENT <file ids>` (comma-separated). Every path is checked before any request: a missing file is `SEND_FILE_MISSING <path>`, an empty file, a directory, more than 10 files, `--again`, `--file` with `--edit` or on telegram are `SEND_FILE_REFUSED ...`, a file over Slack's 1 GB is `SEND_FILE_TOO_BIG <path>`, all on stderr with exit 2 and nothing sent; text with `$(` is refused before any file goes out, and a file whose size changed after the check stops the send before the share (`SEND_FILE_CHANGED`). The files are shared once per call: the share is never retried (a 5xx may have shared already) and a `--file` send is not checked for repeats, so a failure exits non-zero and a person calls it again. A file share takes the watcher's eyes off the messages it answers like a text answer does; the share's ts is not in the API answer, so it answers the messages from before its upload started. Not yet: a reply under a file share that does not mention the Dori is not tracked as its own thread, and files have no repeat check.

`dori send discord --to CHANNEL [--thread ID] --file PATH [--file PATH ...] [--text TEXT | --text-file FILE] [--reply ID] [--ping USER_ID]` posts the text and the files as one Discord message (`multipart/form-data`: `payload_json` with `attachments`, then `files[0]`, `files[1]` ...; the text is optional with `--file`) and prints `SENT <message id>`; `dori thread reply|wait|done discord:<id> [text] --file PATH` does the same in a work thread and sets the thread's status as without a file. Every path is checked, and every file read, before any request: a missing file is `SEND_FILE_MISSING <path>`, an empty file, a directory, more than 10 files (Discord's limit a message) and `--file` with `--edit` are `SEND_FILE_REFUSED ...`, a file over 20 MiB (Discord's default limit a file; a boosted server takes more, but the send does not ask), and files that with the text come to more than Discord's 25 MiB a message request (counted with 16 KiB for the form; also the egress gate's body cap) are `SEND_FILE_TOO_BIG ...`, all on stderr, exit 2, with nothing sent. The repeat check and the speech check run as for a text post: the key adds each file's name and sha256, so the same text with the same files within 10 minutes is `SEND_DUPLICATE <first id>`, while other bytes under the same name post; `--again` sends it anyway. A Dori behind the egress gate sends it through the gate as one request, which takes at most 25 MiB (`BODY_CAP` in `setups/egress-gate/gate.py`).

A Discord thread link in the text goes out as a masked link with the thread's name, `[name](<url>)`: a bare `https://discord.com/channels/<guild>/<thread>` (also in `<...>`, and with `/<message>` after it) and a `<#thread>` mention. Discord draws those as a pill named from the reader's own client cache, and a thread the client has not loaded (an archived one, which a ✅ thread is right after its rename, and one the reader never joined) reads "unknown" (알 수 없음); a masked link shows its own text and still opens the thread. The name is read from the API when the message is sent (`Discord.send` and `Discord.edit`, so every Discord post of a Dori: `dori send`, `dori thread reply|wait|done`, lane and close posts) and goes without its status mark and the status word after it (`✅ 완료 · 🏷️ 릴리스 v2` is `릴리스 v2`) or emoji, since the mark changes after the post. A text channel (and a message in one), a link already masked, code, and a thread the bot cannot read (`DISCORD_LINK_NAME_SKIP <id> ...` on stderr) stay as written.

A Discord post or edit escapes its underscores (`\_`, drawn as a plain `_`), so a file name or path such as `1_Project/2026_크레인` or `a_b_c.txt` is shown as written instead of in italics with its underscores gone (`src/messenger/discord-markdown.ts`, after the thread links are named). Left as written: code blocks and code spans (found, with the URLs and links below, by Discord's own parser simple-markdown, vendored unchanged with its MIT license at `src/messenger/vendor/simple-markdown.js`, so the text of a link label, bold, underline, italics, strikethrough or spoiler is read on its own as Discord reads it; since an escape can change what Discord parses, what is code, a URL or emphasis is read on the text with every underscore escaped, where no underscore pairs as italics, so escaping a text already escaped changes nothing, and the text that goes out is parsed once more: a backslash that would land in code or a URL there is left out), URLs (bare, in `<...>`, and a masked link's address up to its own `)`; its label is escaped), Discord tokens (`<:emoji_name:id>`, `</command_name:id>`, mentions, timestamps), an underscore already escaped (a backslash escapes the punctuation after it, so an escaped backtick opens no code, while an escaped bracket still bounds emphasis), and emphasis written on purpose (in a masked link's label too): `_word_` or `__word__` that opens after a space, the text start, an opening bracket or quote or the marks of bold, strikethrough or a spoiler (`**__x__**`), closes before a space, the text end, closing punctuation or those marks, and holds no underscore (so `_중요_` stays italic, `__init__.py` and `_Project_/` are escaped). An escape next to a URL can move where Discord ends it, so a link would go elsewhere: the text escaped (and the fallback below) is read once more with the same parser, as it is (its own preprocessing drops a form feed), and a whole text (a card's text as put together from its parts) whose link targets (URLs, `<...>` and mail links, masked links' addresses) differ from the text as written goes out as written, with one `DISCORD_LINK_TARGET_WARN` line on stderr that holds no part of the text. A text that fits Discord's 2000 characters only without the escapes goes out with none rather than refused: every `\_` outside code, URLs and tokens loses its backslash, the writer's own too, so a text and the same text already escaped post alike. `dori send discord` and `dori thread reply|wait|done` prepare a text once (`Discord.prepare`: the `--ping` in front, thread links named, underscores escaped or the fallback), key the repeat check (`SEND_DUPLICATE`) on that text and post it as it is, so what is keyed is what goes out. A question card escapes its question, options and answer the same way; each of its texts (and the answered summary in the thread) is measured whole before it is cut to its limit, and one that fits only unescaped, or a card whose 4000 characters of text fit only unescaped, goes out unescaped. The repeat check and the `SENT`/`POSTED` line read the escaped text, so `a_b` and `a\_b` are one message. Slack and Telegram posts are not changed.

A new message goes out once: the same place (platform, `--to` and `--thread`), `--reply`, `--ping` and final text sent again within 10 minutes (`SEND_DEDUPE_MS` in `src/send-dedupe.ts`) is not posted, and neither is a new message equal to the last post of that place, however old (`<stateDir>/sent/last-<hash>.json`, one a place, never pruned): it prints `SEND_DUPLICATE <place> <earlier id>: ...` (`<place>` is `discord:<channel or thread>`, `slack:<channel>[/<thread ts>]`, `telegram:<chat>[/<topic>]`) and exits 3, so the caller has the earlier message's id and cannot read the repeat as a new post. The last-post check comes from [sisyphuslabs/dori-superagent#88](https://github.com/sisyphuslabs/dori-superagent/issues/88): a tool call refused by a hook left the earlier text in a kernel variable, a later call posted that variable 7 and 15 minutes after the first post, and the new id was taken as proof the new text went out. A post prints what the service answered it holds, not what the caller meant: `SENT <id> len=<characters> sha=<first 8 hex of sha256> first="<first 40 characters>"` from Discord's `content`, Slack's `message.text` or Telegram's `text` (`content=not-returned` when the answer had none); `SENT <id>` stays the first two words, so readers of the line (`intent-check` post ids, `replyPattern`) are unchanged. Each post `dori send` or `thread reply|wait|done` makes keeps its own record, named by its message id (Discord snowflakes, Slack ts and Telegram ids grow with time), so the place's last post is its newest one even when an earlier post finished writing later; older records go on the next read. Only those posts are recorded: an edit, a post another command makes (a close summary, a lane post, a card) and a Slack file share do not move the record, so a text sent again across one of them is refused (`--again` posts it), and the edited text of the last post can be sent again once; recording every post and edit is the follow-up in `docs/follow-ups.md`. A close whose reply hook (`dori thread reply`) gets exit 3 with `SEND_DUPLICATE` posted nothing because its summary is already the thread's last post: it counts the summary as there instead of refusing. Two identical sends started at the same moment post once as well (2026-10-20: one reply of the lead carried two identical calls and the owner's thread got the message twice): the first takes a claim file created with O_EXCL under `<stateDir>/sent/`, the other waits for its id. A send that fails removes its claim, so a retry after a real failure still goes out; a claim left without an id for a minute (a sender that died) is taken over; marks older than a day are pruned. Edits are never checked. `--again` posts a repeat on purpose (a reminder that really is the same words). `--reply ID` (Discord, digits only, new messages) posts the message as a reply to that message in the same channel, without pinging its author (`message_reference` with `fail_if_not_exists: false`). An option `send` does not take, or a stray word, is refused before anything is sent (`UNKNOWN_OPTION send: ...`, exit 2) instead of being dropped; `--reply` used to be dropped that way.

What goes to the owner is in the speech this Dori uses with him (`discord.ownerSpeech`, `""` follows `discord.locale`: Korean is 반말): with `casual`, a Discord post or edit whose text has a sentence in ~요/~니다 speech (~니다 and ~니까 only after a syllable ending in ㅂ, as in 합니다 or 습니까; 몫이니까 and 그러니까 are 반말) is refused before anything is sent (`SPEECH_REFUSED send: it is in 존댓말 ("...") ...: write it in 반말; nothing was sent`, exit 2) when its place is the owner's: `DORI_DISCORD_CHANNEL`, a thread in it, or a DM. The pair channel (`DORI_DISCORD_PAIR_CHANNEL`) and other channels are not checked, nor Slack or Telegram; quoted lines (`> ...`) and code are someone else's words or output and are not read. The place is looked up (`GET /channels/<id>`) only for a text that fails, and one that cannot be looked up counts as the owner's. `dori thread reply|wait|done` and `dori ask` (its text and options; a card is always the owner's) make the same check. Its source is `src/close-summary.ts` `ownerSpeechProblem` (2026-10-20, owner "얘는 왜 말투 안 바꼈냐?" on a lane's "...올릴게요." progress post).

### `dori presence <slack|discord>`
Keeps the account shown as online until stopped.
- **Discord:** the bot connects to the gateway and identifies as online.
- **Slack, user token:** it opens one web-client-type socket and tickles it every minute. Slack shows a user active only while such a socket is open, and auto-aways an idle one after about 30 minutes.
- Run one instance per account. Two writers flip each other's presence.

### `dori inbound slack [--loop MIN]`
Prints `INBOUND <source> <channel> <thread> <ts> <user> <text>[ root=<json> recent=<json>]`. It reads from three places, each message once:
- `threads-view`: unread replies in threads the account follows (Slack's own Threads view);
- `own-thread`: new replies in any thread the Dori posted in, tagged or not;
- `unread`: DMs, group DMs and channels with unread mentions.

The Dori's own messages and bot messages are skipped. Every message the Dori posts records its thread in `<stateDir>/slack-threads.json`, whichever helper sends it, so a guest's untagged reply under a root posted with a raw API call is still found.

For `threads-view` and `own-thread`, `text` is the complete current message as a JSON string, without the former 200-character cut. `root` is a JSON object with `channel`, `rootTs`, `user` and `text` (the original root text, bounded to 1000 characters), including when the root is older than the ledger's `seenTs`. `recent` is a JSON array of up to three `{ts,user,text}` objects immediately before the current message, with `text` holding each author's first line. Every replies page is read with `response_metadata.next_cursor`, so this context comes from the end of a long thread. The root is looked up once per thread in an inbound process and cached; a failed root lookup fails the poll instead of producing empty context. `unread` rows have no `root` or `recent` fields. Ported from upstream [#195](https://github.com/sisyphuslabs/dori-superagent/issues/195).

A bot token's `not_allowed_token_type` from `subscriptions.thread.getView` or `client.counts` skips only that view; own-thread replies still arrive. Each skipped method prints one `WARN` per process, even with `--loop`. Other errors fail the poll and leave watched replies unseen for the next pass; seen timestamps advance only after all Slack calls succeed. Ported from upstream [#182](https://github.com/sisyphuslabs/dori-superagent/pull/182), fixing #180.

`conversations.replies` and `files.getUploadURLExternal` automatically send URL-encoded forms (`application/x-www-form-urlencoded; charset=utf-8`), omitting null and undefined fields. JSON methods such as `chat.postMessage` keep `application/json; charset=utf-8`; explicit form calls and retry policies remain supported.

### `dori inbound telegram [--loop MIN]`
Prints `INBOUND <source> <chat> <thread> <update-id> mid=<message_id> <from> <text>[ file=<kind>:<file_id>]`, keeping Slack's field order — `source` is `dm`, `topic`, `edit:dm` or `edit:topic`. `mid=<message_id>` is always present (`-` when Telegram gave none, so later fields never shift) and names the Telegram message behind the line: a new message and the edits that replace it share the same `mid=`, so a consumer can pair an edit with the original line. A media message appends ` file=<kind>:<file_id>` (voice, audio, video, video_note, animation, document, photo — the largest photo variant); the line carries the `file_id`, which a caller can pass to Telegram's `getFile`. Long-polls `getUpdates` (upstream dori-superagent #76, [#79](https://github.com/sisyphuslabs/dori-superagent/pull/79) for edits and media, and [#110](https://github.com/sisyphuslabs/dori-superagent/pull/110) for `mid=`, live locations and the loop):
- only the configured owner's messages pass (`DORI_TELEGRAM_OWNER_ID`); bot messages never do;
- DMs from the owner always pass; in a group (`DORI_TELEGRAM_GROUP_ID`) only the configured topic (`DORI_TELEGRAM_TOPIC_ID`) does — with a group but no topic, every owner message in the group passes — with no group configured, DMs only;
- delivery is at-least-once: the offset in `<stateDir>/telegram-offset` advances past a message only after its `INBOUND` line is out (dropped updates advance immediately), so a crash replays at worst the unprinted lines — duplicates carry the same update id;
- the full text is printed, JSON-escaped on one line: `getUpdates` cannot fetch a message again;
- edits arrive too: `edited_message` updates are polled and printed as their own `edit` kind, carrying the edited text; a live location arrives as a stream of edits carrying only coordinates, and those are dropped, not one line each (an edit with text or a caption still prints);
- an offset file that is not a non-negative integer warns once on stdout, like every other inbound `WARN` (`WARN telegram-offset at <path> is unparseable ...`) and restarts from 0;
- without `--loop` it polls once and exits; with `--loop MIN` it polls again at once after a poll that returned updates, printed or dropped by the gates, and waits MIN minutes only after an empty or failed one (a failed poll prints `WARN <error>`);
- reuses the bot token the skill already stores (`DORI_TELEGRAM_TOKEN`).

Nothing starts it on its own (`dori serve` and the services run `inbound discord` only); without `DORI_TELEGRAM_TOKEN`, or with an id that is blank, not a plain decimal integer after trimming (`1e3` and `0x10` are refused), or (owner, topic) not positive, it exits 1 before any call. An `INBOUND` line that cannot be written whole (stdout closed, a write that stops partway) leaves the offset before its message.

### `dori inbound discord`
Runs until stopped (run it as a service, see `setups/discord-aoe/`). It connects to the gateway with the message-content intent and handles:
- the owner's messages in `DORI_DISCORD_CHANNEL`, its threads, and DMs; everyone else, bots included, is skipped. Each gets the eyes reaction at once, a voice note is transcribed through `hooks.transcribe`, and one row is appended to the inbox file (`DORI_DISCORD_INBOX`, default `<stateDir>/discord/inbox.jsonl`) and printed as `INBOUND discord-<scope> <channel> <id> <author> <text>`. The owner's row (not a `pair-bot` or `watch` row, nor an unregistered webhook's recording) carries `directives`: the ledger entries his text (or transcript) is about, so the lead reads them with the message even when it does the work itself without a lane brief (2026-11-02: MooDori's lead got "그리고 카드처리해 서류 준비하고 있어" as a bare row and missed the 10-19 directive that it prepares those papers). They are the entries a keyword, a kind of work (one hit is enough in a message) or UI words of the text call; entries for every lane, require entries and built-in blocks are left out (a brief carries them). The host's local entries come first, then keyword matches, then kind matches; every keyword match comes in, and kind matches only up to five in all (when the ledger was read with local lines left out, one more line says so: `[장부 경고] ...`, fix it with `dori directives check`), each one line `[형 지침 <id>, <date>] <prompt>` or `[리드 규칙 <id>] <rule>`. The ledger is read for every message (both layers, a bad local line left out). A ledger that cannot be read never holds the row back: it carries `directives_error` and the listener prints `DISCORD_DIRECTIVES_FAIL <id> <error>`.
- the owner calling this Dori anywhere else in the guild: a message in any other channel or thread that mentions its bot user or one of its roles (the roles its bot member has, read again at every gateway READY and printed as `DISCORD_MENTION_IDS user=<bot> roles=<ids>`, plus `discord.mentionRoleIds`; a mention that comes during the read waits for it, and a failed read prints `DISCORD_MENTION_IDS_FAIL <error>` and is tried again by the next mention) gets the eyes and a `scope:"mention"` row with its `channel_id`, a `link` to the message and a `note`: answer in the Dori's own channel or work thread with that link, never in the other channel (it belongs to someone else; read it, do not write there). Another Dori's bot or role is not this Dori's mention, and the owner's other messages in channels the Dori does not own are skipped with no eyes. Mentions elsewhere are not backfilled after a reconnect;
- question-card taps and write-my-own submissions (below), appended as `kind:"answer"` rows and printed as `ANSWER <Qn> <kind> <answer> thread=… session=… tmux=…`;
- the bot's own messages (with `discord.autoUnEye`, on by default): when the bot it runs as writes in a channel, thread or DM, by any helper, the eyes come off every earlier owner message in that same channel, thread or DM, off the message it replies to, and off any message carrying eyes that its text links to (`https://discord.com/channels/<guild>/<channel>/<message>`: how a mention row's eyes come off). Other bots' messages clear nothing, except in the pair channel (next items). The messages still carrying eyes are kept in `eyes.json` beside the inbox file; the removals for one channel run one at a time and wait out a 429's `retry_after`. It prints `EYES_CLEARED <channel> by=<bot message> <ids>`, or `DISCORD_UNREACT_FAIL <id> <error>` for a message it could not clear;
- after each reconnect, the owner's messages it missed in the channel, its active threads and the owner's DM, oldest first within each channel. It resolves only the owner's DM through `/users/@me/channels`. DM history starts at zero once so a lost first DM is recovered even if newer messages are already in the inbox. Each channel then has its own durable scan cursor in `discord/backfill.json`, advanced after a processed page even when its authors are skipped; a full 100-message page is followed by another page. Existing inbox rows deduplicate delivery and seed guild channel cursors, while another messenger's rows never move them. A live message cannot jump an unfinished history scan. A channel whose history answers 404 Unknown Channel (code 10003, the channel was deleted) is logged once as `DISCORD_BACKFILL_GONE channel=…`, its cursor is dropped from `backfill.json`, the rest of the scan continues, and that process does not ask for it again; remove it from the settings (for example `DORI_DISCORD_WATCH_CHANNELS`). Any other error still fails the scan and keeps the cursor. `DISCORD_BACKFILL_SCAN channel=… since=… cursor=… scanned=… added=…` reports scans without bodies; `added` counts accepted inbox rows, not bots. Shadow runs use a separate cursor file beside their inbox;
- Gateway opcode 7 (reconnect) and 9 (invalid session) log `DISCORD_LISTENER_RECONNECT op=…` and close locally with 4000, not Discord's unknown-opcode code 4001. The next connection identifies afresh, resets its sequence and backfills on READY;
- an owner message in a done thread (✅ or `[done]`) reopens it: the thread is unarchived, marked working, and `THREAD_REOPENED <thread>` is printed.
- with `DORI_DISCORD_PAIR_CHANNEL` (a channel shared with other Doris) and `DORI_DISCORD_PAIR_BOT` (one or more of their bot ids, comma or whitespace separated; e.g. three Doris sharing one pair channel, each listing the other two bots): the owner's messages there become `scope:"pair"` rows with the eyes reaction and the listed bots' `scope:"pair-bot"` rows without it (the Dori rarely answers them, so the eyes would never come off); treat pair-bot rows as information, never as requests, except another Dori's lead alert (a row that starts with `LEAD_RUNAWAY <pane>` or `LEAD_AUTOTURN_PAUSED <pane>`, see `watch`): type one short check message into that pane with `dori type`, as SKILL.md says; a row whose head says `repeat` asks for none. Other bots there are skipped, the pair channel is backfilled too, and both scopes count as this listener's own rows for the backfill point. Unset: that channel is skipped like any other.
- another Dori answering the owner in the pair channel (with `discord.callNames` set and `discord.autoUnEye` on): a listed pair bot's post that replies to an owner pair message, or links to one, takes this Dori's eyes off that message when the owner did not call this Dori there. Calling it means one of `discord.callNames` in his text or voice transcript (case-insensitive), a mention of its bot or one of its roles, or a reply to its own post. That pair row then has `called: false`; a row written before the names were set, or while this bot's roles could not be read (a role mention cannot be judged then), has no `called` field and keeps its eyes; so does a voice note whose words did not come through (no transcriber, a failed or empty transcript). The eyes come off once a message is both uncalled and answered, in either order: a reply that comes before the owner's row is written (a voice note still being transcribed, a message the backfill brings later) is kept, also across a restart (from the `pair-bot` rows), and clears the eyes when that row is written; eyes still on a message that was already both when the listener stopped come off when it starts again. It prints `EYES_CLEARED_ANSWERED <channel> by=<their message> bot=<their bot> <ids>`. An owner pair row that did not call this Dori, or any owner pair row while the names are empty, carries a `note`: if it is another Dori's work, do not answer it and run `dori eyes off <id>` (owner 2026-11-03, ledger `eyes-not-mine`).
- with `DORI_DISCORD_WATCH_CHANNELS` (comma-separated channel ids in the same guild where a monitoring app posts its notices, e.g. a system's `#notifications`) and `DORI_DISCORD_WATCH_BOTS` (that app's bot ids): a message there from one of those bots whose text matches `DORI_DISCORD_WATCH_MATCH` (a regular expression; default: a new problem found `새로 확인된 문제`, a new failure that is not `없음` `신규 실패:`, or `반복 실패`) becomes a `scope:"watch"` row without eyes, with a `link` to the alert and a `note`: check what failed, fix it or open a lane for it, and tell the owner in the Dori's own channel with the link, never in the watched channel. Recoveries, routine reports and other authors there are skipped; the watched channels are backfilled too. An invalid regular expression stops the listener at start. The point is that the owner should not have to paste an alert to get it looked at (owner, 2026-10-17: "앞으로 니가 노티피케이션에서 이런 에러 있으면 확인하고 고쳐 줘"). Unset, or no bots: those channels are skipped like any other.

`DORI_DISCORD_SHADOW_INBOX=<file>` runs a shadow listener: the same inbox rows go to that file instead of the live inbox (it refuses to start when the two are the same file), but it writes nothing to Discord: no eyes reaction, no reopen, no unreact, no `eyes.json`, and card taps are not answered: for an owner's tap or typed answer it appends the `kind:"answer"` row the live listener would (same fields; `ts` is its own clock) without changing `questions.json` and prints `SHADOW_ANSWER <Qn> <answer>`; anything else prints `SHADOW_INTERACTION_SKIPPED <interaction> <custom id>`. It prints `DISCORD_LISTENER_READY shadow`. Use it beside a running listener to compare rows by message id before switching listeners; stop it before starting the new one for real.

A rejected token, a bad shard or API version, or a missing intent (every close code Discord marks do-not-reconnect) stops it (exit 3, or 4 for a disallowed intent); other disconnects retry with backoff up to ten seconds, so the listener is back within seconds once the host's network returns.

### `dori eyes off <message id | link>`

Takes this Dori's own eyes reaction off one message at once (`DELETE .../reactions/👀/@me`; other people's and bots' reactions stay). Use it for an owner message you read and will not answer. The channel comes from a Discord message link, else from the `eyes.json` entry that tracks the id, else from `DORI_DISCORD_PAIR_CHANNEL`. It only reads `eyes.json` (the running listener owns that file; the id leaves it at the listener's next sweep of that channel, which finds nothing left to remove) and prints `EYES_OFF <channel> <id>`; it exits 1 with `EYES_OFF_FAIL <ref> <error>` when the input is neither an id nor a link, the channel cannot be found, or Discord refuses.

### `dori ask --text Q --option A [--option B ...] [--thread REF | --reply-to MSG | --channel "<reason>"] [--session ID] [--tmux NAME]`
Posts a question card, pinging only the owner, and prints `ASKED <Qn> message=<id>`. With `--thread` the card goes inside that work thread and the thread is marked waiting (`[waiting]`, or 🔔 with emoji status). A card goes in the thread of its work (directive `request-thread`: the owner's short requests and answers in the channel, permission and approval cards in the thread), so without `--thread` it goes in the work thread of the asking session's open lane (the lane of `--tmux`, else of `--session`, else of the pane the command runs in), or in the one thread `dori thread open --session` mapped to that session, and prints `ASK_THREAD_AUTO discord:<id> lane <key>` (or `mapped to <session>`) first; a lane found from the pane is recorded as the card's `tmux`, where its answer is relayed. When none is found nothing is posted: `ASK_THREAD_REQUIRED ...` names the open lane threads and exits 2. Two ways into the channel: `--reply-to <the owner's message id or link>` answers a message he wrote in `DORI_DISCORD_CHANNEL` as a Discord reply to it (`ASK_REPLY <Qn> <id> in the channel`; his message in one of its threads sends the card into that thread instead, as a reply there), checked against the inbox (`DORI_DISCORD_INBOX`): a message that is not his, or not there, is `ASK_REPLY_TO_UNKNOWN` (exit 2); `--channel "<reason>"` posts in the channel, prints `ASK_CHANNEL <Qn>: <reason>` and keeps the reason on the card (`channelWhy` in `questions.json`), like `launch --no-thread`; an empty reason is refused. Only one of `--thread`, `--reply-to` and `--channel` (exit 2). Each option is shown in full as a numbered line with a short pick button beside it, and the first option's button is the highlighted one, so put your recommendation first; a write-my-own button that opens a text box is added last (1 to 9 options). `--thread`, `--session` and `--tmux` travel with the answer so you know where to relay it. Only the owner's answer counts: the card folds into `[answered] <Qn> … → <answer>` (`✅ <Qn> …` with emoji status) in the interaction response, the answer is appended to `<stateDir>/discord/answers.jsonl`. (`DORI_DISCORD_STATE_DIR` moves `questions.json` and `answers.jsonl` for `ask`, `questions`, `reopen`, `resolve` and the listener alike.) A card inside its thread is that thread's record; a card in the channel for a thread also leaves a silent record line in the thread. Once no question in the thread is open, the thread is marked working again (🔄). The listener takes taps from the channel and from the thread a card was posted in, and must be running to receive them. A failed thread rename is printed as `THREAD_STATUS_FAIL <thread> <error>` and does not fail the card. Every status change (ask, answer, reopen, resolve, `dori thread`, `dori close`) goes through the thread status queue: the mark is decided from the open cards when the rename runs, and a rename Discord refuses with 429 stays in `thread-status.json` (`THREAD_STATUS_PENDING <thread> <status> retry_in=<s>s`) until the listener applies it (`THREAD_STATUS_APPLIED`). An owner message in a thread with an open card adds `open_cards` and `note` to its inbox row and prints `CARD_STILL_OPEN <Qn,...> thread=<id> ...`; the card stays open until you resolve it with `--answer`. An option the card cannot show whole (`**n.** <option>` over 1000 characters) is refused before anything is stored or posted: the egress gate takes a tap's answer only when it equals the pressed option's text in the card, so a cut option's real tap would be refused. An option holding a line that starts `→ **` is refused the same way (a folded card's answer is its last such line). A tap's answer is recorded only once its callback was taken: when the egress gate or Discord refuses the fold, the question stays open and nothing is logged. A button answer folds into the card as its option reads on the open card (escaped or not, as that section was drawn).

### `dori questions [--open]` / `dori reopen <Qn>` / `dori resolve <Qn> [--answer TEXT]`
List tracked questions; put a card's buttons back where it was posted (when a typed answer was not really an answer), marking its thread waiting again; forget a question once its follow-up is done. The folded card stays in the chat as the record. Resolving a card that is still open (the owner answered in a message, or the question was dropped) first edits it, in its thread or channel, into the same record a tap leaves: `[answered] <Qn> … → <TEXT>` (`✅` with emoji status) marked `byReply`, with `repliedInText` when `--answer` is not given; the answer is appended to `answers.jsonl`, and the thread is marked working again once no other question in it is open. A card in a thread that archived itself is edited after the thread is opened (Discord refuses edits there, 50083). A failed edit exits 1 and keeps the question open, so the same command can be run again. It prints `RESOLVED <Qn> folded`; a card already folded by a tap is not edited again and its thread status is left alone (`RESOLVED <Qn> kept`); a question resolved before changes nothing (`RESOLVED <Qn> already`). Since `resolve` forgets the question, `reopen` works only before it.

### `dori serve [--log FILE] [--only TAG ...] [--install-task]`

Keeps this Dori's long-running loops up in one process where there is no systemd and no bash (native Windows): `watch`, `freshness --loop 2`, `dead-panes --loop 5`, `guard --loop 1`, `state-git loop` (as `dori-lanes.sh` runs them), `inbound discord` and `setups/discord-aoe/session-watch.ts`. On Linux the systemd units stay the way.

### `dori lead`
Prints `<aoe-id> <tmux-session>` for the lead, followed by ` stopped` when its tmux session is not running (at boot it is not yet; `dori-lead.service` and `dori.sh` start it from the id). ### `dori thread open <title> [--from MSG_ID] [--first TEXT] [--session S]`
Opens a thread in `DORI_DISCORD_CHANNEL`, named with exactly one working mark in `discord.statusStyle`. `--from` starts it from that message; without it, `--first` is required and posted as the standalone thread's first message. Before anything is opened it reads the directive ledger against the title, `--first` and the owner's message `--from` names (its text or transcript in the inbox): every entry in scope as a lane brief would get it (one keyword or kind hit is enough; the every-lane entries too; not require entries or built-in blocks). The entries its words call come before the every-lane ones. A ledger that cannot be read, or none configured, opens nothing, and so does one whose local layer has a bad line (the host's own directives would be missing; a message row only warns of it): `THREAD_REFUSED <title>: ...`, exit 1 (open the work as a lane, or fix the ledger). Then it records the bare title, session (null when omitted), the directive ids and `openedAt` in `<cardDir>/threads.json` and prints `THREAD_DIRECTIVES discord:<id> <n>: <id> (<why>), ...` with one line per directive (`[형 지침 <id>, <date>] <prompt>` / `[리드 규칙 <id>] <rule>`) for the lead to follow in that thread's work, then `THREAD_OPENED discord:<id>`. `dori directive-audit` reads a thread with no recorded directives that no lane works in as `DIRECTIVE_LEAD thread:<id>`.

### `dori thread map discord:<id> <session|none>` / `dori thread list`
`map` sets the session, keeping the recorded title, and prints `THREAD_MAPPED discord:<id> <session|none>`. `none` stores null. `list` prints one line per mapping: `<id> <session|none> <title>`, with ` [standing]` after a standing thread. The map uses `{"<id>":{"session":null,"title":"..."}}`; `cardDir` is `DORI_DISCORD_STATE_DIR`, else `<stateDir>/discord`, so an existing map there needs no migration. Writes use a temporary file and rename. ### `dori thread set discord:<id> working|waiting|done|standing|unstanding [--open-card]`
Requests the status through the existing `ThreadStatusQueue`, without posting a message. An open lane on the thread that is working (or sent back by an objection, `not-done`) keeps a non-done thread working, past an open card and past `waiting`: waiting means nothing is left on our side (`THREAD_STATUS_APPLIED <id> working open=<cards> working=<lanes>`). With no such lane, open question cards (or `--open-card`) keep it waiting. `done` makes the same check as `dori thread done` below (`THREAD_LEFT_OPEN`, `--force`, `THREAD_DONE_FORCED`); done wins, archives it and drops its mapping after the status is applied. A rate-limited rename stays queued until the listener applies it; the mapping stays until then.
`standing` marks the thread as the one place a kind of work always lives (for example upstream ports): it sets `"standing": true` on its threads.json entry, renames it with the standing mark (📌, `[<discord.standing>]` in words style) and prints `THREAD_STANDING discord:<id> <outcome>`; running it again on a standing thread is how one still showing an older mark gets 📌. The status queue then keeps that mark through every event (a working lane, an open card, a wait, a done), so only the mark stops showing the status. Closing the last lane there posts the result and leaves it open (`thread left open: standing thread`), and the automatic archive only takes done threads. A done mark without `--force` also leaves it open (`THREAD_LEFT_OPEN ...: standing thread`).
`unstanding` ends that and prints `THREAD_UNSTANDING discord:<id> <outcome>` (`THREAD_NOT_STANDING discord:<id>` when it never was): the entry keeps `"standing": false`, so every later rename takes a 📌 left in front off (a rename that failed is made good by the next one, or by `unstanding` again), and the normal rules apply from waiting (a lane working there makes it working). A done mark with `--force` ends it the same way, done: ✅, archived and the entry dropped. A 📌 in the title of a thread that was never standing is part of its name and stays.

### `dori thread <reply|wait|done> discord:<thread id> <text> | --text-file FILE`
A ready `hooks.threadReply` / `hooks.threadDone` for Discord: `["dori", "thread", "reply", "{thread}", "{text}"]`. The text can come from `--text-file FILE` instead; a literal `\n` with no real line break is refused (`SEND_LITERAL_NEWLINE`, see `dori send`). It shows typing, posts the text with emoji removed, and sets the status mark at the start of the thread name: `reply` working, `wait` waiting, `done` done. `done` archives the thread; the others unarchive it. Nothing is renamed when the mark already holds, because Discord allows only about two renames per ten minutes. `done` first makes the same check as closing a lane: while another open lane or an open question card uses the thread, it posts the text and prints `POSTED <id> THREAD_LEFT_OPEN discord:<id>: <holders>; not marked done (--force marks it done anyway)`, and leaves the mark and the archive as they are. The lane whose close runs it is not another user: `hooks.threadDone` runs with `DORI_CLOSING_LANE=<key>`, and `--lane <key>` says the same by hand. `--force` marks the thread done anyway and prints `THREAD_DONE_FORCED discord:<id>: <holders>; marking it done anyway` first.

`thread reply|wait|done` share the repeat check of `dori send`, keyed by the text as they post it (emoji removed), which is the key of `dori send discord --to <thread id>` for a text without emoji; the post is recorded as soon as Discord made it, before the verb's status step: the same text again in that thread within 10 minutes, or the text of the thread's last post at any age, is not posted (`SEND_DUPLICATE discord:<thread id> <earlier id>: ...`; `reply` then exits 3), while the status of `wait` and `done` is still set and they exit 0, so a `done` with the words of the last `reply` still closes the thread. A post prints `POSTED <id> len=<n> sha=<8 hex> first="..."` from the content Discord answered, as `dori send` prints `SENT`. `--again` posts it anyway; an option these verbs do not take (they take `--text-file`, `--force`, `--lane`, `--again`, `--file`) is refused (`UNKNOWN_OPTION thread <verb>`, exit 2).

`thread reply|wait|done` make the speech check of `dori send` (`SPEECH_REFUSED`): 존댓말 in a thread of `DORI_DISCORD_CHANNEL` from a Dori that talks to the owner in 반말 is refused before anything is posted or marked.

### `dori gpu-room [label] [--want SIZE]`: free memory for a GPU start
On a unified-memory GPU (GB10) the driver takes a CUDA context's buffers from system memory and does not wait for page cache to be reclaimed. On 2026-11-02 20:33 KST (MemFree 1G, buff/cache 95G, MemAvailable 95G) the owner's voice note died in `ggml_cuda_init` (whisper-cli exit 134) with `NV_ERR_NO_MEMORY ... kgrctxAllocMainCtxBuffer` in the kernel log; pushing 30G of cache out made the same run work. With MemFree near 1G the driver already fails its big-page allocations on every start and falls back, so a start fails outright when few large free blocks are left. NVIDIA's workaround needs root (`sync; echo 3 > /proc/sys/vm/drop_caches`, [DGX Spark known issues](https://docs.nvidia.com/dgx/dgx-spark/known-issues.html)).

With less than SIZE (`heavyGpuFreeGb`, 20G) free (`dori heavy` before a GPU job: less than a quarter of it, since touching eats the free memory before any cache goes: 17G free took 8.6s for 2.5G more), a helper process in its own scope touches anonymous memory in 256M steps (madvised huge pages, so the kernel compacts while it reclaims) until MemFree plus what it holds reaches SIZE, then lets it all go, so it comes back free in large blocks. It stops at SIZE, before MemAvailable would fall under `heavyHeadroomPct` of the host, and as soon as swap use grows by a step (it then would take another process's memory, not cache). One line on stderr and in `state/heavy/heavy.log`: `HEAVY_GPU_ROOM voice: pushed 19968M of cache out in 10.3s (stop: enough): free 1334M -> 20851M, in 2M+ blocks 478M -> 998M` (a live run with 93G of cache); `HEAVY_GPU_ROOM_SHORT` when the floor leaves no room, `HEAVY_GPU_ROOM_FAILED` when the helper failed (the job still starts); nothing when enough is free or there is no `/proc/meminfo`. `dori heavy` runs this before every GPU job; `transcribe.sh` and `transcribe_long.py` run it before their one retry of a whisper-cli that died in a CUDA error (`TRANSCRIBE_CUDA_RETRY`).

### `dori heavy <label> -- <command ...>`
Waits until load is under `heavyMaxLoad` and a slot is free, then runs the command and frees the slot when it exits. While fewer than `heavySlots` (1) heavy jobs run, load is the only check. Beside running ones it measures the host (GPU use from `nvidia-smi`, GPU memory or, on a unified-memory GPU such as GB10, system memory from `/proc/meminfo`, CPU as 1-minute load over cores) and guesses the new job's use as the largest use among the running heavy jobs (their process trees: `nvidia-smi pmon` SM percent, `ps` RSS and CPU); the job starts in another slot, up to `heavyMaxSlots`, only when every resource keeps `heavyHeadroomPct` (10) percent free with it added, and waits while the last job taken is younger than `heavySettleSec`, so a job that pushed a resource under 10% stops the next one from starting. Running jobs are never stopped. One decision at a time across processes (`admit.lock`). Each job prints one `HEAVY_ADMIT <label> slot.N: <why, with the numbers>` line and a `HEAVY_WAIT <label>: <why>` line when it starts waiting or its reason changes, on stderr and in `state/heavy/heavy.log`. A slot held by a process that no longer exists (or a zombie) is taken over. Use it for full builds and test suites. Installs, focused tests and git do not need it.

The command runs in its own systemd user scope (`systemd-run --user --scope -p MemoryMax=<limit> -p MemorySwapMax=0`, unit `dori-heavy-<label>-<pid>-<n>`, n counting the jobs of that process so a second job of one label never meets the first one's scope still loaded, `HEAVY_SCOPE <label> <unit> MemoryMax=<limit>`), with `oom_score_adj` 500. Over the limit the kernel kills it there and systemd stops only that scope: `HEAVY_OOM <label>: killed at MemoryMax=...` and its exit code (137), while the lane that started it keeps running (2026-10-30 02:33 UTC: a 67.5 GB model under `dori heavy` ran in its lane's aoe-session scope; the host ran out of memory, and systemd's `DefaultOOMPolicy=stop` stopped that scope with the lane in it). On a host-wide OOM (GPU memory the driver allocates on a unified-memory GPU is not always charged to the scope) the raised score makes the kernel pick the job before a lane or a host service, and only its scope stops. The limit is `--mem <size>` (`70G`, `200M`) when given, else what keeps `heavyHeadroomPct` of the host free when it starts. `--mem` also gates the start: even the first job waits (`HEAVY_WAIT <label>: memory: needs ..., ... available, ... held for running jobs still loading -> N% free (needs 10% free)`) until available memory, less what running `--mem` jobs said they need and do not use yet, less its own estimate, keeps `heavyHeadroomPct` free; an estimate larger than the host can ever give is refused at once (`HEAVY_REFUSED <label>: --mem ... never fits here`, exit 2). Where no user scope can be made (macOS, no user manager) it runs as before and says `HEAVY_NO_SCOPE <label>: <why>`. A `--job` run gets the same scope with the default limit.

Before a GPU job (plain `dori heavy`, every `--job`, `--kind gpu` here or on a helper) with less than a quarter of `heavyGpuFreeGb` (20, so 5G) free, `dori gpu-room` runs first (below) and makes it 20G (or the job's `--mem`): `HEAVY_GPU_ROOM <label>: pushed ...` in the heavy log.

A heavy job's command and everything it starts see `DORI_HEAVY_JOB=<label>`, a named `--job`'s command too. A `dori heavy` started under it, plain or `--job` (rv's own `dori heavy` inside `dori heavy ... -- rv make` without `--no-heavy`, a script or a named job that calls `dori heavy` itself), takes no slot, scope, queue host or helper of its own (a `--job` keeps its inputs, outputs and rl check): it runs at once in the outer job's slot and scope, its exit code is its command's (`HEAVY_NESTED <label>: inside the heavy job <outer> here, so it runs now in that job's slot and scope`). Waiting for a slot of its own while the job it runs in held one never ended when that was the last slot (lead 2026-11-08, rv-actreverse-skip). A job on a helper runs in a box with no `dori` on its PATH, so rv there renders without it.

Waiters start in the order they came: each waiting `dori heavy` leaves a ticket in `state/heavy/queue` and only the oldest live one may take a slot (`HEAVY_WAIT <label>: N job(s) ahead in the queue`).

A slot is held by its `dori heavy` process until the command exits, and only while that process lives: a slot whose holder died, or whose pid now belongs to a process started after the slot was taken, is taken over at the next admission, and a holder that ends after that leaves the new job's slot alone. Full slots name their holders (`HEAVY_WAIT <label>: all 8 slots busy: slot.1 <label> pid <pid> 2h50m, ...`), so a job that should have ended shows there. A command that starts work and then watches it must end when the work ends, or it keeps its slot: `tail -F out | sed '/DONE/q'` never exits once the file stops growing (tail writes nothing more, so it never learns sed quit); use `tail --pid=<runner pid> -n +1 -F out | ...` so tail ends with the runner, or put the run itself under `dori heavy` (GongDori 2026-10-21: six finished evals held slot.1-6 for up to 8 h through such ssh watchers, and new jobs queued on slot.8 alone).

### `dori heavy <label> --job <name> [--in FILE ...] [--out DIR] [--rl] [-- arg ...]`: one GPU line over two hosts
Runs a named job from `heavyQueue.jobs` in one line of GPU jobs that spans hosts, so a main host and a second GPU host work like one machine with two GPUs. The job's files live in `heavyQueue.jobDir` (default `/dev/shm/dori-heavy`, memory) and are deleted when it ends; it prints the job's stdout, copies the files the job wrote to `{out}` into `--out` and exits with the job's code. Extra arguments after `--` may hold only letters, digits and `. _ = : , + @ % -` (they cross ssh as one line).

- **Queue host** (`heavyQueue.queue` empty): the job waits in this host's line. At the front it starts here when this host's slots admit it (the same `heavySlots` / `heavyHeadroomPct` rules as above); when they refuse it for load, full slots or headroom (not while a job just taken settles), each of `heavyQueue.helpers` is asked in order and the first that admits it runs it (`HEAVY_HELPER <label> <helper>: <why not here>`); none: it waits, and the jobs behind it keep their order. A job that stands only behind jobs waiting for this host alone (plain `dori heavy <label> -- <cmd>`) may still go to a free helper; it never takes this host's slot ahead of them. `HEAVY_DONE <label> here|<helper>: exit N` when it ends.
- **Helper**: `dori heavy-worker` as the forced command of the queue host's key in `~/.ssh/authorized_keys`, e.g. `restrict,from="<queue host addresses>",command="env PATH=$HOME/.bun/bin:/usr/bin:/bin dori heavy-worker" ssh-ed25519 ...`. It runs only jobs named in its own `heavyQueue.jobs` (its own paths), an rl one only when its own `heavyQueue.rl` is true, and only when its own heavy slots admit it right now and no local job waits in its line; otherwise `WORKER_BUSY` and the queue host keeps waiting. The job gets PATH, HOME, LANG, a TMPDIR inside its folder and the job's `env`, nothing of the Dori's environment; nothing is kept after the run (a folder left by a killed run is deleted by the next request or `sweep`). The helper holds no key to the queue host for this.
- **A helper that cannot be reached** is skipped (`HEAVY_HELPER_DOWN`, once per change, no alert). **A run that breaks off** on a helper (the helper went down, its worker was killed) sends the job back to the front of the line, where it runs again from the start (`HEAVY_HELPER_CUT`).
- **Any other host** (`heavyQueue.queue` = argv that runs `dori` on the queue host, e.g. `["ssh", "-o", "BatchMode=yes", "-o", "ConnectTimeout=5", "main", "~/.bun/bin/dori"]`) sends the job there (`dori heavy-serve`, inputs and result as tar over the same ssh) and runs it itself, under its own slots, only when the queue host cannot be reached or the run broke off (`HEAVY_QUEUE_DOWN`). A host with `heavyQueue.rl` false never runs an rl job: cut off from the queue host, the job waits and tries again every 30 seconds.
- **rl jobs** (`--rl`, or `rl: true` on the job) take the same line as any job: the queue host first, then a helper. The queue host sends them as `run --rl ...`; a helper whose `heavyQueue.rl` is false refuses them (`WORKER_REFUSED rl jobs do not run on this host`, `HEAVY_HELPER_REFUSED` once on the queue host) and the job waits for the queue host. `heavyQueue.rl` defaults to true; set it false on a host that must not run reinforcement learning.

A job is `{"argv": [...], "env": {...}, "rl": false}`; argv fills `{in0}`, `{in1}`... (the `--in` files in order), `{in}` (their folder) and `{out}`. Each host names the same jobs with its own paths, e.g. a transcription job on both hosts with `"argv": ["<dori checkout>/skills/dori-mode/setups/discord-aoe/transcribe.sh", "{in0}"]` and that host's `DORI_ASR_DIR` in `env`; `hooks.transcribe` then becomes `["dori", "heavy", "voice", "--job", "transcribe", "--in", "{file}"]`. Count the jobs a helper took: `grep -c HEAVY_HELPER state/heavy/heavy.log` on the queue host, `grep -c HEAVY_WORKER_ADMIT` on the helper.

### `dori heavy <label> [--mem SIZE] --kind cpu|browser|gpu --sync PATH ... [--env NAME ...] [--tools NAME ...] [--back GLOB ...] [--stale-again] -- <command ...>`: a lane's own command on the less busy PC
With `--kind`, a lane's own command (a browser test, a build, a CPU job) runs on whichever PC is less busy. Without `--kind` it runs here as before.

With or without `--kind`, a `bash -c` (or `-lc`, ...) script that pipes and does not set pipefail itself runs as `set -o pipefail; <script>` (`HEAVY_PIPEFAIL <label>: ...`), so `bun test 2>&1 | tail -15` exits with bun's failure, not tail's 0. On 2026-11-02 such a run failed 171 of 744 tests on the helper and still said `HEAVY_DONE ... exit 0`. A pipe inside a script file (`bash run.sh`) is that script's business: put `set -o pipefail` in it.

- **Choice.** Busy is CPU load over cores in percent (for `gpu`, the larger of GPU use and CPU). When this host is more than 15 points busier than a helper, the first of `heavyQueue.helpers` that is under (busy - 15)% and whose heavy slots admit the job runs it (`HEAVY_SPREAD <label> <helper>: ...`). Otherwise the job waits for this host's slots under the usual rules (10% headroom), and a helper still takes it when this host refuses it for load, headroom or full slots, as with `--job`, and also while this host only waits for a just-started job to show its load (`heavySettleSec`), so the other PC never sits idle through that wait. A `cpu` or `browser` job tells its slot that its load shows after 20 seconds (a file `settle` in the slot), so on either PC the next job may start beside it after 20 seconds instead of `heavySettleSec` when every resource keeps 10% free; a `gpu` job and plain `dori heavy` keep `heavySettleSec`.
- **Kind first.** A helper whose `prefer` lists the job's kind is asked before anything else, however idle this host is, and takes it under its own slot and 10% headroom rule (`HEAVY_SPREAD <label> <helper>: gpu jobs go to this helper first (heavyQueue.helpers prefer)`); when none takes it the job goes on as above. Training, simulation and GPU tests go as `--kind gpu`, so the training sparks (ori644d, ori4b69, `prefer: ["gpu"]`) take them and this PC stays free for the lanes (owner 2026-11-08 23:03 KST: "우리 학습용 spark 있는데 자율 굴착 시험왜 여기서 돌리고 있어?"). Order the other helpers so `cpu` and `browser` work reaches the general PCs (4eae, cha) before the sparks.
- **Machine.** When the `--sync` paths hold an ELF program or library (a venv's compiled modules, `node_modules` native addons), the job carries its machine (`arch=aarch64`) and a helper of another machine refuses it (`HEAVY_HELPER_REFUSED ... this host is x86_64 and the job's --sync paths hold aarch64 programs or libraries, which do not run here`); a job without such files (a plain bun test, an ffmpeg render with the helper's own tools) goes to any machine.
- **Box check.** Before it takes a job a helper starts its box once with nothing in it. Where AppArmor keeps bwrap from making its namespaces (Ubuntu 24.04 without `/etc/apparmor.d/bwrap`, the training sparks until 2026-11-08) it refuses (`its box does not start on this host: ...`) instead of taking the job and failing it; the fix is that one root file, `profile bwrap /usr/bin/bwrap flags=(unconfined) { userns, }`, then `apparmor_parser -r` it.

- **The box on the helper.** The helper's forced command `dori heavy-worker` takes the verb `exec` only with `heavyQueue.exec: true` there (else `WORKER_REFUSED exec is off`), and it needs `bwrap` and a systemd user scope. - **Output.** stdout and stderr stream back live as text lines, and the exit code is the command's. A run is stale when the helper takes no bytes of the upload for `heavyQueue.staleMin` (20) minutes, or, after the upload, a helper that beats sends no line for that long (at least three of its beats): `HEAVY_HELPER_STALE <label> <helper>: <why>`, the ssh is killed, and the helper is asked to stop what is left (`dori heavy-worker "stop <label> <run>"`, the run id its admission line gave, `WORKER_ADMIT slot.N alive=60 run=<id>`, so another run of the same label goes on: that run's worker and what it started are killed, its job folder deleted and its slot freed, and only when the process behind its pid is still the worker recorded at admission (boot id and start time), so a reused pid is left alone, and killed before its folder is deleted; a helper that names no run id (an older dori) is not asked at all, since a stop by label could end another run of that label there; `HEAVY_HELPER_STOP <label> <helper>: WORKER_STOPPED N`, `HEAVY_WORKER_STOP` in the helper's log; the stop gets 30 s, at most `staleMin`, its stderr read included, and one left unended past that, as an ssh that exits and leaves a child holding its stderr, is let go: `no answer within N s`, and dori heavy exits without it). The stale run's ssh, local tar and untar that have not ended are killed too (by pid; one already ended is never signalled, its pid may be another's by then), and every wait on them together gets 5 s: whatever has not ended by then (a read stuck in uninterruptible disk I/O, a pipe a child of the ssh still holds) no longer holds the caller, which logs `HEAVY_STALE_LEFT <label> <helper>: ... pid N not ended` (or `its pipes are still held`) and exits without it. ssh, tar and untar stay in the caller's process group, so a Ctrl-C on its terminal ends them with it. The job then ends with exit 124, or with `--stale-again` goes back to the line, where that helper is skipped for 10 minutes and another helper or this host runs it (with `--helpers-only` the job waits that pause out; only helpers that turned it away for good end it with exit 2). ### `dori heavy hold-local [on --until <30|2h|HH:MM|ISO> --reason "<why>" [--except <account> ...] | off]`: a measuring window on this host

While a host measures speed or runs a regression (zzangdori on 0a83, announced in #dori-pair), a job of another account in its heavy slot moves the numbers: on 2026-11-08 `dori heavy` put gongdori's rvp-make5, make7 and make8, soodori's whole `bun test` (105 s) and an rv-occlude-points check into 0a83's slot whenever every helper was busy, and the window broke five times. Each account's slots are its own, so the hold lives where every account looks: one file per account in `heavyHoldDir` (`/tmp/dori-heavy-hold`, made 1777 and sticky like `backlog.hostDir`, so only its owner replaces or removes a file).

- `dori heavy hold-local on --until 30 --reason "rv-cpu-speed re-measure"` (the lead, or the Dori that measures) holds this host's heavy slots until then: `HEAVY_HOLD_LOCAL on by <account> until <ISO time> (<N> min left): <reason>; new heavy jobs of every account on this host go to a helper or wait, running ones go on`. `--until` takes minutes (`30`, `30m`), hours (`2h`), a time on this host's clock (`03:10`, the next one; 0a83's clock is UTC, so a KST time goes as an ISO time) or an ISO time (`2026-11-09T04:45+09:00`), at most 24 hours ahead; `--reason` is one line. A second `on` of the same account replaces its hold. `--except <account>` (repeatable, up to 16 account names) lets that account's jobs through: it is kept in the hold file and shown as `...(<N> min left); except yoodori, okdori: <reason>`, and a file whose `except` is not a list of account names holds every account.
- One job always runs here under a hold, with `HEAVY_HOLD_EXEMPT <label>: the owner's transcription (--job transcribe) runs here under the hold by ...`: `dori heavy <label> --job transcribe` (`hooks.transcribe` = `dori heavy voice --job transcribe`), since the owner waits for his transcript and an account without a helper (yoodori) would wait the whole window (lead 2026-11-08). While a hold is on it also passes this account's jobs that wait in line for the hold; without one it waits its turn. No other job is let through.
- `dori heavy hold-local off` ends this account's hold (`HEAVY_HOLD_LOCAL off by <account>`, and a line for each hold of another account still on); another account's hold ends at its time or with its own `off`. `dori heavy hold-local` alone prints the live holds, or `HEAVY_HOLD_LOCAL off: no hold on this host`.
- Meanwhile every `dori heavy` of every account on the host reads the holds before each try for a slot here, a job that was already waiting too: none takes a slot here, running jobs go on. A job that may go to a helper (`--kind ... --sync ...`, `--job`) goes to the first helper that admits it (`HEAVY_HOLD_LOCAL <label>: this host's heavy slots are held by ...; it goes to the first helper that admits it`); one that cannot (plain `dori heavy`, a `--kind` job that stays here with `HEAVY_LOCAL`, such as dori's own `bun test`, or one every helper refused) waits with `...; it cannot run on a helper, so it waits here until the hold ends` and starts after it. As a helper the host answers `WORKER_BUSY this host's heavy slots are held by ...`. GPU branches of `dori fork-explore` wait too.
- A hold whose file cannot be read (or is not a JSON object) still holds, and none holds longer than 24 hours after its file was last written, whatever its `until` says: the earlier of the file's mtime and ctime counts, since its owner can move mtime but not ctime. The account named is the file's owner, not what the file says. A hold directory this account cannot read holds too (`by ?`, until it can be read), and `on` refuses a directory that is not mode 1777. A hold file it cannot open holds as unreadable until its day ends (its times come from a look at it before the open); an entry it cannot even look at, or a hold directory it cannot read, holds until it can, renewed a minute at a time with a line naming it (only the directory's owner can cause that); and a file over 4 KiB holds as unreadable without being read whole; a file past its day is not opened at all. Each file is opened once, without waiting on a FIFO and without following a link, and read only when that descriptor is the file looked at, so an entry swapped in between changes nothing (a hold renewed in between, which `on` does by renaming a new file over the old, is looked at once more; an entry that keeps changing holds as unreadable); `on` writes its file and makes it readable through the descriptor it created, never through a name another account could swap; a link, FIFO, socket or other non-file in an account's place only drops that account's own hold. The directory is opened once too and everything in it reached through that descriptor: one that is a link or not mode 1777 holds (`by ?`) with nothing in it opened, and one swapped after the check is never read. Trust, written down: every Dori account on the host may set and clear its own hold and so stop every account's new local jobs; the account that made the directory (the first to set a hold) owns it and could drop every hold by replacing it or make it unreadable; anything else in the directory is hostile input that may never make a reader hang, follow a link, read past 4 KiB, crash, or miss a valid hold. Kubernetes cordon and Slurm DRAIN keep such a hold in one authorized controller instead; a broker of that kind for dori is a follow-up. A job that took a slot here while a hold was being set (its admission samples load and headroom first) gives the slot back once the hold is there.

### `dori heavy <label> --helpers-only --kind cpu|browser|gpu --sync PATH ... -- <command ...>`: on a helper, never here

The caller's choice for one job (zzangdori 2026-11-08): it runs only on a helper, never in this host's heavy slot. It takes no slot and leaves no ticket in this host's line (so jobs behind it here are not held up) and waits for a helper that admits it, asking them as a waiting `--kind` job does (`HEAVY_HELPERS_ONLY <label>: waits for a helper; it never runs on this host`). It ends with exit 2 and a `HEAVY_HELPERS_ONLY <label>: ...; it does not run here` line when no helper can take it: no `heavyQueue.helpers`, a job that cannot leave this host (the reason `HEAVY_LOCAL` would give), or every helper refused it (`no helper can run it (<helper>: <why>; ...)`, a missing bundle or an old dori there too). Without `--kind`, or with `--job` (a `--job` runs in the GPU line of every host), it is refused. Its `--mem` is not checked against this host's memory: each helper asked refuses an estimate it can never fit (`WORKER_REFUSED --mem ... never fits here`, so the next one is asked; exit 2 when none fits) and admits it only while that much stays free beside its running jobs, as any helper does for a `--kind` job with `--mem`. Inside a heavy job (`HEAVY_NESTED`) it runs in that job's slot as any inner job.
