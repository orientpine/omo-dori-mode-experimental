# Scripts

`scripts/` is a bun + TypeScript package with one CLI, `dori`. Every external command runs as an argv array; nothing builds a shell string.

## Install and test

```sh
cd skills/dori-mode/scripts
bun install          # dev dependencies only (types, tsc)
bun link             # puts `dori` on your PATH
bun test             # behavior tests with fake herdr/git/gh; nothing real is touched
bunx tsc --noEmit    # typecheck
```

Needs: bun 1.3+, herdr, git, and the GitHub CLI (`gh`) for `merged`/`closed` signals (npm for `published`). The `command`, `file` and `url` signals need nothing extra. The full list of signal kinds is in `sessions.md`. The host guard reads `sysctl`, `memory_pressure` and `df` on macOS; on Linux it reads `/proc/loadavg` and `df`, and memory and swap read as unknown.

### Backend `aoe`

With `"backend": "aoe"` lanes run as [agent-of-empires](https://github.com/njbrake/agent-of-empires) sessions instead of herdr panes. Needs `aoe` and `tmux`. What differs:

- A pane id is the session's tmux name, `aoe_<title>_<first 8 of the aoe id>`; `leadPane` and `ignorePanes` take these names. Panes are the live sessions in `aoe list` that have a tmux session; `aoe_term_*` terminals and stopped sessions are not panes. `workspace_id` is the aoe profile, so leave `workspaces` empty or list profiles.
- `launch` runs `aoe add <cwd> -t <key> --tool <agentCommand[0]> -l --extra-args "--model <model>"`, waits up to 3 minutes for the agent's `❯` prompt, then types the lane prompt. `agentCommand`'s other arguments and `laneWorkspace` are not used. aoe refuses a title+path pair that already exists, even in its trash.
- Text goes in through `dori type` (it runs `tmux send-keys -t =<name>: -l -- <text>` and a separate `Enter`, each an argv array, then checks the input box); lanes report to the lead the same way, never with a raw `send-keys`. Only the agent's input box (the lines between the last two `─` borders) counts as unsent text, so the same text echoed in the transcript does not trigger extra Enters, while a paste folded into `[paste #1 +13 lines]` or a tall box whose `❯` line scrolled away does.
- `close` runs `aoe session stop <id>` and `aoe rm <id>`: the session goes to the aoe trash and can be restored. It is never purged.
- The session id comes from the agent's `--session-id` argument (aoe passes one to omo), found under the tmux pane's pid; the environment and session-file rules follow as with herdr.
- `claim-done` without a key finds the lane by the tmux session it runs in. `guard` and `can-launch` count aoe sessions as panes.
- `watch` also reads `aoe ps --json` and the lane screens and prints `LANE_BLOCKED <key> <state> <pane>` for a working lane whose agent waits for a human (see `dori watch` below).
- `launch` reports `STARTUP_ERROR` with the agent's own message as soon as a startup error or `Pane is dead` shows while it waits for the prompt.

Hooks are argv templates for your messenger CLI. `{thread}`, `{text}` and `{key}` are filled into each argument separately, so the text stays one argument whatever it contains.

## Commands

### `dori update [--pull] [--dry-run]`

Applies the clone's current HEAD. `--pull` first runs `git -C <update.repo> pull --ff-only`. The first run saves HEAD and sorted known dotted config keys to `<stateDir>/update.json`, prints and logs `UPDATED first-run`, and restarts and announces nothing. If HEAD equals the saved `applied` SHA, it prints `UP_TO_DATE` without writing a watch-log line.

On a new HEAD it diffs the saved SHA against HEAD. Every service with a matching `update.services.paths` prefix is restarted once. It notes the service log's byte size before restarting and waits only for a new complete line matching `ready`, not an old ready line. With an empty `ready`, it checks user-unit activity instead. Each attempt prints and logs `RESTARTED <unit> <sha7>` or `RESTART_FAIL <unit> <reason>`; it attempts every affected service and then records the HEAD even when readiness failed. `UPDATED <old7>..<new7> changed=<n> restarted=<units>` lists successful restarts.

Keys this code knows but the saved code did not, and which are not set in the raw config file, print and log `CONFIG_NEW_KEY <key> unset in <config path> (default used)`. The known keys are saved for the next run. A restart failure sends `[ALERT] dori update: RESTART_FAIL ...` to `update.alertPane`, including new-key notices; without a restart failure the key notices do not trigger an alert. Git failures (including rejected pulls) print and log `UPDATE_FAIL` with stderr and alert the same pane, preserving the previously applied SHA.

After restarts, one `[UPDATE]` summary goes to `leadPane` (`DORI_LEAD_PANE` overrides it). It contains merged PR titles from old..new (or commit subjects if there are no merges), changed `references/`, `SKILL.md`, and `setups/**/README.md` paths under this skill, new config keys, restart results, and `update.announce`. Delivery prints and logs `ANNOUNCED <pane>` only after the pane-send helper saw the text submitted (see `dori type`), else `ANNOUNCE_FAIL <pane> <reason>` next to the helper's `NOT_SUBMITTED` line. A missing lead pane logs `ANNOUNCE_FAIL` without sending anything. Alerts and announcements use the same argv pane-send helper as lanes.

`--dry-run` prints planned local changes and restarts with a `DRY_RUN` prefix; it does not pull, restart, send, or write state/watch logs. A failed update/restart exits 1. The generic systemd path unit can run `dori update` after a pull; see the Discord + aoe setup.

### `dori notify-change --summary TEXT [--file PATH ...]`

Sends one `[UPDATE]` message containing the supplied summary and changed guidance paths, followed by `update.announce`, to `leadPane`. Use it when a Dori's own memory or AGENTS guidance changes outside the script clone. Prints and logs `ANNOUNCED <pane>` or `ANNOUNCE_FAIL <pane> <reason>`; failed delivery exits 1.

### `dori handover [--note FILE] [--title T] [--model M] [--keep-old] [--no-monitors] [--minutes N] [--dry-run]`

Moves the lead to a new agent session when its conversation got long (backend `aoe`). In order:

1. **Note.** Writes `<stateDir>/handover/<stamp>.md` (and `.json`): the open lanes with status, pane, thread and last report; every monitor the old session still runs, persistent or not, read from omo's manifest `<sessionsDir>/--<cwd>--/extensions/terminal/<session id>.json` (a monitor whose recorded process is gone is left out; the new session re-arms each one as persistent); the configured `handover.watchers`; open question cards; the old session's unfinished todos and goal; timers matching `handover.timers`; and the file given with `--note` (your own notes: what you promised, what you wait for). It refuses (`HANDOVER_REFUSED`, exit 2, nothing changed) when `leadPane` has no live aoe session, when `DORI_LEAD_PANE` is set in the environment (it overrides the config file, so lanes would keep reporting to the old pane; drop it, also from a wrapper script that exports it), when another handover holds `<stateDir>/handover/lock` and its process is alive, when a `handover.watchers` check fails for the old lead (`configured watchers not running`; `--no-monitors` does not skip it), or when neither a running monitor nor a configured watcher was found (the line names the manifest it read, or says the omo session could not be told; `--no-monitors` hands over without them). The session id comes from omo's `--session-id <id>` or `--session <session file>` argument (the uuid at the end of the file name), else a child's `PI_SESSION_ID`, else the session file made at start. When the old lead's path is a symlink it prints `HANDOVER_CWD_SYMLINK <path>, a symlink to <real path>; the new session opens in <cwd>`.
2. **New session.** Opens `aoe add <cwd> -t <title>` (`handover.cwd`, else the old lead's path with symlinks resolved), waits for the prompt, tells the old lead to stay quiet, and types `handover.prompt` plus "read the handover note at <path>". The note tells the new session to re-arm every monitor, to start each watcher whose `arm` says how, and to answer `HANDOVER_PROBE <id>` lines with `dori handover ack <id>`.
3. **Repoint.** `leadPane` in the config file (and `update.alertPane` if it named the old lead), `DORI_LEAD_TMUX` and `DORI_LEAD_AOE_ID` in `dori.env`, added when the file lacks them (each file backed up as `.bak-handover-<stamp>`), every open lane's brief footer (the old pane name replaced) plus a `[LEAD]` message with the new report command, and open question cards whose `tmux` was the old lead. Then it restarts `handover.services`, because `dori watch`, `freshness` and `dead-panes` read `leadPane` once at start. Lines: `HANDOVER_CONFIG`, `HANDOVER_ENV`, `HANDOVER_LANE <key> brief=rewritten|unchanged|missing told=yes|no`, `HANDOVER_CARDS`, `HANDOVER_RESTARTED`.
4. **Checks**, within `--minutes` (default `handover.verifyMin`): every monitor of the old session runs in the new one (same command and filter, or same path; the description only for a monitor with neither; persistent, not suspended, its process alive; the new session's manifest is read under the new cwd), `HANDOVER_MONITORS_OK`; every `handover.watchers` check exits 0 with the new pane and session filled in, `HANDOVER_WATCHERS_OK`; a freshly loaded config routes reports to the new pane; then a `[REPORT] handover-probe ... HANDOVER_PROBE <id>` line typed into the pane the config names, and a `{"kind":"handover-probe"}` line appended to the inbox file, are both acked by `dori handover ack <id> --state <stateDir>` run from the new pane (the probe line carries `--state`, so a Dori whose `dori` wrapper sets another state dir acks into the right one). An ack from any other pane (the old lead also sees the inbox) does not count.
5. **Close.** Only when every check passed: `HANDOVER_DONE`, then the old session is stopped and moved to the aoe trash (`HANDOVER_CLOSED`; `--keep-old` leaves it and tells it it is no longer the lead). A failed check prints `HANDOVER_VERIFY_FAIL <reasons>`, runs step 3 the other way round (config, env, lanes, cards back to the old lead, services restarted), tells the old lead it stays the lead, leaves the new session open to look at (`HANDOVER_ROLLED_BACK`) and exits 3.

Every line also goes to `watchLog` with source `handover`, and the outcome to `<stateDir>/handover/<stamp>.result.json`. Run from inside the lead's own tmux session, it re-runs itself as a `systemd-run --user` unit (`HANDOVER_DETACHED unit=... log=<stateDir>/handover/run.log`), because closing the old session ends every process in it. `--dry-run` writes the note and prints the plan (`HANDOVER_DRY_RUN`) without opening or moving anything.

`dori handover ack <id> [--state DIR]` records the pane it runs in for that probe id under `<DIR or stateDir>/handover/acks/` (`HANDOVER_ACK <id> pane=<pane>`).

### `dori launch <key> --title T --brief FILE --done "..." [--thread REF] [--model M] [--cwd DIR] [--tag T ...] [--done-weak-ok] [--goal G] [--challenge-before STEP ...] [--dry-run]`
Opens a lane: appends the footer to the brief, opens a tab, starts the agent, and checks the pane for startup errors after 20 seconds. Exit 3 on `STARTUP_ERROR`.

With `--thread discord:<id>` and `DORI_DISCORD_TOKEN` set, it then writes the lane's first message in that thread, so a thread opened for the lane never sits empty: `discord.laneStartText` with the title, the `--goal`, the first lines of the brief, the Done line, the key and the pane. It prints `THREAD_START_POSTED <ref> message=<id>`; a thread that already has a message is left as it is (`THREAD_START_SKIP`); without a token it prints `THREAD_START_NO_TOKEN` and a Discord error `THREAD_START_FAILED`, and the lane runs either way. `launch` never opens a thread itself: for work that is the same as or continues an earlier lane, pass the ref of the thread that work already has, so it stays in one place; several open lanes may share a thread, and a close leaves a shared `discord:` thread open while another open lane uses it.

Before the footer it adds a `## Past signals (written by dori launch)` section when earlier lanes in the same area have a record: lanes with the same `--cwd` (unless it is `defaultCwd`) or a shared tag. The key's first word is always a tag (`rl-e8` shares `rl` with `rl-e7`); `--tag` adds more and is stored in the lane. Up to `signals.launchLanes` lanes, newest first, one line each (numbered attempts, root-cause switch, fixes, rejected claims, re-sends and nudges) plus their warnings, so the new lane does not repeat a fix that already failed.

After Past signals comes `## Hypothesis tree (written by dori launch)` when the area's tree (the lane's `--cwd` unless it is `defaultCwd`, else its first tag, plus its other tags) has open entries: a few lines each of open, supported and falsified hypotheses, untried directions, research due, findings and recent attempts (see `dori tree`).

The footer tells the lane to report with `["dori","type","<leadPane>","--text","<report line>"]` (an argv array; `NOT_SUBMITTED` means send it once more), for herdr and aoe alike. `--goal "<the owner's words>"` is stored in the lane as `goal` and written into the footer with the instruction to run `dori intent-check` at each stage change; without it `launch` prints `LAUNCH_NO_GOAL <key>: ...` and goes on. `--challenge-before "<step>"` (repeatable) is stored as `challengeBefore` and tells the lane to put that step's plan through `dori challenge` first; `claim-done` refuses (`CHALLENGE_MISSING`, exit 5) until a challenge is on record. Require it for steps that cost hours or a GPU queue, change the approach, or follow a falsified hypothesis. `--dry-run` prints the brief exactly as the lane would read it (your text, Past signals, Hypothesis tree, footer) followed by `DRY_RUN <key>: ...`; it writes nothing, registers nothing and opens nothing.

When every `Done =` signal only checks that files exist or contain text (a `file` signal, or a command that is only `grep`/`test`/`cat`/`ls`/`wc`/`jq`..., directly, via `sh -c` or in a readable shell script), it first prints `LAUNCH_DONE_WEAK <key>: ...` asking for a signal that measures behavior, then launches anyway. `--done-weak-ok` silences it. A script it cannot read is not called weak.

`REF` is `<adapter>:<id>`, e.g. `discord:<thread id>` (digits only) or `telegram:<chat>/<topic>`. An empty id (`discord:`), a bare `--thread`, a ref without an adapter, or whitespace in the id is refused before anything opens: exit 1 with a one-line reason, and no lane is registered. Leaving `--thread` out is fine; the lane is registered with thread `none`. `adopt` checks `--thread` the same way.

### `dori adopt <key> --pane ID --title T --brief FILE --done "..." [--thread REF] [--tag T ...] [--goal G] [--challenge-before STEP ...]`
Registers a lane that is already running; `--goal` and `--challenge-before` are stored as for `launch`.

### `dori set-thread <key> <adapter>:<id>`
Points an open lane at another work thread, for example one created after the lane was launched. The ref is checked as for `launch`; a bad one exits 1 and leaves the lane unchanged. Prints `THREAD_SET <key> <old> -> <new>`.

### `dori sync [--write]`
Prints `key | thread | pane | session | status` for every open lane and every unregistered agent pane, followed by a `SIGNALS <key> [<outcome>] ...` line for each open lane that has a record (see `dori signals`) and drift. Read-only unless `--write`, which stores session ids.

### `dori claim-done [<key>] --evidence TEXT` / `dori object-done <key> --reason TEXT ...`
The two halves of the done flow. Both message the lane's pane and check that Enter registered. A claim on a paused lane is recorded and printed as `LANE_DONE_CLAIMED_PAUSED <key> <pane> <evidence>` (and once by `dori watch`), but it never closes the lane on a timer; the lead closes it or objects. A lane launched with `--challenge-before` that has no `dori challenge` on record gets `CHALLENGE_MISSING <key>: ...` and exit 5 instead of a claim.

### `dori pause <key> <reason>` / `dori resume <key>`
Parks a working or not-done lane that waits on a human, for example on the owner's approval. The status becomes `paused`, the previous one is kept in `pausedFrom`, and `PAUSED: <reason>` goes into the lane's history. While paused, `dori freshness` neither nudges nor posts for it, `dori watch` reports no `LANE_BLOCKED` and does not auto-close it, and `dori dead-panes` skips its pane. `dori resume` restores the previous status with a `RESUMED` history entry and restarts the silence clock, so the first nudge comes a full `nudgeAfterMin` later; when a claim arrived during the pause it prints a `NOTE` saying so. Pausing a lane that is not working or not-done, or resuming one that is not paused, exits 1.

### `dori fix-attempt <key> --metric M --hypothesis H [--hypotheses H1 --test T1 ...] [--improved] [--no-hypotheses REASON]`
Records a fix you asked the lane for, in the lane's `fixes`, and takes one step of the stuck ladder. Prints `FIX_RECORDED <key> attempt=<n> on-metric=<m> stuck=<s> (tagged t, inferred i)` (n: this metric and hypothesis; m: this metric; s: the stuck count) and the `STUCK` line when the metric's rung went up. `dori freshness` records the lane's own reports tagged `(fix: <metric> / <hypothesis>)` the same way; a fix you recorded that the lane then reports counts once. Before it records, it prints what the area already tried on that metric: `PRIOR_FIX <lane> "<metric>": <hypothesis> xN, ...` per lane (this lane, its cwd, its tags), or `PRIOR_FIX none on "<metric>" in this area`, and `PRIOR_ATTEMPTS <key> numbered attempts 1-N, root-cause switch: <time|none>` when the lane's reports number their attempts. See `sessions.md`, "Repeated fixes".


The stuck ladder: failed attempts on one metric are counted whatever the hypothesis (a fix you asked for that the lane then reports counts once), in the lane's current session, since the last one recorded with `--improved` (the previous fix moved the metric) and since the last PASS of the metric its reports showed; the inferred count (`dori repeat-check`, under the same `autoSignals.aliases` name) counts too, and the larger one is the stuck count. Each rung change prints and logs one line, `STUCK <key> "<metric>" rung N (tagged t, inferred i, hypotheses h[, fixated][, inferred only]) -> <what to do> [<old names>]` (source `stuck`), once per rung; a count that went down (PASS, `--improved`) lowers the mark silently, so the next stuck run alerts again. The old names at the end (`HYPOTHESES_REQUIRED`, `RESEARCH_DUE`, `ROLLOVER_DUE`, `SAME_FIX_3` when fixated, `REPEAT_SUSPECT` when the inferred count reached `stuck.researchAt`) stay for one release so monitors that grep them still match.

- Rung 2, from `stuck.hypothesesAt` (2): `fix-attempt` refuses unless you give at least `explore.minHypotheses` (3) distinct competing hypotheses with `--hypotheses`, each followed by one cheap discriminating experiment with `--test`, in the same order. A refusal prints `HYPOTHESES_REQUIRED <key> attempt N on "<metric>" ...` with the command to run instead, logs the same line, exits 5 and records nothing. An accepted branch prints and logs `STUCK_BRANCH <key> attempt N on "<metric>": H4 ... (test: ...) | ...` and puts every hypothesis with its test into the area's tree as open. `--no-hypotheses "<reason>"` goes on without them and logs `HYPOTHESES_OVERRIDE <key> ...: <reason>`. Every recorded attempt also goes into the tree as tried. A lane's own unbranched second report is rung 2 too: the `STUCK` line tells you to re-instruct it with hypotheses.
- Rung 3, from `stuck.researchAt` (3): a research entry goes into the tree (so the next brief in the area shows it), and with `explore.sendResearchToLane` the lane gets `explore.researchText`: ulw research on the exact symptom, then a `dori challenge` of its next plan, before the next patch, in the same session. No rollover at this rung: a lane that is researching cannot be moved, and a moved one would re-read the research. An inferred count starts it too.
- Rung 4: an attempt that failed after rung 3, one hypothesis tried `stuck.fixatedAfter` (3) times after the lane branched (`fixated`), or an owner-check finding still there after a re-read the lead confirmed (`"@context"`, see `dori owner-check`). A count that jumps (the first untagged scan of a long loop) prints one line with the skipped rungs' old names and `first count` or `from rung N`. `--improved` restarts both halves (the inferred cycles counted so far become a baseline), a PASS too, and the `fix-attempt` gate uses this same count. The line says to decide a rollover (`dori rollover-propose`, then `dori handover --lane <key> --approved-by "lead:<reason and signal>"`). Nothing switches by itself, not even with `handover.autoRolloverLanes` on.
### `dori signals [--lane K | --cwd DIR | --tag T ...]`
What earlier lanes in one area tried and how it went, from records only (no model call). Read it before you re-instruct a lane. The options combine as "any of". The first line is the area: lanes, done claims rejected over claims, and rework (your messages to the lanes plus freshness nudges, per lane). Then per lane, newest first:

- its outcome (`open`, `paused`, `not-done`, `done-claimed`, `closed, verified`, `closed by the lead`), cwd, tags, re-sends (`scorecard.leadSendPattern` in `scorecard.leadSessions`) and nudges (`scorecard.lanesLog`);
- numbered fix attempts: a `[REPORT]` line or a message you typed into the lane matching `signals.numberedAttemptPattern` ("adjustment 2", "조정 2/2욌째"), with the words around the first mention and the latest mention before the root-cause switch;
- the root-cause switch: the first such message after an attempt that matches `signals.rootCausePattern` (a message about the root cause is never itself an attempt);
- tagged fixes by metric with each hypothesis and its count (the lane's `fixes`, or the `(fix: M / H)` tags in its reports when the sweep never recorded them);
- rejected done claims with the reasons;
- warnings: `SAME_FIX` (one metric and hypothesis `stuck.fixatedAfter` times), `REPEAT` (one metric over several hypotheses, or numbered attempts up to `stuck.fixatedAfter` with no root-cause switch), `REJECTED` (two or more rejected claims).

Without an option it prints one `SIGNALS <key> [<outcome>] fixes N, attempts 1-N, rejected R/C, re-sends S, nudges U` line per open lane with a record. Session files older than the oldest lane asked about are not read.

### Exploring when stuck

The point of these commands: when a fix does not move a metric, the next step is to find out which explanation is true, not to patch again. Each has its own section below; how the lead uses them is in `sessions.md`, "Stuck: branch, look outside, check intent", and the E7 example in `operating-lessons.md`.

### `dori tree [show|add|falsify|support|close|reopen] [ID] [--lane K | --cwd DIR | --tag T] [--kind K] [--text T] [--test X] [--metric M] [--result R]`
The hypothesis tree of one area: a JSON file per repo (`<stateDir>/trees/cwd-<path>.json`) or tag (`tag-<tag>.json`). A lane's area is its cwd unless that is `defaultCwd`, else its first tag. Without an area option it uses the lane of the pane it runs in, else the current directory. Entries have an id by kind: `H` hypothesis, `D` untried direction, `F` finding, `R` research due, `T` an attempt tried; and a status: `open`, `falsified`, `supported`, `closed`.

- `show` (default) prints `TREE <area>: N entries` and the entries by group: open hypotheses with their tests, supported, falsified (do not retry), untried directions, research due, findings, attempts tried, then closed ones.
- `add --kind hypothesis|direction|finding|research --text T [--test X] [--metric M] [--result R]` prints `TREE_ADDED <id>`, or `TREE_EXISTS <id>` when the same kind already says the same thing (a missing test is filled in).
- `falsify|support|close|reopen <ID> [--result R]` sets the status and prints `TREE_SET <id> <status> -> <result>`.

Fed automatically by `fix-attempt` (tried attempts, branched hypotheses, research due), `freshness` (the lanes' tagged fix reports), and `fork-explore` (results). `launch` attaches the compact form to new briefs.

### `dori challenge <key> --plan FILE [--model M] [--all]` and `dori challenge --check [<key>]`
Adversarial review before a big step. It sends the plan (up to 60,000 characters), the lane's title and goal, and the area's tree to a model of another family than the lane's own model, in a fresh context (no session, skills, context files or lane history): `explore.challengeCommand`, by default `omo -p --no-session --tools read,grep,find,ls --no-extensions --no-skills --no-context-files --omo-senpi-disabled --system-prompt <reviewer instructions> --model <reviewer> <prompt>`, run in the plan's repository (the git top level of the plan's directory, else that directory). The reviewer can read and search files there to check what the plan cites; it cannot change files or run anything. Its final reply is the review, under three headings: "Reasons this will fail", "Missing alternatives", "Cheapest falsifying test". Only a reply with all three is saved. Families come from the model id (`claude`/`opus`/`sonnet`/`fable` anthropic, `gpt`/`o3`/`codex` openai, `grok` xai, `gemini` google, `qwen`, `kimi`, `glm`, `deepseek` ...), whatever provider serves it.

Why read-only tools: `omo -p` runs the reviewer as an agent, and an agent run ends at the first reply without a tool call. With `--no-tools`, a reviewer given a plan that cites files and results answered "I'll read the cited evidence first, then write the review" and that sentence was its whole output (reproduced 5 of 5 on a real plan; with read-only tools the same prompt wrote the review 4 of 4, reading 7-8 times first).

Order: by default the best GPT, then the best Claude, then the best Grok model that omo offers with a subscription login (`chatgpt-subscription/gpt-6-astra`, `anthropic-subscription/claude-fable-5-1`, `xai/grok-4.7`), then a second model of each family (`gpt-6.1-sol`, `claude-opus-5-5`, `grok-4.6`). Why these: `gpt-6-astra` is OpenAI's top tier in omo's catalog (priced 5x `gpt-6.1-sol`, and omo's escalation model above it), `claude-fable-5-1` is Anthropic's (priced 2.5x `claude-opus-5-5`, newer than `claude-fable-5`), and `grok-4.7` is the newest xai model (4.3 to 4.7 cost the same). On another machine, run `dori challenge --check` and put its best callable model of each family first. The lane's own family is always skipped, so on a Claude lane the order is GPT, then Grok. Without `--all` the first reviewer that writes a review is the only one asked (fallback order). With `--all` one review is collected from each family in list order, the next model of a family standing in for one that fails; each review is saved and recorded, and a family with none is reported. `--model` asks that one model (refused when it is the lane's family).

Before any call, each id is checked on this host: `explore.modelsCommand` lists the models each provider offers and `explore.authCommand` says whether a provider is logged in. An id whose provider offers it and is logged in is called as listed; one whose provider is not logged in (or does not offer it) is called on a logged-in provider that offers the same model (`github-copilot/gpt-6-astra` -> `chatgpt-subscription/gpt-6-astra`); one no logged-in provider offers is skipped with the reason. Ids are compared exactly as `omo --list-models` prints them (a `:high`-style thinking suffix aside): omo itself runs an inexact id as whatever it matches (`xai/grok-4` ran as `grok-4.7`), so such an id is skipped rather than silently doubled. `dori challenge --check [<key>]` prints this per id, without a review: `REVIEWER_OK <id> [-> <id called>] (<family>): <why>` or `REVIEWER_SKIP <id> (<family>): <why>`; with a key, only the ids of another family than that lane's model. It exits 1 when none can be called.

- A final reply that lacks a heading gets one stricter retry that quotes what went wrong (a safety net; with read-only tools it should not be needed). If the retry still lacks one, both replies are saved as `<stateDir>/challenges/<key>/<time>-<model>-raw.md` and the next reviewer is asked.
- A reviewer that exits with an error, or times out after `explore.challengeMinutes` (exit 124), is skipped for the next one.
- Each skip prints `CHALLENGE_SKIP <model>: <why>` and is logged as `CHALLENGE_SKIP <key> ...`; when no reviewer writes a complete review the command fails (exit 1) with every reason and raw file, logged as `CHALLENGE_FAILED <key> ...`.

Each review is saved as `<stateDir>/challenges/<key>/<time>-<model>.md` (with `- Read access: <dir>`, and `- Attempts: 2` when the stricter retry wrote it), recorded in the lane's `challenges`, logged as `CHALLENGE <key> reviewer=<model> ...`, and printed with `CHALLENGE_SAVED <file> reviewer=<model>`.

### `dori fork-explore <key> --metric M --hypotheses H1 --test T1 --hypotheses H2 --test T2 ... [--gpu N ...|--gpu-all] [--mode agent|cmd] [--minutes N] [--model M]`
Parallel branch exploration: one short, time-boxed task per hypothesis (at least two), all measuring the same metric M. With `--mode agent` (default) each branch is a headless agent run, `explore.branchCommand` in the lane's cwd, told its hypothesis, the metric, its test, the time limit (`--minutes`, default `explore.branchMinutes`), not to edit tracked files, and to end with `METRIC:`, `VERDICT: supports|falsifies|inconclusive` and `EVIDENCE:` lines. With `--mode cmd` each `--test` is a command run with `bash -lc` in the lane's cwd, which prints the same lines. CPU branches start at once. A GPU branch (`--gpu <branch number>`, repeatable, or `--gpu-all`) first takes a heavy slot, the same slots and load limit as `dori heavy`, so GPU branches queue one by one while CPU branches run. A branch that runs out of time is `timeout`; one that fails without a verdict is `error`. It prints `FORK_START ...`, then one markdown table (branch, hypothesis, metric value, verdict, evidence, run time, cpu or gpu with the slot wait), and `FORK_SAVED <file>`. The table and the raw results go to `<stateDir>/explore/<key>/<time>.md` and the lane's `explorations`; each hypothesis goes into the tree as falsified (falsifies), supported (supports) or open with the result noted; the watch log gets `FORK_EXPLORE <key> ...`.

### `dori research-hint <key> [--send]`
A search plan for the lane's stuck symptom, from its records only (no model call): `RESEARCH_HINT <key> on "<metric>": N attempts, ...`, the symptom and last report, what was already tried, four or five queries (papers, GitHub issues, failure-mode write-ups, how other repositories set the same problem up, other causes now that a hypothesis is falsified), and the `dori tree add --kind finding` line to record what was found. Works on closed lanes too.

With `--send` (and at rung 3 of the stuck ladder, when `explore.sendResearchToLane` is on) it types `explore.researchText` into the lane's pane as one line. The text starts with `ulw research `, so omo attaches its ulw-research skill pointer, and the lane runs the search as an ultra research: sources read in the owner's browser, a claim graph, a cited result. omo attaches that pointer only to typed (interactive or rpc) input that names `ulw research` outside quotes, code and links. It never attaches it when the text starts with a `[TAG]` such as `[LEAD]`, nor in a child or team-member session, and a brief that mentions it does not count. `{question}` is the research question built from the lane's records: the exact symptom (the metric that does not improve, the last report), what was tried, what a test ruled out and how, what is still open, and what to look for (papers, GitHub issues and discussions, repos that hit the symptom). The rest of the default text tells the lane to read the ulw-research SKILL.md first, record findings with `dori tree add --kind finding`, have its next plan challenged with `dori challenge`, and report back before the next patch. It prints `RESEARCH_SENT <key>` (or `RESEARCH_SEND_FAILED`, exit 1) and records the send in the lane's `research`.

### `dori research-check <key>`
Did the last ulw research text start the skill? It looks in the lane's session directory (`sessionsDir/--<cwd with / as ->--/`) for the newest `*.jsonl` written since the send that holds a user message starting with the typed text. From the send on, it looks for two markers:

- the pointer: an entry `{"type":"custom_message","customType":"omo-ulw-research:skill-pointer",...}`, or `<omo-ulw-research-pointer>` inside the typed user message (omo appends it there when the agent was busy);
- the skill read: an assistant `toolCall` block that reads the file, not one that only names it: the `read` tool with a path ending in `ulw-research/SKILL.md`, or an `eval`/`bash` call whose code holds the file's path (`/...`, `~/...`, `./...`, `${dir}/...`) as a whole string literal and reads a file with it (`Bun.file`, `readFile`, `readFileSync`, `createReadStream`, or `cat`/`sed`/`head`/`tail`/... on an interpolated path), or runs `cat`/`sed`/`head`/`tail`/`less`/`awk`/... on the path itself. A finding written with `dori tree add`, an `echo`, a memory note, or a log search that quotes the path is a mention and does not count. Only a read after the typed message reached the session counts for this send: a lane still busy with an earlier send may read the skill after the send but before it gets the new text, and that read counts as an earlier read.

Both markers: `RESEARCH_STARTED <key> ...`. Not yet: `RESEARCH_PENDING <key> N min ...: seen=… pointer=… skill-read=…`. Still missing after `explore.researchVerifyMin`: `RESEARCH_NOT_STARTED <key> ...` (exit 6), with what is missing (the text never reached the session log, omo attached no pointer, or the lane did not read the skill; a lane that read it earlier in the same session often does not read it again and answers without the skill's protocol, and the line says so) and the fix (re-send with `--send`, or tell the lane to read the SKILL.md). `dori freshness` runs the same check on every tick for a lane with a pending send and prints `RESEARCH_STARTED` / `RESEARCH_NOT_STARTED`. The decided line goes to the watch log once (source `research`), and the result is kept in the lane's `research.result`.

### `dori repeat-check <key> [--since ISO|Nd|Nh] [--until ISO] [--repo DIR ...] [--backtest]`
Untagged repeats, the inferred half of the stuck count. Lanes rarely tag their fixes, so a tagged count stays low while a lane re-targets one failing gate with prescription after prescription. This reads what the lane leaves anyway: its `[REPORT]` lines (in its own session folder, `<sessionsDir>/--<cwd>--`, and in `scorecard.leadSessions`), the commit subjects on its branches (`worktrees`, its cwd if that is a repository, and `--repo`) and its hypothesis-tree entries. A gate line fails when an item carries a value and `FAIL` (`교착 554 FAIL(≤2)`, or the items of a bare `FAIL 도랑 위 덤프 1·교착 58` list up to a dash), or when a prescription's verdict (`기각`, `판정 불가`, `REJECTED`) names a known metric in its sentence. A new attempt targets it when one sentence (`autoSignals.targetScope`) holds a prescription word and the metric's name or an alias, and is not negated ("안 띄움", "not launched") or only a diagnosis; a failure is never consumed by the report that states it. Each "failed, then a new attempt on it" is one cycle; attempts within `autoSignals.repeatGapMin` are one; a `PASS` of the metric starts it again. From `stuck.researchAt` cycles it prints `INFERRED <key> "<metric>" <n> (from untagged ...; tagged <t>) ...` with every failure and attempt line as evidence, else `REPEAT_NONE` with the counts. In `freshness` the counts and each metric's last PASS are kept in the lane's `inferred`, a grown count's full chain is appended to `<stateDir>/auto-signals/<key>.md`, and every changed metric takes a step of the stuck ladder (its `STUCK` line, if the rung went up). A PASS before the sweep ends the run, so no line. Default window: the lane's current session. `--backtest` replays the window and prints each time a count reached `stuck.researchAt` or grew past it, with its time.

### `dori owner-check <key> [--force | --reread]`
A reviewer of another family than the lane's (`reviewers.models` with `autoSignals.ownerCheck.first` in front, checked like `challenge` reviewers) gets the lane's brief (without the Past signals and tree sections launch adds), the owner's goal, the lead's `[LEAD]` relays that carry the owner's words (a Discord message link, or marked 원문 / verbatim) and the newest reports, all as written in Korean or any language, and answers in blocks `VERDICT: VIOLATION | CONTRADICTION | GOAL_LOSS`, `OWNER: "<quote>"`, `REPORT: "<quote>"`, `WHY: ...`, or `VERDICT: OK`. The prompt also carries the registry's fact on a done claim (`Done claim on record: none ...` or the claim's time and evidence): a report that only names `dori claim-done` or quotes the footer is not a claim, and only reports that were sent (a `send-keys`, `send-text` or `dori type` call) or received (text typed into the session) are read, so a report template quoted in a goal, brief or note is no report. Prints `OWNER_CHECK <key> <kind> owner "..." vs report "...": <why> [reviewer <model>]`; a quote not found in the inputs adds `(unverified: ...)`, and so does a CONTRADICTION resting on the claim-done command while no claim is on record. An unverified finding goes to the watch log as that `OWNER_CHECK` line and stays off the ladder. A verified finding is the stuck ladder's context rung: it prints and logs one line, `STUCK <key> "@context" rung context (<kinds>: owner "..." vs report "...": <why>; reviewer <model>) -> confirm the finding, then dori owner-check <key> --reread ... [OWNER_CHECK_<kind>]`; a finding still there after a re-read you confirmed with `--reread` is `rung 4` (`[... ROLLOVER_DUE]`; without a re-read it stays the context rung), and a clean check (`OWNER_CHECK <key> OK ...`, logged as such) ends the context rung. It runs only when a report is newer than the last check, at most once per `autoSignals.ownerCheck.minIntervalMin` and `maxPerDay` times a day per lane (`OWNER_CHECK_SKIP` says why); `--force` skips the interval and daily limit, never the new-report rule. A reviewer that fails or answers out of format is skipped for the next; none left is `OWNER_CHECK_FAILED` (exit 1). The result is kept in the lane's `ownerCheck` (with the first finding). Nothing is sent to the lane by the check. `--reread` is your confirmation of the last finding: it types `stuck.rereadText` into the lane (its brief path and the finding filled in) and prints `REREAD_SENT` (or `REREAD_FAILED`, exit 1); after a clean check it refuses (`REREAD_REFUSED`, exit 1).

### `dori intent-check <key> [--direction TEXT] [--next TEXT] [--goal G]`
Prints the owner's goal (the lane's `goal`) next to the lane's current direction and next step, then runs the owner check on them at once (`dori owner-check`, with no interval and no new report needed but within `autoSignals.ownerCheck.maxPerDay`; the stated direction is in the prompt and counts as evidence a finding may quote): `OWNER_CHECK <key> OK ...`, or a finding with its `STUCK <key> "@context" ...` line. It replaced a count of shared words with the goal, which could not judge a Korean goal at all (an English report of the same step scored 0.00). The direction is what the lane last stated with `--direction` (stored in the lane's `direction` with `--next`), else its last report; the next step is `--next`, else a "next:" in the report, else the test of its first open hypothesis. `--goal` sets the goal of a lane launched without one. `dori freshness` runs the owner check first for a lane whose milestone report matches `explore.stagePattern` (a new stage, phase, pivot or next step).

### `dori scorecard [--date YYYY-MM-DD|today|yesterday] [--post] [--to discord:<id>]`
Prints the day's token scorecard, computed from records only (no model call), for the calendar day in `scorecard.timeZone` (default today):

1. cost per verified completion: the API-priced cost of every assistant call in `scorecard.sessions` (default `sessionsDir`) that day, over the lanes closed that day (a close always re-reads the Done signals);
2. the done-claim rejection rate, always next to line 1, since either alone can be gamed: claims that day, and the `not-done` entries that answered a claim (a lane parked as not-done is not a rejection; a repeated claim counts once);
3. the three lanes with most rework: the lead's messages to the lane (`leadSendPattern` in `leadSessions`) plus freshness nudges (`lanesLog`);
4. first reply to the owner: median and p90 seconds from an owner message in the inbox to the first lead tool result matching `replyPattern` after the message reached the lead session;

plus the lead's context tax: its cost, the share spent re-reading cache, and its median context size. A line whose source is not configured says so. Each run saves the card for the lead to read (`SAVED <path>`): `<stateDir>/scorecard/<date>.json` (the numbers and the card) and `latest.md` (the card); day files older than `scorecard.keepDays` are removed. Nothing is posted unless `--post` is given, which sends the card to `--to`, `scorecard.postTo` or `DORI_DISCORD_CHANNEL`.

### `dori close <key> [--note TEXT]`
Closes a lane now. Refuses (exit 2) unless every `Done =` signal reads back live. On success it marks the thread done through `hooks.threadDone`, then, when `DORI_DISCORD_TOKEN` is set and the thread is `discord:<id>`, sets the thread's name to the done mark (`✅` or `[done]`, per `discord.statusStyle`) and archives it. An archived thread is unarchived, renamed and archived again, because Discord refuses to rename an archived thread; a thread that already shows done and is archived is left alone. If that fails, `THREAD_DONE_WARN <key> <thread>: <error>` is printed and the close still succeeds. A thread that another open lane also uses is left open (`thread left open` in the receipt). Then it closes the tab, and removes the lane's worktrees with a plain `git worktree remove`, which refuses a dirty worktree. When `hooks.threadDone` is set but the lane has no usable thread (`none`, empty, or malformed), the hook is not run and `THREAD_MISSING <key> thread=...` is printed before `CLOSED`, and the receipt records `thread missing`; close that thread by hand, or run `dori set-thread` before closing. The automatic close in `dori watch` prints the same line before `LANE_CLOSED`.

### `dori watch`
Runs forever. Every 30 seconds it prints each new claim once (`LANE_DONE_CLAIMED`). Claims older than `closeAfterMin` are settled: unpushed or uncommitted work and failing signals turn into objections (`LANE_NOT_DONE`); otherwise the lane is closed (`LANE_CLOSED`). The thread gets `discord.doneText` through `hooks.threadDone`, not the claim's evidence (that stays in the lane's record and the `LANE_DONE_CLAIMED` line); `discord.postRawReports: true` posts `Done: <evidence>` as before. The deadline lives in the registry, so a restart picks up where it left off.

With backend `aoe` it also prints `LANE_BLOCKED <key> <state> <pane>` once each time a working (or not-done) lane's agent stops for a human. Unless the screen shows a running turn (`esc to interrupt`), `state` is `waiting` or `error` when `aoe ps --json` says so, `question` when omo's question UI (`Ask user ·`, `(0/1 answered)`) is on screen (aoe shows that as `idle`), and `idle` once the turn has stayed ended for 45 seconds. A lane waiting on something that will wake it is not idle: its status line shows a monitor (`◉ watching`), wake sources on duty (`wake source`), a scheduled goal continuation (`goal continues in`) or an active goal (`Pursuing goal`). The state is kept in the lane's `blocked` and `idleSince` fields, so a restart does not repeat the line; when the lane runs again they clear and the next block is reported again. If `aoe ps` fails, the tick prints `LANE_WATCH_WARN blocked check: ...` and the done flow still runs.

### `dori freshness [--loop MIN]`
For working lanes that have gone quiet: a nudge in the pane after `nudgeAfterMin`, then after `postAfterMin` a short status line in the owner's words posted to its thread: `discord.quietText` with `{min}` as the minutes since the last report. The report itself is a note for the lead, so it is not posted; it goes to `leadPane` as `[DORI] <key>: N min without a new report ... Last report: <report>` for the lead to retell in plain words. Each happens once per silence. With `discord.postRawReports: true` the old behavior returns: the last `[REPORT]` line is posted to the thread, home paths and pane ids scrubbed, and the lead gets no note.

Lanes send `[REPORT]` lines to the lead pane, so the report is read from the last 3000 lines of `leadPane` first and from the lane's own screen second. A report the agent UI wrapped over several lines is joined up to the next blank line. A report that differs from the last one seen (kept in the lane's `lastReport`) counts as hearing from the lane and starts a new silence. Output lines: `NUDGED`, `NUDGE-FAILED` (the text stayed in the pane's input), `POSTED` (ending in `; lead told` or `; lead not told: <why>`), `NO-REPORT`, `STUCK` (one per rung change of the stuck ladder, from a new report tagged `(fix: <metric> / <hypothesis>)` and from the inferred count, which `dori repeat-check` computes over the lane's current session on each new report; see `dori fix-attempt`), `ROLLOVER_DUE` for a measured threshold, and `RESEARCH_STARTED` / `RESEARCH_NOT_STARTED`. Then, for at most `autoSignals.ownerCheck.perTick` lane heard from since its last owner check (a lane whose milestone report started a new stage first), it runs `dori owner-check`; a finding prints its `STUCK ... "@context"` line (OK results go only to the log). Only rung 3 types into the lane (the ulw research text); nothing else here sends anything to the lane.

### `dori dead-panes [--loop MIN]`
Prints `DEAD_PANE <id>` once per hour for a pane whose last lines match `deadPanePatterns`.

### `dori guard [--loop MIN]`
Prints `HOST_GUARD ALERT <reasons>` when load, free memory, free disk or the pane count crosses its threshold, and `HOST_GUARD CLEAR` when it recovers. It also prints `COMPUTE_READY` / `COMPUTE_BUSY` as load crosses `loadOk`. Only changes are printed.

### `dori can-launch`
Prints `CAN_LAUNCH` and exits 0 when the host has room for another lane. Otherwise it prints `HOLD <reasons>` and exits 4. The reasons come from the guard's memory, disk and pane-count thresholds. CPU load alone never holds a launch, because it moves too fast to plan around.

### `dori type <pane> --text TEXT | --text-file FILE`

Types text into an agent pane and confirms the agent took it. Every script that types into a pane (launch prompts, `[LEAD]` notes from `claim-done`, `object-done` and `freshness`, `update` announcements and alerts, `research-hint --send`, same-fix notes, handover prompts, `setups/discord-aoe/self-restart.sh`) goes through the same helper; use this command for your own relays to lanes.

1. Waits for the `❯` prompt (aoe), types the text as one argv argument, waits 1.5 s so a long text lands whole (it arrives as a paste), presses Enter.
2. Reads the input box, the lines between the last two `─` borders. Folded pastes (`[paste #1 +13 lines]`) and a tall box whose `❯` line scrolled out of view count as text still there; the same text in the transcript above does not. Still there after 3 s: one more Enter, and 3 s more.
3. An empty box must show a running turn (`esc to interrupt` on or just above the box) within 15 s.

Prints `SUBMITTED <pane>` (exit 0) or `NOT_SUBMITTED <pane> <reason>` (exit 1); `NOT_SUBMITTED` also goes to the watch log as `submit NOT_SUBMITTED <pane> <reason>`. Text with a backtick or `$(` is refused. `scorecard.leadSendPattern` counts `dori type <pane>` as a lead message to that lane.

### `dori send <slack|telegram|discord> --to TARGET --text TEXT [--thread ID] [--edit ID]`
Posts a message, or edits one with `--edit`. Tokens come from `DORI_SLACK_TOKEN` (plus `DORI_SLACK_COOKIE` for a user token), `DORI_TELEGRAM_TOKEN` or `DORI_DISCORD_TOKEN`. Text containing `$(` is refused, since it can only come from a shell string. Rate limits are retried with the server's wait time; other errors fail at once.

### `dori presence <slack|discord>`
Keeps the account shown as online until stopped.
- **Discord:** the bot connects to the gateway and identifies as online.
- **Slack, user token:** it opens one web-client-type socket and tickles it every minute. Slack shows a user active only while such a socket is open, and auto-aways an idle one after about 30 minutes.
- Run one instance per account. Two writers flip each other's presence.

### `dori inbound slack [--loop MIN]`
Prints `INBOUND <source> <channel> <thread> <ts> <user> <text>`. It reads from three places, each message once:
- `threads-view`: unread replies in threads the account follows (Slack's own Threads view);
- `own-thread`: new replies in any thread the Dori posted in, tagged or not;
- `unread`: DMs, group DMs and channels with unread mentions.

The Dori's own messages and bot messages are skipped. Every message the Dori posts records its thread in `<stateDir>/slack-threads.json`, whichever helper sends it, so a guest's untagged reply under a root posted with a raw API call is still found.

### `dori inbound discord`
Runs until stopped (run it as a service, see `setups/discord-aoe/`). It connects to the gateway with the message-content intent and handles:
- the owner's messages in `DORI_DISCORD_CHANNEL`, its threads, and DMs; everyone else, bots included, is skipped. Each gets the eyes reaction at once, a voice note is transcribed through `hooks.transcribe`, and one row is appended to the inbox file (`DORI_DISCORD_INBOX`, default `<stateDir>/discord/inbox.jsonl`) and printed as `INBOUND discord-<scope> <channel> <id> <author> <text>`;
- question-card taps and write-my-own submissions (below), appended as `kind:"answer"` rows and printed as `ANSWER <Qn> <kind> <answer> thread=… session=… tmux=…`;
- the bot's own messages (with `discord.autoUnEye`, on by default): when the bot it runs as writes in a channel, thread or DM, by any helper, the eyes come off every earlier owner message in that same channel, thread or DM, and off the message it replies to. Other bots' messages clear nothing. The messages still carrying eyes are kept in `eyes.json` beside the inbox file; the removals for one channel run one at a time and wait out a 429's `retry_after`. It prints `EYES_CLEARED <channel> by=<bot message> <ids>`, or `DISCORD_UNREACT_FAIL <id> <error>` for a message it could not clear;
- after each reconnect, the owner's messages it missed in the channel and its active threads, oldest first. It reads after the newest message among the inbox rows it wrote itself (`dm`, `channel`, `thread`), so rows other listeners append to a shared inbox file (another messenger, another channel) never move that point;
- an owner message in a done thread (✅ or `[done]`) reopens it: the thread is unarchived, marked working, and `THREAD_REOPENED <thread>` is printed.
- with `DORI_DISCORD_PAIR_CHANNEL` (a channel shared with a second Dori) and `DORI_DISCORD_PAIR_BOT` (that Dori's bot id): the owner's messages there become `scope:"pair"` rows with the eyes reaction and that bot's `scope:"pair-bot"` rows without it (the Dori rarely answers them, so the eyes would never come off); treat pair-bot rows as information, never as requests. Other bots there are skipped, the pair channel is backfilled too, and both scopes count as this listener's own rows for the backfill point. Unset: that channel is skipped like any other.

`DORI_DISCORD_SHADOW_INBOX=<file>` runs a shadow listener: the same inbox rows go to that file instead of the live inbox (it refuses to start when the two are the same file), but it writes nothing to Discord: no eyes reaction, no reopen, no unreact, no `eyes.json`, and card taps are not answered: for an owner's tap or typed answer it appends the `kind:"answer"` row the live listener would (same fields; `ts` is its own clock) without changing `questions.json` and prints `SHADOW_ANSWER <Qn> <answer>`; anything else prints `SHADOW_INTERACTION_SKIPPED <interaction> <custom id>`. It prints `DISCORD_LISTENER_READY shadow`. Use it beside a running listener to compare rows by message id before switching listeners; stop it before starting the new one for real.

A rejected token or a missing intent stops it (exit 3, or 4 for a disallowed intent); other disconnects retry with backoff up to a minute.

### `dori ask --text Q --option A [--option B ...] [--thread REF] [--session ID] [--tmux NAME]`
Posts a question card, pinging only the owner, and prints `ASKED <Qn> message=<id>`. With `--thread` the card goes inside that work thread and the thread is marked waiting (`[waiting]`, or ⏸️ with emoji status); without it the card goes to `DORI_DISCORD_CHANNEL`. Each option is shown in full as a numbered line with a short pick button beside it, and the first option's button is the highlighted one, so put your recommendation first; a write-my-own button that opens a text box is added last (1 to 9 options). `--thread`, `--session` and `--tmux` travel with the answer so you know where to relay it. Only the owner's answer counts: the card folds into `[answered] <Qn> … → <answer>` (`✅ <Qn> …` with emoji status) in the interaction response, the answer is appended to `<stateDir>/discord/answers.jsonl`. (`DORI_DISCORD_STATE_DIR` moves `questions.json` and `answers.jsonl` for `ask`, `questions`, `reopen`, `resolve` and the listener alike.) A card inside its thread is that thread's record; a card in the channel for a thread also leaves a silent record line in the thread. Once no question in the thread is open, the thread is marked working again (🔄). The listener takes taps from the channel and from the thread a card was posted in, and must be running to receive them. A failed thread rename is printed as `THREAD_STATUS_FAIL <thread> <error>` and does not fail the card. Every status change (ask, answer, reopen, resolve, `dori thread`, `dori close`) goes through the thread status queue: the mark is decided from the open cards when the rename runs, and a rename Discord refuses with 429 stays in `thread-status.json` (`THREAD_STATUS_PENDING <thread> <status> retry_in=<s>s`) until the listener applies it (`THREAD_STATUS_APPLIED`). An owner message in a thread with an open card adds `open_cards` and `note` to its inbox row and prints `CARD_STILL_OPEN <Qn,...> thread=<id> ...`; the card stays open until you resolve it.

### `dori questions [--open]` / `dori reopen <Qn>` / `dori resolve <Qn>`
List tracked questions; put a card's buttons back where it was posted (when a typed answer was not really an answer), marking its thread waiting again; forget a question once its follow-up is done. The folded card stays in the chat as the record. Resolving a card that is still open (dropped without an answer) marks its thread working again once no other question in it is open; resolving an answered card leaves the thread status alone.

### `dori lead`
Prints `<aoe-id> <tmux-session>` for the lead, followed by ` stopped` when its tmux session is not running (at boot it is not yet; `dori-lead.service` and `dori.sh` start it from the id). The tmux name comes from `DORI_LEAD_TMUX`, else `leadPane` (`DORI_LEAD_PANE` overrides the config). `DORI_LEAD_AOE_ID` is accepted only when its first eight characters match the tmux name's final eight characters; otherwise the id is found with `aoe list --json`. No configured lead, or no matching aoe session (`aoe list` includes stopped ones), exits 1 with a reason. `src/lead.ts` exports `findLead` for other callers.

### `dori thread open <title> [--from MSG_ID] [--first TEXT] [--session S]`
Opens a thread in `DORI_DISCORD_CHANNEL`, named with exactly one working mark in `discord.statusStyle`. `--from` starts it from that message; without it, `--first` is required and posted as the standalone thread's first message. Records the bare title and session (null when omitted) in `<cardDir>/threads.json` and prints `THREAD_OPENED discord:<id>`.

### `dori thread map discord:<id> <session|none>` / `dori thread list`
`map` sets the session, keeping the recorded title, and prints `THREAD_MAPPED discord:<id> <session|none>`. `none` stores null. `list` prints one line per mapping: `<id> <session|none> <title>`. The map uses `{"<id>":{"session":null,"title":"..."}}`; `cardDir` is `DORI_DISCORD_STATE_DIR`, else `<stateDir>/discord`, so an existing map there needs no migration. Writes use a temporary file and rename. The exported `threads`, `mapThread` and `dropThread` in `src/messenger/thread-map.ts` take the directory as their first argument and can be imported by a JS kernel.

### `dori thread set discord:<id> working|waiting|done [--open-card]`
Requests the status through the existing `ThreadStatusQueue`, without posting a message. Open question cards (or `--open-card`) keep a non-done thread waiting; done wins, archives it and drops its mapping after the status is applied. A rate-limited rename stays queued until the listener applies it; the mapping stays until then.

### `dori thread <reply|wait|done> discord:<thread id> <text>`
A ready `hooks.threadReply` / `hooks.threadDone` for Discord: `["dori", "thread", "reply", "{thread}", "{text}"]`. It shows typing, posts the text with emoji removed, and sets the status mark at the start of the thread name: `reply` working, `wait` waiting, `done` done. `done` archives the thread; the others unarchive it. Nothing is renamed when the mark already holds, because Discord allows only about two renames per ten minutes.

### `dori send discord --to <thread> [--edit <id>] --status working|done --text <text>`
Writes the text as the progress message in `discord.statusStyle`: `working: <text>` / `done: <text>`, or `⏳ · <text>` / `✅ <text>` with emoji.

### `dori transcribe <audio-file>`
Runs `hooks.transcribe` and prints the transcript. A failed or empty transcription is an error, never an empty message.

### `dori heavy <label> -- <command ...>`
Waits until load is under `heavyMaxLoad` and one of `heavySlots` is free, then runs the command and frees the slot when it exits. A slot held by a process that no longer exists (or a zombie) is taken over. Use it for full builds and test suites. Installs, focused tests and git do not need it.
